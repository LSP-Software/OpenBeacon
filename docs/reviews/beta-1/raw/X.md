### [X-01] No single owner for "end this session on this phone"; six entry points each clear a different subset of local state

- Location: apps/mobile/lib/deviceRemoved.ts:21-49 (`wipeThisPhone`); apps/mobile/lib/signOut.ts:39-86 (`signOutOfThisPhone`); apps/mobile/providers/SessionDataCleanup.tsx:22-34; apps/mobile/providers/TrackingProvider.tsx:171-176; apps/mobile/lib/deviceRemoved.ts:68-80 (`checkThisPhoneAfterSessionLoss`); apps/mobile/app/account/delete.tsx:314-331; apps/mobile/components/ConfirmIdentity.tsx:55-56; apps/mobile/app/serverUrl.tsx (server switch: no cleanup); apps/mobile/lib/auth-client.ts:9,47-51 (SecureStore with default accessibility)
- Category: design
- Severity: medium
- Launch: post-beta. Build the minimal version as part of fixing S8-01 (must-fix), not after it.
- Confidence: high
- Evidence: I read every caller of the cleanup helpers (`grep -rlF` for each of 22 helper names). This is what each path clears:

  | State                                                                               | Remove phone / device removed (`wipeThisPhone`) | Sign out, keep phone        | Delete account (`delete.tsx`) | Session lost elsewhere (UNAUTHORIZED) | Server switch                               |
  | ----------------------------------------------------------------------------------- | ----------------------------------------------- | --------------------------- | ----------------------------- | ------------------------------------- | ------------------------------------------- |
  | better-auth cookie + session cache                                                  | yes                                             | yes                         | yes                           | not explicitly                        | **no** (S8-01)                              |
  | Query cache, group colours, upload times                                            | yes                                             | yes (SessionDataCleanup)    | yes (SessionDataCleanup)      | yes (SessionDataCleanup)              | restart                                     |
  | Native capture + provisioned epoch keys                                             | yes                                             | yes                         | yes (TrackingProvider)        | yes (TrackingProvider)                | only once the new server rejects the cookie |
  | Native queue rows                                                                   | PENDING only (S6-10)                            | only if a pause was pending | **no**                        | **no**                                | no                                          |
  | Pending sharing changes                                                             | yes                                             | conditional                 | **no**                        | **no**                                | no                                          |
  | Pending join codes                                                                  | yes                                             | yes                         | **no**                        | **no**                                | no                                          |
  | Device private key, history keys, saved device link, `encryption.device.active.*`   | yes                                             | no (by design)              | **no** (S8-06)                | **no**                                | no                                          |
  | Registration record                                                                 | yes                                             | yes                         | yes (via session-loss check)  | yes                                   | scoped by URL                               |
  | Revoke token `sessionTokenToRevokeOnNextLogin`                                      | no                                              | written                     | no                            | no                                    | **sent to the new server** (S8-01)          |
  | `locationSharing.localPause/synced/clockOffset`, `encryption.history.unpublished.*` | no                                              | no                          | no                            | no                                    | no                                          |

  Storage keys are scoped in seven different ways. 7 key families are global (`custom_server_url`, `api_compatibility`, `tracking.keyCheck`, `tracking.keyState`, `map.showSymbols`, `theme.preference.*`, `encryption.device.registered`). 2 are scoped by server only (`locationSharing.clockOffset.[url]` and the compat state). 3 are scoped by server + user (+device) (`locationSharing.*` as a JSON-array suffix). 9 are per user, 3 per device, 1 per group only (`group.color.<groupId>`) and 1 per device + group. Three naming styles are in use: dotted, snake_case (`custom_server_url`, `api_compatibility`, `openbeacon_cookie`) and JSON-array suffixes. Credentials (`openbeacon_cookie`, `openbeacon_session_data`, `sessionTokenToRevokeOnNextLogin`) use SecureStore's default accessibility, which is `WHEN_UNLOCKED` and migratable on iOS. Keys use `WHEN_UNLOCKED_THIS_DEVICE_ONLY` through three copies of `getSecureStoreOptions` (S1-10).

  Leaving a group, being removed or deleting a group clears none of the per-group keys: `group.color.<id>`, `tracking.upload.<device>.<id>`, `map.keyBannerDismissed.<user>.<id>`, `recovery.historyWarningDismissedFrom.<user>.<id>`, the hidden-groups list, and queued rows (S6-03). Grepping `storage.remove(` finds no group-scoped removal.

  Each path has its own test (`deviceRemoved.test.ts`, `signOut.test.ts`, `SessionDataCleanup.test.tsx`). No test checks what each reason must clear, and no test covers account deletion.

- Failure scenario: (a) A user with a phone and a tablet deletes their account from the phone. `requestDeletion` deletes all sessions (accountRouter.ts:356) but doesn't revoke devices. The tablet's next request gets UNAUTHORIZED, not DEVICE_REMOVED. The tablet treats this as an ordinary session loss (`checkThisPhoneAfterSessionLoss` only forgets the registration record) and keeps the device private key, every History private key (versions 1 to N), the queued ciphertext and the pending sharing change. When the deletion completes 7 days later, nothing on the tablet ever runs again to remove them. S8-06 covers only the phone that pressed Delete. (b) Every bug in this area so far (S8-01, S8-06, S6-10) is a path that forgot one row of the table. The next feature that adds local state (Places, for example) has to be added to five places, and nothing fails when one is missed.
- Suggested fix: Add one `endSession({ reason })` in `lib/` with reason `signedOut | phoneRemoved | accountDeleted | serverChanged | sessionLost`, driven by a single table like the one above. Make the five entry points call it. Scope every credential and per-account key family by `[serverOrigin, userId]` through one key-builder module, and give credentials `WHEN_UNLOCKED_THIS_DEVICE_ONLY`. On `sessionLost`, keep keys, but record `{userId, lostAt}`. On the next sign-in by a different account, or after 30 days with no sign-in, wipe the previous user's key material. Add a table-driven test that checks each reason against the expected keys.

### [X-02] Errors have no machine-readable identity: the app branches on overloaded HTTP-style codes and on English message text

- Location: packages/api/src/trpc.ts:79-122 (a `cause` with only 3 values); apps/mobile/lib/tracking.ts:609-647 (upload classifier, message match at :625); apps/mobile/lib/groupEncryption.ts:62 (`HISTORY_RECIPIENT_MISMATCH_MESSAGE`, exported from packages/schemas); apps/mobile/app/setup/link.tsx:161; apps/mobile/lib/needsFreshSignIn.ts:3-4; apps/mobile/lib/recovery.ts:48-49,152,286,331-336; apps/mobile/app/account/add-device.tsx:49-53; apps/mobile/app/account/sign-out-others.tsx:36; docs/development/api-compatibility.md (error identity not listed as API surface)
- Category: design
- Severity: medium
- Launch: post-beta. Do it before fixing S6-03 and S6-06.
- Confidence: high
- Evidence: The server throws `TRPCError` with FORBIDDEN 39 times, NOT_FOUND 33, BAD_REQUEST 28, CONFLICT 23 and PRECONDITION_FAILED 7. Only three conditions get a machine-readable `data.cause` (`DEVICE_REMOVED`, `DEVICE_PENDING`, `DEVICE_UNVERIFIED`). The app compares `data.code` 56 times in 17 files, through six separate classifiers (`getErrorCode` in tracking.ts, `hasTrpcCode` in recovery.ts, `needsFreshSignIn`, `isDeviceRemovedError`, `codeNoLongerValid` in add-device, `problemMessage` in setup/link). It also matches server English text twice: `"The active device is not registered."` is a literal in tracking.ts:625 and is typed out separately in 4 server places (groupEpochRouter.ts:226 and :337, groupTracking.ts:160, groupEpochs.ts:406), and `HISTORY_RECIPIENT_MISMATCH_MESSAGE` is a shared constant. Examples of overloaded codes:
  - `uploadBatch` can throw FORBIDDEN with no message (group gone, groupTrackingRouter.ts:37), "You are not a member of this group" (procedures/auth/group.ts:13 and groupTrackingRouter.ts:45), or "The active device is not registered." The first two are permanent, and the third means "re-key".
  - "Fresh sign-in needed" is only recognisable as "FORBIDDEN with no cause" (`needsFreshSignIn`). sign-out-others treats any FORBIDDEN as that case.
  - `changePhrase`/`reset` map CONFLICT or NOT_FOUND to "Your recovery phrase changed on another phone" (recovery.ts:286, :334). NOT_FOUND from `lockThisDevice` ("This phone isn't registered yet.", deviceActivation.ts:60) gets that copy too.
  - CONFLICT means "already a member", "stale ciphertext", "sole owner", "history key exists" and "phone already set up" across 23 throw sites.

  The compatibility doc doesn't treat codes, causes or messages as part of the API, so a copy edit on the server silently changes how older apps behave.

- Failure scenario: Someone fixes S6-03 by making "not a member" terminal (delete queued rows). With today's signals, the uploader can only tell that apart from "device not registered" by message text, so the fix either matches more English strings or drops rows on any FORBIDDEN. A later server copy edit, or an S2-03 change that rewrites messages, then makes old apps either delete rows they should keep or keep retrying rows forever. The same applies to the S6-06 fix (terminal versus transient sharing changes).
- Suggested fix: Extend the existing `cause` mechanism into a shared `ErrorReason` string union in packages/shared, for example `NOT_GROUP_MEMBER`, `GROUP_GONE`, `DEVICE_NOT_REGISTERED`, `FRESH_SIGN_IN_REQUIRED`, `RECOVERY_CHANGED`, `ALREADY_MEMBER`, `STALE_WRITE`, `SOLE_OWNER` and `HISTORY_RECIPIENT_MISMATCH`. Set it through a typed `cause` class, the way `DeviceRemovedError` works, and send it in `data.reason`. The change is additive, so no level bump is needed. Give the app one `errorReason(error)` helper, delete the six local classifiers, and stop comparing message text. Add "error reasons are API surface; never repurpose one" to docs/development/api-compatibility.md and to the S10-05 snapshot.

### [X-03] Server and library error text reaches users verbatim; failure copy and offline detection are re-invented per screen

- Location: 50 lines in apps/mobile that show an `error.message` in `Alert.alert` or inline text; 26 of the files are in app/ and components/ (for example app/join.tsx:45, app/(tabs)/groups/[groupId]/SettingsTab.tsx:49,99, MembersTab.tsx:146,227,330, app/account/devices.tsx:52, app/setup/name.tsx:66, app/account/delete.tsx:47, app/account/recovery-_.tsx, components/dialogs/_); apps/mobile/lib/serverUnreachable.ts (one shared string, used by 2 modules)
- Category: UX
- Severity: medium
- Launch: post-beta
- Confidence: high
- Evidence:
  - `zodmsg.ts` reproduces what tRPC 11 + zod 4 send for an input check failure. `message` is the JSON-serialised issue array: `"[\n  {\n    \"expected\": \"date\",\n    \"code\": \"invalid_type\",\n    \"path\": [\n      \"requestedAt\"\n    ], ...`. Any screen that shows `error.message` shows that JSON when an older app meets a stricter server (S10-01, S10-06) or a client schema drifts from the server (S5-07).
  - S2-03 shows internal Prisma, S3 and Resend messages reaching the client. rateLimitMiddleware.ts:34 lets raw Bun Redis errors (S4-01) through the same way.
  - There are 24 hand-written variants of "Can't reach the server / Check your connection" across 19 files, next to one exported `SERVER_UNREACHABLE_MESSAGE` used only by `timeoutLink` and `auth-client`.
  - "Offline" is detected four different ways: `expo-network` (OfflineBanner), `TRPCClientError` without `data` (5 screens), `RequestTimeoutError`, and a synthetic 503 `SERVER_UNREACHABLE` from auth-client.
  - Many server messages are user copy in their own right, for example "This phone couldn't prove it's yours. Try again." (deviceRouter.ts:228). So the S8-15 fix ("tablets are called phone") has to change server strings too, and old apps keep showing the old ones.
  - There is no shared error-state component. S9-03, S8-04, S8-14, S7-02 and S7-03 are separate instances of a screen that shows a failed load as empty, as a spinner or with the wrong copy.
- Failure scenario: A 1.12 app talks to a self-hosted 0.11 server, or a future server tightens an input. The user taps "Save name" and gets an alert whose body is a block of JSON with `"code": "invalid_type"`. During a Redis blip they instead get "Connection closed". With the server down, the Groups tab says "No groups yet" (S9-03) while the Account tab says "Couldn't reach the server". Each screen behaves differently for the same fault.
- Suggested fix: Add `lib/userMessage.ts` that maps an error to copy. Use X-02's reason when present. Map no `data`, a timeout or a 5xx to one offline string, map BAD_REQUEST with `zodError` to "This app and server don't agree. Update the app or try again later.", and fall back to the server message only for 4xx with a known reason. Replace the 50 `error.message` uses. Add `ErrorState` (message + Retry) and `EmptyState` components, and require `isError && !data` handling before the empty state. This also fixes S9-03 and S8-14. Moving user copy out of server messages is optional but keeps one source of copy.

### [X-04] Client timeouts are shorter than the server's worst case, and create-style mutations aren't idempotent, so a retry after a timeout can duplicate work

- Location: apps/mobile/lib/timeoutLink.ts:18-24 (30 s mutation timeout); apps/mobile/components/dialogs/CreateGroupDialog.tsx:45-71 with apps/mobile/lib/groupEncryption.ts:77 (new `groupId` on every attempt); packages/database/src/client.ts:14 (pool wait unbounded, S4-03); apps/backend/src/index.ts:66-68 (Bun `idleTimeout` 60 s); packages/api/src/router/accountRecoveryRouter.ts:196 (awaits Resend with no timeout, S5-01)
- Category: bug
- Severity: low
- Launch: post-beta
- Confidence: medium (the code paths are certain; reaching them needs a server that is already slow)
- Evidence: The app aborts mutations after 30 s, and the server keeps running the handler. Nothing passes the request's abort signal into Prisma, S3 or email calls. A server request can outlive that in several ways: a pool wait with `connectionTimeoutMillis: 0` (S4-03), a Redis command hang of about 30 s (S4-01), a Resend send with no timeout (S5-01), and storage calls with no timeout (S3-05). Only three mutations carry an idempotency key: `setLocationSharing` (`requestId`), `uploadBatch` (`clientPointId`) and device link (`linkId`). `groupLifecycle.create` takes a client-generated `groupId`, but `buildCreateGroupInput` makes a new one on every attempt. `groupInvites.send`, `accountRecovery.requestResetCode`, `groupInvites.createShared` and `feedback.submit` have no key.
- Failure scenario: The hosted pool is saturated (for example, S4-02's deletion retries hold connections). A user taps Create on "Family", waits 30 s, sees "Can't reach the server" and taps Create again. Both requests commit, and the user now has two "Family" groups, each with its own epoch. They have to work out which one to invite people to, and delete the other. `groupInvites.send` and `requestResetCode` send duplicate emails the same way.
- Suggested fix: Generate the `groupId` once per dialog open, not per submit. Have the server treat a repeat `create` with the same `groupId` by the same user as success, returning the existing group instead of P2002/500. Give `groupInvites.send` and `requestResetCode` a client request ID and dedupe on it in Redis for a few minutes. The server-side timeout fixes (see the timeout table and D5 in the Duplicate map) shrink the window, but don't close it.

### [X-05] API response shapes follow no convention: void, `{ message }`, whole Prisma rows, three time formats and two cursor styles

- Location: per `outputs.txt`. Whole rows: auth.registerDeviceKey (packages/api/src/router/authRouter.ts:28-52, the full `UserDevice` including `sharingRequestId`, `activatedBy`, `revokedAt`, `publicKeyAlgorithm`), groupSettings.rename, groupMembership.updateRole, groupMembership.get. `{ message }`: groupLifecycle.create and delete, groupInvites.accept, acceptShared, decline and send, groupMembership.remove. ISO strings: maps.getSignedPmtilesUrl and forceRefreshSignedPmtilesUrl (`expiresAt`, `refreshAt`). Relative ms: groupInvites.createShared (`expiresInMs` next to `expiresAt: Date`), accountRecovery.status (`freshForMs`).
- Category: design
- Severity: low
- Launch: post-beta
- Confidence: high
- Evidence:
  - The 83 procedure outputs were printed with the TS compiler API (`dump.cjs`). Mutations return `void` (10), `{ message: string }` with server English (7, and a grep of the app finds no reader of `data.message`), status objects (`{status}`, `{activated}`, `{linked}`, `{rotated}`), counts (`{added}`, `{signedOut}`), or whole database rows (4; S10-10 lists three, and `registerDeviceKey` is the fourth and the widest).
  - Timestamps are `Date` through superjson everywhere except the maps router, which sends ISO strings that the app compares with the device clock (S7-04). `createShared` sends a relative `expiresInMs` so it survives clock skew, but `deviceLink.status` sends an absolute `expiresAt`. The app has a server-clock offset (`serverNow()` in lib/locationSharing.ts:73-80), but only sharing UI uses it.
  - Pagination has two styles: `{cursor: {createdAt, id} | null, hasMore}` (`groupTracking.poll`) and `{nextCursor: number | null}` (`listEpochKeyWraps`, `listHistoryBackfill`).
- Failure scenario: A migration adds a column to `UserDevice`, and it ships to every client in `registerDeviceKey` without review, the same risk S10-10 describes for groups. Someone adds an expiry to a new procedure and copies whichever of the three styles they find first. If they copy the maps style, the client-clock bug in S7-04 repeats.
- Suggested fix: Write a short convention into docs/development/api-compatibility.md. Mutations return the data the app needs or `void`, never an English message or a raw row. Use explicit `select` on every return. Use `Date` for instants plus a server `now` when the client must compare, or relative ms for countdowns. Use one cursor shape. Narrow `registerDeviceKey` to `{ sessionLinked, id, userId }` (check the app's reads first). The S10-05 snapshot would then enforce the convention.

## Cross-section interactions

- **I1. S10-01 × S6-06 makes level-4 apps stop sharing permanently.** Read with `git show` at 4c33f1d6 (app 1.10.0) and ad26893b (app 1.11.0): neither sends `requestedAt`, and both skip every upload while a pending sharing change exists (`if (device && hasPendingSharingPause(device.userId)) return;`, tracking.ts:716 and :707). `changeLocationSharing` keeps the pending change and returns "queued" when the mutate fails (1.11 locationSharing.ts:245-271).
