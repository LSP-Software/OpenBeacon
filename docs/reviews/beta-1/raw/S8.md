## Findings

### [S8-01] Switching server sends the old server's session cookie and raw session token to the new server

- Location: apps/mobile/lib/auth-client.ts:9, apps/mobile/lib/auth-client.ts:47-51, apps/mobile/lib/api.ts:101-104, apps/mobile/lib/auth.ts:79-92, apps/mobile/app/serverUrl.tsx:43-52, apps/mobile/app/serverUrl.tsx:123-124, apps/mobile/components/ApiCompatibilityGate.tsx:150-154
- Category: security
- Severity: high
- Launch: must-fix
- Confidence: high
- Evidence: Read `@better-auth/expo` 1.7.14 `dist/client.js`. The cookie is stored under one fixed key, `${storagePrefix}_cookie` (`openbeacon_cookie`), and attached to every auth request to whatever `baseURL` is. `api.ts` also copies `authClient.getCookie()` into the `Cookie` header of every tRPC call. Nothing is keyed by server. `SESSION_TOKEN_TO_REVOKE_KEY` is also a single unscoped SecureStore key, and `revokePendingSessionToken` posts its raw value to `/revoke-session` on the current server at the next sign-in. The server URL screen says "Your current session will remain active", and `ApiCompatibilityGate` offers "Use a different server" while signed in. The registered device record is the only thing scoped to the server (`registeredDevice.ts:18`).
- Failure scenario: A user signed in to the hosted server opens "Use a different server" (from the compatibility gate, or after signing out with a failed sign-out that saved the token for revocation) and enters a self-hosted URL that someone else runs. After the restart, the app's first `get-session` and every tRPC call carry the hosted `better-auth.session_token` cookie to that server. Its operator can replay the cookie against `api.openbeacon.net` and act as the user on any procedure that doesn't need a fresh session: device and group listings, account metadata, renaming, leaving or deleting groups they own, and so on. If a revoke token is pending, the raw token for server A is posted to server B. The cached `openbeacon_session_data` also makes the app show server A's user until server B answers.
- Suggested fix: Treat a server change as a full sign-out. When `setServerUrl` changes the value, clear `openbeacon_cookie`, `openbeacon_session_data` and `SESSION_TOKEN_TO_REVOKE_KEY` (or sign out against the old server first). Better still, include a hash of `baseUrl` in `storagePrefix` and in the revoke key, so a credential can only reach the server that issued it. Change the copy that says the session remains active.

### [S8-02] A server URL with a trailing slash or path passes the check, then every API call 404s

- Location: apps/mobile/app/serverUrl.tsx:16-18, apps/mobile/app/serverUrl.tsx:44, apps/mobile/lib/server-url.ts:9-15, apps/mobile/lib/base-url.ts:5-6, apps/mobile/lib/api.ts:93, apps/mobile/lib/apiCompatibility.ts:114
- Category: bug
- Severity: medium
- Launch: must-fix
- Confidence: high
- Evidence: `checkServerCompatibility` strips trailing slashes before calling `/health`, so the check reports "ok". `setServerUrl(url)` then saves the raw string, and `api.ts` builds `${baseUrl}/api/trpc`. Ran a throwaway test against the real Hono app (`apps/backend/src/slash.reviewtmp.test.ts`, deleted): `/api/trpc/account.version` matched the route, but `//api/trpc/account.version` and `//health` returned 404 `Not Found`. That 404 carries no compatibility headers, so the app can't explain it. Ran the screen's zod schema (`zurl.reviewtmp.ts`, deleted): `"https://a.com/"`, `"https://a.com/path?x=1#f"`, `"ftp://a.com"` and `"javascript:alert(1)"` all pass `z.url()` (the last two are then caught by the protocol check), and `""` fails, even though the copy says "Leave blank to use the default hosted server".
- Failure scenario: A self-hoster pastes `https://beacon.example.com/` from the browser bar. The app says the server is fine and to restart. After the restart, sign-in or the loading screen fails with unhelpful errors, or loops (see S8-04). Nothing tells them that the slash is the problem.
- Suggested fix: Normalise in one place, in `server-url.ts`. Parse with `new URL`, require http(s), reject a query, fragment or credentials, strip trailing slashes, and store `origin + pathname` without the trailing slash. Run the compatibility check on the normalised value. Fix the "leave blank" copy, or allow blank to mean default. Add unit tests.

### [S8-03] Plain `http://` server URLs are accepted, but release builds will likely block them, and they would send passwords and session tokens in clear text

- Location: apps/mobile/app/serverUrl.tsx:30-41, apps/mobile/app.json:27-35
- Category: security
- Severity: medium
- Launch: post-beta
- Confidence: medium
- Evidence: `handleSave` accepts `http:` and `https:`. `app.json` sets no `usesCleartextTraffic` and no iOS ATS exceptions, and the repo has no `expo-build-properties`. The current Expo/React Native templates allow cleartext only in debug builds (the release manifest placeholder is `false`), and iOS ATS blocks plain HTTP to public hosts. I couldn't check the prebuilt manifest (no `android/` directory is committed), so the "blocked" part is medium confidence.
- Failure scenario: A self-hoster enters `http://192.168.1.10:3000`. In a release build, the health check fails with "Couldn't reach this server", they tap "Save anyway", and nothing ever connects. If a build did allow cleartext, the password at sign-in, email codes and the session cookie would cross the network unencrypted. E2E still protects locations, but not the account.
- Suggested fix: Require `https://`, except for `localhost` and `10.0.2.2` in development builds. Say why in the error message, and point to the README's reverse-proxy guidance.

### [S8-04] The launch screen retries forever with no message or way out when the device check fails

- Location: apps/mobile/app/index.tsx:79-93, apps/mobile/app/index.tsx:102-104
- Category: UX
- Severity: medium
- Launch: must-fix
- Confidence: medium
- Evidence: With a session present, `HomeScreen` renders only the pulsing `LoadingScreen` and calls `isThisDeviceActive()`. On any error, it schedules `route()` again after 5 s, forever. `isThisDeviceActive` returns early from the local flag for active devices, so this affects devices that aren't active yet: just signed in, Pending, or a session left over from a failed `completeAuthenticatedSessionSetup`. It needs `device.status` from the server. Nothing on the screen shows an error, and there's no sign-out, server or retry control. `_layout` has no other exit, because `index` renders before the guard matters.
- Failure scenario: A user signs in on a new phone and kills the app before setup. Later they open it while the server is down, misconfigured (S8-02), returning 500s, or with a stale session cookie that the server rejects in a way that doesn't clear the session (for example, a server switch). The app shows the beacon logo indefinitely. Force-quitting doesn't help, and the user can't reach "Use a different server" or sign out.
- Suggested fix: After the first failure, show the error under the logo with "Try again", "Sign out" and, if self-hosted, "Change server". Back off the retries.

### [S8-05] Any route can be opened by deep link, including the setup "Remove devices" screen, which ticks every other device and blocks Back

- Location: apps/mobile/app/+native-intent.tsx:4-7, apps/mobile/app/setup/remove-devices.tsx:28-33, apps/mobile/app/setup/remove-devices.tsx:39, apps/mobile/app/setup/remove-devices.tsx:48-64, apps/mobile/app/_layout.tsx:47-71
- Category: security
- Severity: medium
- Launch: post-beta
- Confidence: high
- Evidence: `redirectSystemPath` passes every path through unchanged. Expo Router therefore resolves `openbeacon://setup/remove-devices`, `openbeacon://account/remove-device?deviceId=…&name=…`, `openbeacon://account/recovery-reset` and so on. `setup/remove-devices` is in the Protected group, so it only needs an Active device. It defaults `ticked` to every other device, disables Android Back and the iOS swipe, and has no confirmation dialog. The only exits are "Remove ticked devices" and "Keep them all". `removeDevice` is a `freshSessionProcedure` (`packages/api/src/router/accountRouter.ts:461`), so the attack works only inside the fresh-session window, for example just after a sign-in or ConfirmIdentity. The same default-ticked, unconfirmed bulk removal is also the legitimate path after "Start fresh", even though its warning says "Your other phones keep working".
- Failure scenario: A crafted link sent in a chat opens "Remove devices you no longer have", with all of the user's other phones and tablets ticked and no way back. If the user taps the big red button within the fresh-session window, every other device is removed, and each one wipes its keys and queued locations the next time it connects.
- Suggested fix: Allow-list deep-link paths in `redirectSystemPath` (`join`, and auth callback paths) and map everything else to `/`. In `remove-devices`, start with nothing ticked or ask for confirmation, and only allow the screen when it's reached from a just-completed reset (for example, a one-shot in-memory flag).

### [S8-06] Deleting the account only signs out; it leaves the device key, history keys and queued points on the phone

- Location: apps/mobile/app/account/delete.tsx:314-331
- Category: security
- Severity: medium
- Launch: post-beta
- Confidence: high
- Evidence: After `requestDeletion` succeeds, the screen calls `authClient.signOut()` and navigates to `/`. It doesn't use `signOutOfThisPhone` or `wipeThisPhone`. `TrackingProvider` then revokes tracking access with `keepDeviceRegistration: false`, and `checkThisPhoneAfterSessionLoss` only forgets the registration record. The per-user device private key and history keys in SecureStore, the `encryption.device.active.*` flag, the native ciphertext queue, the saved device link, pending sharing changes and pending join codes all stay. The "remove this phone" path (`wipeThisPhone`) deletes all of them.
- Failure scenario: A user picks "Delete immediately". Their account and server data are gone, but the phone keeps their history private keys and any unsent encrypted points until the app is uninstalled. That contradicts what the user expects of deleting an account in a privacy-first app. The 7-day option can keep the keys, so that cancelling by signing in still works, but immediate deletion has no reason to.
- Suggested fix: For `immediate`, run `wipeAfterRemovingThisPhone()` (or `wipeThisPhone`) before signing out. For the 7-day path, at least clear the pending join codes and pending sharing changes, and say on screen that this phone keeps its keys until deletion completes.

### [S8-07] Join accepts an invite without saying which group or who will see your location

- Location: apps/mobile/app/join.tsx:29-52, apps/mobile/app/join.tsx:62-115
- Category: UX
- Severity: medium
- Launch: post-beta
- Confidence: medium
- Evidence: A deep link `openbeacon://join?code=…` pre-fills the code. One tap on "Join group" runs `sharedAcceptanceContext` and then `acceptShared`, and calls `requestTrackingSync()`, so sharing with the group starts straight away. The screen only shows "Join a group" and the code. The acceptance context already returns the member recipients, so a member count or "you'll share your location with N people" could be shown first. - Suggested fix: Fetch the acceptance context first. Show a confirmation that says location sharing will start and how many members the group has, and require a deliberate "Join and share my location" tap.

### [S8-08] ConfirmIdentity with a different Google account signs that account up

### [S8-09] Android Auto Backup is on by default and backs up native tracking preferences

- Location: apps/mobile/app.json:27-35
- Category: security
- Severity: low
- Launch: post-beta
- Confidence: medium
- Evidence: `@expo/config-plugins` `AllowBackup.js` defaults to `android:allowBackup="true"`. `expo-secure-store` adds backup rules that include every `sharedpref` file except `SecureStore`. MMKV (`files/mmkv`) and the Room queue are therefore excluded, but `openbeacon_tracking_queue` (owner, deviceId), `openbeacon_tracking_capture` (`enabled`), `openbeacon_tracking_sharing`, `openbeacon_notices` and the Keystore-encrypted epoch key blob are cloud-backed up and copied in device-to-device transfer. The epoch key blob can't be decrypted on a new phone, so no keys leak.
- Failure scenario: A user moves to a new phone with Google's transfer tool. The new install starts with `capture enabled = true` and the old phone's device ID and queue owner, before the app has been opened or signed in. How the boot receiver behaves then is S6's area, but the state is stale at best. Any future secret put in plain SharedPreferences would also be backed up silently.
- Suggested fix: Set `"android": { "allowBackup": false }`, since nothing in the app is useful to restore. Or ship explicit `dataExtractionRules` that exclude everything.

### [S8-11] Auth client timeout stops at response headers; a stalled body hangs sign-in

- Location: apps/mobile/lib/auth-client.ts:29-35
- Category: bug
- Severity: low
- Launch: post-beta
- Confidence: medium
- Evidence: `customFetchImpl` clears the timer and removes the abort listener as soon as `fetch` resolves, which is when the headers arrive. better-fetch reads the body afterwards, with no timer and with a signal that no longer aborts. The tRPC path doesn't have this problem, because `timeoutLink` stays active until the observable completes.

## Refactor candidates

- **Identity-gated step screens** (`remove-device`, `sign-out-others`, `recovery-setup`, `recovery-change`, `recovery-reset`): each repeats the `step` state, the `useEffect` that moves from `verify` to `ready` when `gate.decision === "ready"`, the `ConfirmIdentity` block, and a `reauthenticate` handler with its own Alert. ## Patterns for the cross-cutting pass

- **Error handling**: screens use `tryCatch` around `mutateAsync` or lib calls, then `Alert.alert(title, error.message)`. Many show the raw tRPC message. Some screens map `TRPCClientError` with no `data` to "Check your connection" (remove-device, sign-out-others, setup/link `problemMessage`, recovery-restore), and others don't (delete, join, add-device). Better-auth calls return `{ data, error }` and are checked by `error.code` (`EMAIL_NOT_VERIFIED`, `INVALID_SIGN_UP_TOKEN`, `INVALID_TOKEN`). Device-level errors (removed, pending, unverified) are handled globally in `deviceRemovedLink` by `cause`.
- **API shapes**: lib helpers return discriminated `status` objects (`{ status: "reauthenticate" | "conflict" | "unsaved" | … }`) for recovery flows and `{ data, error, deviceRemoved }` for session setup. `emailCodes` uses `authClient.$fetch` with hand-written generic types and no runtime validation of responses.
- **Validation**: forms use react-hook-form with `zodResolver` and the shared `@openbeacon/schemas` (sign-in, sign-up, change password, email code, device name). Ad hoc forms with no resolver: delete-account password, ConfirmIdentity password, recovery-reset "RESET" box (uses `isResetConfirmed`). The server URL uses `z.url()` plus a manual protocol check, and isn't normalised.
- **Loading/error UI**: most account screens show `LoadingIndicator` for `isPending` and a text + "Try again" block for `isError`. Gaps: delete (no loading), password (no loading), setup screens treat UNAUTHORIZED as offline, and the index screen has no error UI at all.
- **Timeouts/retries**: tRPC has `timeoutLink` (20 s queries, 30 s mutations, overridable through `context.timeoutMs`). React Query retries queries 3 times, except on timeout or 4xx codes. Mutations aren't retried. Some flows force `networkMode: "always"` (removeDevice, signOutOtherSessions). The better-auth client has a 30 s timeout on headers only (S8-11). The `/health` check has 10 s. The index route retries every 5 s forever (S8-04). Polling: device link status every 2 s, recovery status on the waiting screen every 5 s. Sign-out waits up to 10 s for a final sharing sync and up to 10 s for the tracking flush.
- **Logging**: `loggerLink` logs `[TRPC] down <path>` for errors in production and all directions in development. Paths only, no inputs. No other logging in scope.
- **Storage**: MMKV (`openbeacon` instance) holds the server URL, compatibility state, registered device record (scoped by `baseUrl`), active-device flags, pending join codes (24 h TTL), theme, dismissed prompts (`recovery.promptDismissed.<userId>`, `newSignInBanner.dismissed.<deviceId>`, `recovery.restoreCardDismissed.<userId>`), none of them cleaned on sign-out except join codes. SecureStore holds the better-auth cookie and session cache (unscoped, S8-01), the revoke token (unscoped), and device and history keys (S1). The query cache is cleared by `SessionDataCleanup` when the user ID changes or the session ends. `wipeThisPhone` is the only complete local wipe, and delete-account doesn't use it (S8-06).
- **Screen security**: `preventScreenCaptureAsync` and app-switcher protection are used on NewRecoveryPhrase (setup, change, reset), recovery-restore and the setup/link QR (which contains the PSK). Recovery inputs use `secureTextEntry`, no autofill and a hidden context menu. The group invite QR (`SharedInvite`, S9) and the add-device camera screen aren't protected. That's probably fine, since an invite code is shareable by design.
- **Possible iOS caveat (unverified)**: the expo-secure-store cookie uses the default keychain accessibility (`WHEN_UNLOCKED`), so JS requests made while an iOS device is locked can't read the cookie. Worth checking if iOS background uploads ever run in JS.
