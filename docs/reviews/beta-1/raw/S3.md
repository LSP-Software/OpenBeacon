## Findings

### [S3-01] A member who leaves creates, and keeps, the group key used after they leave

- Location: packages/api/src/router/group/groupMembershipRouter.ts:212-308 (self-removal passes the leaver's `nextEpoch` to `persistGroupEpoch`); apps/mobile/lib/groupEncryption.ts:135-159 (`buildRemoveGroupMemberInput` builds the epoch on the leaving phone); packages/api/src/lib/groupEpochs.ts:350-557
- Category: security
- Severity: high
- Launch: must-fix
- Confidence: high
- Evidence: Read the code. When `actor.id === input.memberId`, the leaver's phone generates epoch N+1, wraps it to everyone else, and the server stores it. Proved with a temporary integration test (`leaverKey.reviewtmp.test.ts`, run against a throwaway integration database, then deleted). The member leaves and keeps `leaveEpoch.epochKey`. The owner uploads a point under epoch N+1. The member rejoins with a shared code, calls `groupTracking.poll({ cursor: null })`, and decrypts the owner's post-departure point: `LEAKED {"latitude":1.23,"longitude":4.56}`.
- Failure scenario: Mallory leaves a family group using a modified client and keeps the key she generated for the next epoch. That epoch protects every location the group shares until the next join, leave or device change. Anyone who gets that ciphertext can decrypt it with her key: a later re-admission (see S3-02), a database leak, or the hosted operator. Rotating on leave is supposed to stop exactly this (encryption CONTEXT: "A new Epoch starts when … someone joins or leaves").
- Suggested fix: on self-removal, don't accept an epoch from the leaver. Delete the member and set `epochRotationRequired = true`, and let a remaining member rotate through the existing `rotationContext`/`rotate` path; the upload `keyState` hash already prompts that. This can stay server-only and backward compatible: the server ignores the `nextEpoch` that older apps send on self-leave. Add an integration test that the leaving device can't create the post-departure epoch. Admin removal is fine as it is, because the admin stays in the group.

### [S3-02] Tracking reads ignore when the reader joined, and uploads under superseded epochs are accepted indefinitely

- Location: packages/api/src/lib/groupTracking.ts:233-283 (`pollGroupTrackingPoints` filters only by `groupId` and cursor), :285-324 (`getLatestGroupTrackingPoints`), :136-145 and :164-174 (upload accepts any group epoch created since the sender joined); groupRotation.integration.test.ts "permits old uploads before and after rotation"
- Category: security
- Severity: medium
- Launch: must-fix
- Confidence: high
- Evidence: Read the code; the same temp test proves both halves. After the member left, the owner uploaded a point under the pre-departure epoch: `{"accepted":[…-stale-epoch]}`. After rejoining, `poll({ cursor: null })` returned every stored point in the group, including points from before the rejoin. Wrap endpoints are limited by `joinedEpochNumber`, but the ciphertext endpoints aren't.
- Failure scenario: (a) X is removed at epoch N and keeps key N on their phone. Other members' phones keep uploading queued and lagging points under epoch N, and the server accepts them. If X is re-invited later, a modified client polls from a null cursor and decrypts everything stored under N, including the period X was out of the group. With S3-01, X can read all of epoch N+1 too. (b) Any new member can page through 60 days of the group's stored rows from before they joined: sender user and device, receipt time and point count. Honest apps never ask for this (they start from `getLatest`), so it costs nothing to forbid.
- Suggested fix: in `poll` and `getLatest`, join `GroupEpoch` and return only points whose `epochNumber >= ctx.groupMember.joinedEpochNumber`. Clamp a null or older cursor to the member's join time. Consider rejecting uploads under an epoch older than the latest departure epoch for points the server receives after that departure, or at least add a test that documents the trade-off.

### [S3-03] Any signed-in user can write about 100 MB of ciphertext a minute, with no quota

- Location: packages/api/src/router/group/groupTrackingRouter.ts:21-28 (240 requests/min); packages/schemas/src/schemas/group/tracking.ts:23-36 (100 points per batch, `ciphertext` up to 4096 chars); packages/api/src/router/group/groupLifecycleRouter.ts:85-91 (anyone can create a group of one)
- Category: security
- Severity: high
- Launch: must-fix
- Confidence: high
- Evidence: Read the limits. The rate limit is per user per procedure path (`rateLimitMiddleware.ts`). 240 × 100 × ~4.1 KB ≈ 100 MB/min, or ≈ 140 GB/day per account, kept for 60 days. The only per-point check is a `clientPointId` that the attacker chooses, starting with their own revision prefix. A real phone uploads every 60–120 s with a handful of ~200-byte points.
- Failure scenario: a user, or a script running several free accounts, creates a solo group and loops `uploadBatch`. Postgres disk on the hosted server fills within hours, and every group's uploads and sign-ins fail. Backups grow the same way.
- Suggested fix: cut the limits to near real usage. For example, cap the points in a batch, cap points per device per minute in Redis (cost = `points.length`, as `groupInvites.send.recipients` already does), and lower the `ciphertext` maximum to the largest payload the Kotlin encoder can produce plus a margin. Add a per-group or per-account row budget that the cleanup job can report on.

### [S3-04] Presigned image uploads don't bind Content-Type, so the public CDN will serve any file type

- Location: packages/api/src/lib/storage.ts:197-217 (`getPresignedUploadUrl`); packages/api/src/lib/image-upload.ts:136-158 (`confirmImageUpload` checks only the size)
- Category: security
- Severity: medium
- Launch: post-beta
- Confidence: high
- Evidence: Ran `scratchpad/presign.ts` with the same SDK options. The URL is signed with `X-Amz-SignedHeaders=content-length;host;x-amz-checksum-sha256`, and `content-type` is neither signed nor hoisted. So the uploader picks the stored `Content-Type`. The checksum only pins the bytes to a hash the client chose. Confirmation never reads `ContentType` from the HEAD response or checks the bytes are WebP.
- Failure scenario: a user requests a profile or group image upload, then PUTs an HTML page with `Content-Type: text/html`. The object is publicly reachable at `S3_CDN_URL/<bucket>/user/<id>/uploads/avatar/<uuid>.webp`, before or after confirmation, until cleanup. That is free phishing or script hosting on the operator's CDN domain. If confirmed, members' apps get an image that won't decode.
- Suggested fix: add `content-type` to `signableHeaders`, so the PUT must send `image/webp`. On confirm, check `HeadObject.ContentType === "image/webp"` and the WebP magic bytes with a ranged GET; delete the object if either fails. At the CDN, set `X-Content-Type-Options: nosniff` and `Content-Disposition: inline` for that path.

### [S3-05] Group deletion calls storage with no timeout while it holds the group lock; storage calls never time out anywhere

- Location: packages/api/src/router/group/groupLifecycleRouter.ts:23-82; packages/api/src/s3client.ts:4-11; packages/api/src/lib/storage.ts:219-287 (no `abortSignal`)
- Category: bug
- Severity: medium
- Launch: must-fix
- Confidence: high
- Evidence: Read the code. `delete` takes `Group … FOR UPDATE`, then runs one `ListObjectVersions` plus `DeleteObjects` per pending upload and for the current image, all inside a 15 s interactive transaction. `s3Client` sets no request or connection timeout. Map-tile R2 reads pass `AbortSignal.timeout(10_000)`, but image storage calls don't. Each upload to that group is its own interactive transaction (Prisma default timeout 5 s) and waits on `Group FOR SHARE`. The pg pool is the adapter default.
- Failure scenario: storage is slow. An owner deletes a group. For up to 15 s every upload, mutation and join in that group queues on the row lock, holding pool connections, and fails with a Prisma transaction timeout ("Transaction already closed"), so the app sees a 500. If the image `DeleteObjects` succeeds but the transaction then times out, the group survives while its image has been deleted, leaving a broken `group.image`. Outside transactions, `confirmGroupImageUpload` and `confirmProfileImageUpload` can hang forever on a black-holed HEAD.
- Suggested fix: give `s3Client` a request handler with connection and request timeouts, or pass `abortSignal: AbortSignal.timeout(…)` on every `send` in storage.ts. For group delete, commit the DB deletion first and record the image keys for the cleanup job (as `accountDeletionCleanup` does for accounts), or at least do the storage calls before taking the lock and keep the lock only for the DB work.

### [S3-06] Changing `S3_CDN_URL` makes every group with an image impossible to delete

- Location: packages/api/src/lib/storage.ts:345-371 (`extractImageStorageObject` returns null unless the URL starts with the current `S3_CDN_URL`); packages/api/src/router/group/groupLifecycleRouter.ts:61-76; packages/api/src/lib/account-deletion.ts:56-58
- Category: bug
- Severity: medium
- Launch: post-beta
- Confidence: high
- Evidence: Read the code. `group.image` stores a full URL built from the `S3_CDN_URL` in effect at upload time. Group delete throws `INTERNAL_SERVER_ERROR "The group image cannot be removed from storage."` when the stored URL doesn't parse against the current base. Account deletion throws `Cannot identify group image for cleanup.` for solo groups. Replacing an image silently skips deleting the old object.
- Failure scenario: a self-hoster moves their CDN to a new domain, or the hosted service changes CDN. Every owner who tries to delete a group that has an image gets a 500 with no way forward. Scheduled account deletions for users with imaged solo groups fail on every run. Old images are orphaned on replacement.
- Suggested fix: store the object key (or bucket and key) in the database and build the public URL when reading. Until then, document that `S3_CDN_URL` must never change, and fall back to matching the key suffix `user/<id>/uploads/group/<groupId>/avatar/<file>`.

### [S3-07] Shared invite codes stay valid after their creator is demoted or removed

- Location: packages/api/src/router/group/groupMembershipRouter.ts:387-395 (demotion deletes only `groupMemberInvite`); packages/api/src/router/group/assertGroupMemberCanBeRemoved.ts:46-51 (removal deletes only email invites); packages/api/src/router/group/groupInvitesRouter.ts:115-168 (`acceptShared` doesn't check the creator's current role)
- Category: security
- Severity: low
- Launch: post-beta
- Confidence: high
- Evidence: Read the code. `GroupSharedInvite.creatorId` is never checked after creation. Email invites are revoked on demotion and departure, and the integration test "demoting an inviter drops the invites their new role could not send" asserts that, but shared codes are not.
- Failure scenario: an owner removes a misbehaving admin, who has just generated a code. For up to 5 minutes, anyone with that code can still join the group as a member.
- Suggested fix: in `acceptShared`, require the creator to still be an OWNER or ADMIN of the group. Alternatively, delete the creator's unused shared invites in `updateRole` and in the removal CTE.

### [S3-08] An upload can claim any of the account's active devices as its sender

- Location: packages/api/src/lib/groupTracking.ts:120-162; packages/api/src/router/group/groupTrackingRouter.ts:47-53
- Category: security
- Severity: low
- Launch: post-beta
- Confidence: high
- Evidence: Read the code. `senderDeviceId` only has to be an active, unrevoked device of the session's user. It is never compared with `ctx.deviceId`. History backfill (`listHistoryBackfill`, `addHistoryWraps`) and epoch creation do require the calling phone's own device ID.
- Failure scenario: a session on the account's phone uploads points attributed to the account's tablet. Viewers then see the tablet somewhere it isn't, and it overrides the tablet's real `lastLocationAt`. This only works within one account, so the impact is small, but it weakens the per-device pause guarantees and audit trail.
- Suggested fix: require `point.senderDeviceId === ctx.deviceId`, or document why queued points from another device ID must be accepted. If that is needed for re-registration, accept only the session's device or a revoked predecessor that the server can map.

### [S3-09] Group list items are built by hand in three places, and `get` returns the raw Prisma row

- Location: packages/api/src/router/group/groupMembershipRouter.ts:41-56 and 57-61; packages/api/src/router/group/groupInvitesRouter.ts:234-311; packages/api/src/router/group/groupLifecycleRouter.ts:108-166
- Category: duplication
- Severity: low
- Launch: post-beta
- Confidence: high
- Evidence: Read the code. The same `select` and `members.map(...) satisfies GroupListItem` appear three times. `groupMembership.get` spreads the whole `Group` row (including `epochRotationRequired` and `updatedAt`) plus the caller's raw `GroupMember` row into the API response. The `!createdMember.group` check in `accept` can't fail, because of the FK.
- Failure scenario: a new field is added to one copy and not the others, or a sensitive column added to `Group` or `GroupMember` later leaks through `get` with no review.
- Suggested fix: add one `groupListItemSelect` and `toGroupListItem` helper in `types/GroupListItem.ts`. Give `get` an explicit `select`. Remove the dead check.

## Patterns for the cross-cutting pass

- Authorisation: `protectedProcedure` requires an Active device (Pending and unverified devices are refused). `groupMemberProcedure` checks membership outside any transaction, and every mutation repeats the check under `Group FOR UPDATE`. Reads (`poll`, `getLatest`, wraps) rely on the middleware check only. IDOR checks on `memberId`, `inviteId`, `epochId` and `deviceId` are consistently scoped by `groupId` or `recipientId`/`userId`; I found no cross-group or cross-account access. `pendingDeletion` is checked only in invites and group create.
- Lock order (no inversions found): `User` (FOR NO KEY UPDATE for pause, device, account and join; FOR SHARE for upload) → `Group` (FOR UPDATE for every group mutation; multi-group sorted by id in `lockUserGroups`; FOR SHARE for upload) → `GroupMember` (FOR SHARE own row on upload; FOR UPDATE actor, target and owners in remove) → `AccountHistoryKey` FOR SHARE (epoch persist, `addHistoryWraps`) → advisory xact lock on hash(userId) (pending image upload). Paths checked: upload vs pause, rotate, accept, remove member, remove device, device activation, recovery reset, account deletion and group delete. The only long lock hold is group delete (S3-05).
- Transactions: Prisma interactive transactions with the default 5 s timeout, except group delete (15 s). A timeout reaches the client as an unmapped Prisma error, i.e. INTERNAL_SERVER_ERROR. A P2002 on client-chosen IDs (`groupLifecycle.create` with a used `groupId`) is also unmapped and returns a 500.
- Errors: `TRPCError` with plain-English messages. `tryCatch` is used for storage and key-state calls. Conflict-style optimistic updates (`expectedCiphertext`) return CONFLICT "… Reload and try again." Uploads report per-point outcomes (`accepted` / `discarded` / `duplicates` / `expired`) instead of throwing, except for an epoch from another group or a previous membership, which throws BAD_REQUEST and makes the app bisect the batch.
- Validation: zod schemas from `@openbeacon/schemas`; procedure inputs merge with the middleware's `groupId` max(128). Some inner schemas omit `.max` (`groupTrackingPollSchema.cursor.id`, `removeGroupMemberSchema` IDs, `members` input).
- Timeouts: R2 manifest reads 10 s; key state on upload is raced against 2 s, and the losing query keeps running; S3 image calls have none (S3-05).
- Rate limits: per user per path. `groupInvites.redeem` still has an `ipLimit` (the project memory says IP limits are meant to be removed).
- Logging: `maps.*` logs userId, object key and expiry on every call (disclosed). Image cleanup failures log a fixed message without the error. No plaintext or keys are logged in this section.
- Storage: images go in a public bucket under `user/<uploaderId>/uploads/...`, the URL is stored in full, deletion removes every version, orphans are swept by scheduled jobs (S4), and Content-Type is unchecked (S3-04).
