### S6-01: Cold app launch stops sharing and wipes native keys before permissions load; offline, sharing stays off

- Verdict: CONFIRMED WITH CORRECTIONS
- Severity: high (reviewer said high)
- Launch: must-fix
- Evidence:
  - `apps/mobile/providers/LocationPermissionProvider.tsx:42` starts `permissionState` as `null`. The launch effect (:112-120) only sets it after `requestNotificationPermissions()` (`PermissionsAndroid.check` plus `areNotificationsEnabled`, `lib/notifications.ts:53-64`) and then `requestForegroundLocationPermissions()` (`getForegroundPermissionsAsync`, then `getBackgroundPermissionsAsync`, `lib/locationPermissions.ts:181-194`). That is at least four sequential native round trips. The first launch after install also shows a system prompt.
  - `apps/mobile/providers/TrackingProvider.tsx:53` maps `null` to `startCapture = false`. Both providers are gated on the same session and device-active state. The first cycle (:178-186) waits only for a dynamic import and the synchronous `resumeTracking()`, then runs `reconcileTrackingKeys({ startCapture: false, force: true })`. In practice the tracking cycle always reads `false` first. The existing TrackingProvider tests mock `permissionState` as non-null (`TrackingProvider.test.tsx:120-126`), so this path has no coverage.
  - `lib/tracking.ts:493-498`: `stopImmediately` calls native `stopCapture()` without any condition. `reconcileTrackingKeysInternal` (:221-226) then calls `revokeEpochKeys()`, before any network call. Natively, `stopCapture` stops `TrackingCaptureService` and sets capture-enabled to false. With no group list, `revokeEpochKeys` also sets capture disabled and clears the epoch key store (`OpenBeaconTrackingModule.kt:52-57`, :102-111). After that, nothing restarts capture on its own: `syncBackgroundTracking` uses `onlyIfRunning: true`.
  - The key check is stored in MMKV (`lib/trackingKeyCheck.ts`) with scope `[baseUrl, userId, startCapture]`. The `!startCapture` path revokes keys but never clears or marks the stored check stale. If the last `startCapture: true` check is still fresh (4 min, or 30 min while uploads keep `keyState` fresh), the next `reconcile({ startCapture: true, force: false })` takes the fresh branch (:273-290). It sees `hasKeys: false` and leaves capture stopped.
  - Reproduced independently with a temporary copy of `lib/tracking.test.ts`. I made the native mock faithful: `revokeEpochKeys()` clears keys, `startCapture` sets running. `groupMembership.list` throws while offline. The file was deleted afterwards. Results:
    - Offline. Online provision gives running with 2 keys. Then `reconcile(false, force)` rejects with "Network request failed", leaving capture not running and 0 keys. Then `reconcile(true)` resolves "ok", still not running, 0 keys, and `startCapture` is not called.
    - Back online with the app still open, the 60 s interval cycle `reconcile(true, force: false)` still leaves capture not running with 0 keys, because the key check is still fresh. Only a forced cycle (app returns to the foreground, or a `requestTrackingSync`) restored running with 2 keys.
    - Online cold start: `reconcile(false, force)` gives not running with 0 keys, then `reconcile(true)` gives running with 2 keys. That costs 1 extra stop, 1 extra start and 1 extra provision.
  - No network-reconnect trigger exists. `requestTrackingSync` is only called from UI actions (`app/join.tsx`, group screens, setup, recovery, sign-out).
- Corrections:
  - Online, the extra network cost is smaller than the reviewer implies. The first launch cycle uses `forceKeyCheck: true` anyway, so key wraps would be fetched once regardless. The waste is the extra `!startCapture` pass, its membership/rotation/backfill calls, and the service stop/start. That stop/start flickers the persistent notification and drops fixes for a second or two.
  - "Deletes stored group keys" means the native provisioned epoch-key copies. They are re-provisioned from server wraps, so no key material is permanently lost. The loss is capture coverage.
  - The recovery window is wider than the reviewer says. Coming back online while the app stays open does not help until the key check expires (4 to 30 min). Bringing the app back to the foreground online fixes it at once, because that cycle is forced.
  - The same `null` state also occurs whenever `readyToAsk` is false (`/setup` routes, `/account/recovery-*?setup`). Entering those screens stops capture and revokes keys the same way.
- Fix assessment: The direction is right, but the fix as written is incomplete.
  1. Gate only the reconcile step on a known permission state, not the whole cycle, so flushes still run. If `syncLocationPermissions` errors, it returns `null` and never sets state. A plain "skip while null" would then disable reconciles for the whole session, so fall back to a direct `getLocationPermissionState()` read.
  2. Independently, whenever native keys are revoked, also call `markTrackingKeysStale()` (or `clearTrackingKeyCheck()`). Alternatively, in the fresh branch, fall through to the network path when `startCapture && !hasKeys`. Without this, any interrupted revoke leaves the fresh-check trap in place.
  3. Keep stop and revoke for a known `isReadyForSharing === false`.

  Add a TrackingProvider test that starts at `permissionState: null`, and a tracking test for revoke-then-fresh-check. Client-only change: no API level, encrypted format or migration impact. Needs an app version bump.

### S6-02: iOS build asks for Always location and says "Sharing enabled", but iOS never captures or uploads

- Verdict: CONFIRMED WITH CORRECTIONS
- Severity: low (reviewer said high)
- Launch: post-beta (must be fixed before any iOS release)
- Evidence:
  - The code facts hold:
    - `app.json` has `platforms: ["ios","android"]`, `ios.bundleIdentifier`, `buildNumber`, and `isIosBackgroundLocationEnabled: true`.
    - `modules/openbeacon-tracking/expo-module.config.json` is `platforms: ["android"]`, and `lib/trackingModule.ts` returns `null` off Android.
    - `LocationSharingCard.tsx:153-163` shows "Sharing enabled on …".
    - The background-permission dialog (`LocationPermissionProvider.tsx:202-224`) asks for precise and background location without any platform check.
  - iOS is not part of Beta 1:
    - `docs/security/beta-1-privacy-draft.md:7` says "Beta 1 includes Android and both hosted and self-hosted backends."
    - `docs/development/account-deletion.md:15` says "iOS Keychain entries survive uninstall, so revisit this before shipping iOS."
    - `docs/development/location-sharing.md:58` says native tracking exists only on Android.
    - There is no `eas.json` and no mobile build or release workflow; `.github/workflows` only has backend deploy, image publish and pre-merge checks.
    - The only iOS entry points are the dev scripts `bun run ios` / `expo run:ios` in the README.
- Corrections: The failure scenario needs an iOS build in family members' hands, and Beta 1 doesn't ship one. App Store rejection is also moot for the beta. This is a latent gap: the iOS app config and UI claim a capability that doesn't exist.
- Fix assessment: The suggestion is reasonable for when iOS is picked up. A cheap interim option is to leave `isIosBackgroundLocationEnabled` off and add a `Platform.OS !== "android"` branch to the sharing card and the background-permission dialog. Another is to drop `"ios"` from `platforms` until a capture implementation exists. Either way, track it as a pre-iOS-launch issue. No compatibility impact.

### S10-04: A "too old" result taken from a missing procedure flips on and off, because only same-level mismatches stick

- Verdict: CONFIRMED WITH CORRECTIONS
- Severity: medium (reviewer said medium)
- Launch: post-beta (cheap fix, worth taking before the first beta build if there is time, because installed apps keep this logic)
- Evidence:
  - `lib/apiCompatibility.ts:32-42`: `decideUnknownProcedure` returns `serverTooOld`/`appTooOld` whenever the levels differ.
  - `applyVerdict` (:184-189) clears any non-`outOfSync` state on an `"ok"` verdict.
  - `ApiCompatibilityGate.tsx:41-47` refreshes `/health` on every foreground while a problem is set.
  - The backend middleware (`apps/backend/src/helpers/apiCompatibility.ts:10-21`, mounted on `/api/*` in `app.ts:11`) puts both level headers on every API response.
  - Reproduced with a temporary copy of the `apiCompatibility.test.ts` harness (deleted). It used the real shipped levels (4/4/4) against a server at level 5 / minClient 4 that dropped a procedure without raising `minClient`, which is a rule-14b miss. Alternating the 404 `UNKNOWN_PROCEDURE`, an ordinary 200 from another procedure, the 404 again, and `/health` gave `["appTooOld",null,"appTooOld",null,"appTooOld",null,"appTooOld",null]`. The same-level control (`outOfSync`) stayed set across an ordinary 200.
- Corrections:
  - It's worse than the reviewer says. The verdict is cleared not only by `/health` but by any successful `/api` response. `apiCompatibilityFetch` reads the level headers, `readApiCompatibilityResponse` (:97-107) returns `"ok"`, and `applyVerdict` clears the state. While the gate is up, background react-query refetches, the 60 s tracking cycle and background uploads all keep the gate flapping, not just foreground events.
  - Each clear also resets `notified`, so `showApiCompatibilityNotice` (`lib/tracking.ts:803-812`) can post the compatibility notice again on each new trip.
  - The mirror (`appTooOld`) case is reachable by the shipped beta app (level 4) against any future server that drops a procedure without raising `minClient`. The `serverTooOld` case needs a future app with a missed rule-14a bump.
  - Both cases need a team mistake in level bumps. The impact is a flickering gate, start/stop uploads and repeated notices, not data loss. That is why I rate it post-beta.
- Fix assessment: The suggested fix (record that the verdict came from a 404/426 and keep it until Try again or a server `version` change) is right, but it must cover both clearing paths: `/health` refreshes, and the header-derived `"ok"` in `apiCompatibilityFetch`. Simplest approach: apply the existing `outOfSync` stickiness rule to every problem set from a 404 or 426 body. Also extend the "fetch `/health` to record `serverVersion` when it's null" step (:235-237), which today only runs for `outOfSync`, so a server upgrade can still clear the gate. Keep level-header-derived problems clearable, since those genuinely resolve when the levels change. Add one test per level ordering. Client-only change, no API level or format impact; needs an app version bump.
