## Findings

### [S4-01] Redis client never reconnects after a short outage under traffic, so every API call fails until the backend restarts

- Location: packages/cache/src/cache/OpenBeaconCache.ts:59-61; apps/backend/src/cache.ts:4-7; packages/auth/src/index.ts:28-33; packages/email/src/index.ts:43-45; packages/api/src/middlewares/rateLimitMiddleware.ts:34-40; packages/api/src/procedures/auth/base.ts:17,31; apps/backend/src/routes/health.ts:8-16
- Category: bug
- Severity: high
- Launch: must-fix
- Confidence: high
- Evidence: Tested Bun 1.4.4 `RedisClient` with default options, which is how every `OpenBeaconCache` in production is built (no `redisOptions`), against a throwaway real `redis:7` container (`scratchpad/redis/t5.ts`, `t6.ts`, `t7.ts`, `t8.ts`) and a controllable TCP proxy (`t1.ts`–`t4.ts`). Results:
  - A 0.4 s `docker restart` with no commands in flight recovered. Idle outages of 4 s and 12 s also recovered.
  - A 3 s outage with one command a second (`t8.ts`): one command hung about 30 s, then the client stayed `ERR_REDIS_CONNECTION_CLOSED` on every later command, 3 s and 30 s after Redis was back. A new `RedisClient` to the same URL got `PONG` straight away (`t5.ts`).
  - Through the proxy, a 5 s outage with 5 pings and a 40 s idle outage both left the client permanently closed.

  Every tRPC procedure runs `rateLimitMiddleware`, which awaits `ctx.cache.rateLimits.consume`. When that throws, the request fails with a 500. Nothing in `OpenBeaconCache` recreates the client. `/health` doesn't touch Redis, so Coolify/Docker sees a healthy backend.

- Failure scenario: Redis restarts for an upgrade, a Coolify redeploy or an OOM kill while phones are uploading every 60 s. A few requests hang for about 30 s. After that every API call (uploads, polls, sign-in rate limits, email sends through the email package's separate client) returns INTERNAL_SERVER_ERROR until someone restarts the backend by hand. The scheduled runner's email client fails the same way, so account-deleted emails stop silently.
- Suggested fix: Wrap the client in `OpenBeaconCache`. On `ERR_REDIS_CONNECTION_CLOSED`, close it and create a new `RedisClient` (or call `connect()`) with backoff. Put a short timeout on each command (Bun has no per-command timeout, so race it against a timer) and set `enableOfflineQueue: false`, so a Redis stall fails fast instead of hanging requests for about 30 s. Decide fail-open vs fail-closed per caller: the general per-procedure limit can fail open with a log line, while the email-code guess limit should keep failing closed. Share one cache instance per process instead of three (backend, auth, email). Add a readiness check or a "Redis reachable" field to health. Add an integration test that restarts Redis.

### [S4-02] Deleting a heavy user's account overruns Prisma's 5 s transaction timeout, so it never completes, and each retry locks the user's groups

- Location: packages/api/src/lib/account-deletion.ts:19-98 (called from apps/scheduled-jobs/src/jobs/accountDeletion.ts:21-36, apps/scheduled-jobs/src/deleteAccount.ts:17, packages/api/src/router/accountRouter.ts:358-366); the same pattern for one group at packages/api/src/router/group/groupMembershipRouter.ts:310
- Category: bug
- Severity: high
- Launch: must-fix
- Confidence: high on the failure mode, medium on the exact threshold
- Evidence: `scripts/seed-deletion.sql` seeds one pending-deletion user with points in two groups whose other member is the owner, at 30 s spacing (the default capture interval in `CaptureSamplingPolicy.kt`). `scripts/run-deletion.ts` calls `deleteAccountRecords({ mode: "scheduled" })` on a throwaway integration database:
  - 345,600 payload rows (60 days, 2 groups at 30 s): succeeded in 5,482 ms, just over the 5 s default.
  - 691,200 rows: `P2028 Transaction API error: A query cannot be executed on an expired transaction. The timeout for this transaction was 5000 ms, however 25780 ms passed` (cold), and 7,458 ms warm. Everything rolled back and all 691,200 rows remained.

  While the warm run was in progress, an `INSERT` into `GroupEncryptedPayload` for one of the user's groups from another member waited about 2 s, until the rollback. `lockUserGroups` takes `FOR UPDATE` on the groups, and the payload FK check needs `FOR KEY SHARE`. The transaction passes no `timeout`. Prisma checks the timeout only at the next query, so the full bulk delete runs before the abort.

- Failure scenario: A user in three or more groups, or one who moves a lot, asks to delete their account. Each scheduled attempt deletes hundreds of thousands of rows for 5–25 s while blocking other members' uploads to those groups. It then rolls back, sets `deletionRetryAt` +5 min, and logs only `Scheduled account deletion failed` with no code. This repeats every 5 minutes forever. The account and its location history are never erased, which breaks the erasure promise. The operator CLI and the API's `immediate` path hit the same wall. Leaving a group with a large history has the same pattern for one group.
- Suggested fix: Move the bulk payload delete out of the locking transaction. In the first short transaction, re-check the deadline under the user lock and mark the account as being deleted, so a sign-in can't cancel it. Then delete `GroupEncryptedPayload` rows by `senderUserId` in batches of a few thousand without group locks; sessions are already revoked, so no new uploads arrive. Finish with a short transaction for the group handling and the `User` delete. Give that transaction an explicit `timeout`. Log `errorCode(error)` on failure. Add an integration test that seeds about 500k rows.

### [S4-03] Prisma/pg pool has no connection-wait limit, no statement timeout and an unconfigurable pool size

- Location: packages/database/src/client.ts:14-15
- Category: design
- Severity: medium
- Launch: post-beta
- Confidence: high that these settings are missing; medium on impact
- Evidence: `new PrismaPg({ connectionString })` creates a `pg.Pool` from that config alone (`@prisma/adapter-pg` dist line 776), so node-postgres defaults apply: `max: 10`, `connectionTimeoutMillis: 0` (wait forever for a connection), and no `statement_timeout`, `lock_timeout` or `idle_in_transaction_session_timeout`. No caller sets them either (grep for `statement_timeout`, `connection_limit` and `PrismaPg` finds only this file). Interactive transactions use Prisma's 5 s default, but that is only checked between queries (see S4-02), and some transactions do network I/O while holding locks (S3 deletes inside `groupLifecycleRouter.ts:54-76`, the Redis `peek` inside the email-code transaction in `packages/auth/src/emailCode.ts:166`).
- Failure scenario: A slow query, a lock wait (for example behind S4-02's group locks) or a stalled S3 call inside a transaction holds connections. With only 10 per process, later requests queue for a pool slot with no limit. The API hangs instead of returning errors, and `/health` stays green.
- Suggested fix: Pass `max`, `connectionTimeoutMillis` and `idleTimeoutMillis` to `PrismaPg`, read from env with sane defaults. Set `options: "-c statement_timeout=… -c lock_timeout=… -c idle_in_transaction_session_timeout=…"`, with a longer statement timeout for the runner. Document pool sizing for self-hosters.

### [S4-04] Runner jobs have no timeouts on S3, Resend or Redis calls, and `/health` is static, so a hung call stops a job forever unnoticed

- Location: apps/scheduled-jobs/src/scheduler.ts:26-44; apps/scheduled-jobs/src/jobs/accountDeletion.ts:49-50,63; apps/scheduled-jobs/src/jobs/imageUploadCleanup.ts:59,104,132; apps/scheduled-jobs/src/health.ts:5-13; packages/api/src/s3client.ts:4-11; packages/api/src/r2.ts:8-15; packages/email/src/transport.ts:31-36
- Category: bug
- Severity: medium
- Launch: post-beta
- Confidence: medium (the AWS SDK and Resend defaults are from knowledge of those libraries, not tested here)
- Evidence: The scheduler only re-arms a job after its `run` promise settles. The S3 clients are built without a `requestHandler` timeout, and the Resend SDK's `emails.send` uses `fetch` with no signal. SMTP has timeouts. `runAccountDeletion` ends with `await waitForSecurityAlerts()`, which awaits every background email, and email sending first awaits a Redis `consume` that S4-01 showed can hang about 30 s. The health body is computed once at startup and always returns `ok`.
- Failure scenario: An S3 `ListObjectVersions`/`DeleteObjects` call or a Resend request never returns, for example after a half-open TCP connection. `account-deletion` never runs again in that process, so due accounts stay undeleted, while Docker's HEALTHCHECK keeps reporting the runner healthy.
- Suggested fix: Give the S3 and R2 clients a `NodeHttpHandler` with `connectionTimeout` and `requestTimeout`, and give Resend sends an `AbortSignal.timeout`. Have the scheduler record each job's last start and finish, and make `/health` return 503 when a job has run far longer than its delay or hasn't succeeded within N intervals. Optionally run each job under a hard timeout.

### [S4-05] Account deletion failures are logged without a code, and permanent failures retry every 5 minutes forever

- Location: apps/scheduled-jobs/src/jobs/accountDeletion.ts:30-36,53-58; apps/scheduled-jobs/src/deleteAccount.ts:15
- Category: design
- Severity: low
- Launch: post-beta
- Confidence: high
- Evidence:
  - Unlike every other job, the account deletion loop drops the error and logs only `Scheduled account deletion failed` / `Account image cleanup failed`, without `errorCode()`.
  - `deleteAccountRecords` throws CONFLICT when the user is the sole owner of a group with other members. Scheduling excludes pending-deletion co-owners, but the deletion-time check counts any other owner, and the operator CLI uses `mode: "immediate"`. So if owner B is removed with the CLI while co-owner A is pending, A's scheduled deletion throws CONFLICT on every run.
  - Nothing distinguishes that case, or S4-02's P2028, from a transient error.
  - The CLI looks up `findUnique({ where: { email } })` with the raw argument. better-auth stores emails lowercased, so `Foo@example.com` reports `Account not found.`
- Failure scenario: An operator sees `Scheduled account deletion failed` every 5 minutes with no hint of the cause. The account is never deleted and nobody is told.
- Suggested fix: Log `errorCode(result.error)` or the TRPC code. After N failures, or for CONFLICT, log a distinct line, or email the owner if the conflict needs their action. Lowercase and trim the CLI email.

### [S4-06] Pending device cleanup runs one unbounded transaction, so a backlog stops the device-link and challenge cleanup too

- Location: apps/scheduled-jobs/src/jobs/pendingDeviceCleanup.ts:7-25
- Category: bug
- Severity: low
- Launch: post-beta
- Confidence: medium
- Evidence: The `SELECT … FOR UPDATE SKIP LOCKED` has no `LIMIT`. The session and device deletes run in one `$transaction` with the default 5 s timeout and an unbounded `IN (...)` list. If the transaction throws, the function rejects before the `deviceLink` and `deviceChallenge` deletes, contrary to the README's "deletes device links and challenges separately, so a skipped device doesn't hold them up".
- Failure scenario: Many abandoned sign-ins (abuse, or a buggy client creating Pending devices) build a backlog large enough to pass 5 s. Every hourly run then times out and rolls back, and expired device links (which hold wrapped `ciphertext`) and challenges are never cleaned.
- Suggested fix: Add `LIMIT 1000` and loop like the other jobs, and run the link and challenge deletes independently, for example in their own `tryCatch` steps.

### [S4-07] Schema constraints that Prisma doesn't see, or that are missing

- Location: packages/database/prisma/schema.prisma:173,191 with migration.sql:621-622 (CHECK constraints); schema.prisma:140-150 (PendingUpload.groupId); schema.prisma:86-101 (Account)
- Category: design
- Severity: low
- Launch: post-beta (cheaper to fix now, while there's a single init migration)
- Confidence: high
- Evidence:
  - `GroupJoinAlert.memberId` and `GroupSharedInvite.creatorId` are optional in Prisma (`String?`, `onDelete: Cascade`) but forced non-null by hand-written CHECK constraints. Generated types say `string | null` for values that can never be null, and `prisma migrate diff` and `db push` can't see the rule.
  - `PendingUpload.groupId` uses `""` as a sentinel for user avatars, with no FK to `Group`. Deleting a group leaves its pending uploads unless each caller deletes them by hand, which `account-deletion.ts:69` and `groupLifecycleRouter.ts:78` do.
  - `Account` has no unique `(providerId, accountId)`. better-auth's `findAccountByKey`/`findAccountOwnerByKey` (`internal-adapter.mjs:557-570,686-698`) query by those columns, which means a sequential scan per lookup. They throw `Multiple accounts match the same accountId` if duplicates exist, and nothing in the database prevents duplicates.
- Failure scenario: Code written against the generated types handles impossible nulls, or a future migration drops the CHECK without anyone noticing. A concurrent link race inserts a duplicate Google account row, and that user can no longer sign in.
- Suggested fix: Make `memberId` and `creatorId` required and drop the CHECKs. Model user and group avatar uploads so `groupId` can be a real FK, for example a separate table or a nullable `groupId` with a surrogate id and a partial unique index. Add `@@unique([providerId, accountId])` to `Account`.

### [S4-08] Missing FK index on PersonalGroupNickname.targetId

- Location: packages/database/prisma/schema.prisma:225-232
- Category: design
- Severity: low
- Launch: post-beta
- Confidence: high
- Evidence: The primary key `(ownerId, targetId)` covers `ownerId` only. `targetId` has `ON DELETE CASCADE` from `GroupMember` but no index. Every `GroupMember` delete (leave, remove, account deletion, group delete) has to scan `PersonalGroupNickname` to find rows where it is the target. All other FK columns I checked are covered by an index or by the leading column of a unique constraint.
- Failure scenario: Once nicknames are widely used, member removal and account deletion get slower in proportion to the table size. This isn't urgent at beta scale.
- Suggested fix: Add `@@index([targetId])`.

### [S4-09] Removed devices that were ever active are kept forever with their name, model and platform

- Location: packages/database/prisma/schema.prisma:241-275; apps/scheduled-jobs/src/jobs/pendingDeviceCleanup.ts:8-16; packages/api/src/lib/removeDevice.ts:59
- Category: design
- Severity: low
- Launch: post-beta
- Confidence: high
- Evidence: Removing a device only sets `revokedAt`. `pendingDeviceCleanup` deletes only devices with `activatedAt IS NULL`. `GroupEncryptedPayload.senderDevice` is `Restrict`, so a device row has to outlive its points, but after 60 days no points remain and nothing deletes the row. Owner notes say a stale-device job is an open decision.
- Failure scenario: The server keeps the device name, model and platform of every phone a user has ever removed until the account is deleted. That is personal operational data with no remaining purpose, and the table grows without bound.
- Suggested fix: Add the planned device clean-up. Delete revoked devices with no remaining `GroupEncryptedPayload` rows a set time after `revokedAt`, and set the history-wrap and epoch sender references to null as the FKs already allow.

### [S4-10] Encrypted payloads stored as base64 text, with repeated label strings, on the largest table

- Location: packages/database/prisma/schema.prisma:358-380 (GroupEncryptedPayload), plus the key and wrap columns in GroupEpochRecipientKey and GroupEpochHistoryWrap
- Category: design
- Severity: low
- Launch: post-beta
- Confidence: medium (size impact estimated, not measured)
- Evidence: `nonce` and `ciphertext` are base64 `TEXT`, which costs about 33% more than `bytea`. `kind` (`trackingPoint`) and `algorithm` are repeated free-text strings on every row, and every point is stored once per group. The table carries 7 indexes and the autovacuum tuning.
- Failure scenario: Storage and I/O on the hot table are about a third higher than needed, which affects the hosted bill, vacuum time and the cleanup throughput the README measures.
- Suggested fix: Consider `Bytes` (bytea) for nonce and ciphertext while keeping base64 on the wire, and enums for `kind` and `algorithm`. Converting a populated table later means a full rewrite.

## Refactor candidates

- **`OpenBeaconCache` connection handling** (about 100 lines): today three independent instances each hold their own raw `RedisClient`. One shared, self-healing wrapper with command timeouts would fix S4-01 and remove `toRedisOptions`. The `FakeRedis` in `testUtils.ts` (about 200 lines) reimplements the Lua token bucket in TypeScript. Its logic already differs slightly (it always sets `lastMs = now` and treats expiry differently). Since `OpenBeaconCache.integration.test.ts` already runs the real scripts, the fake could be replaced by a thin stub of `send` results, or the unit tests could run only against the integration cache.
- **`deleteAccountRecords` split into phases** (about 100 lines): this would fix S4-02. Phase 1: lock, check due, mark deleting. Phase 2: batched payload delete. Phase 3: short final transaction. The same batched helper could serve group leave (`groupMembershipRouter.ts:310`) and the location-history job.
- **`expiredRecordsCleanup.ts`** (about 120 lines): six nearly identical `DELETE … WHERE id IN (SELECT … LIMIT 1000)` blocks. A small `deleteExpired(table, column, cutoff, extraWhere?)` helper built on `Prisma.sql` would halve the file. Adding `FOR UPDATE SKIP LOCKED` there would also stop two overlapping runners deadlocking on the same batch, which is possible today during a deploy overlap but harmless.
- **Job observability**: each job builds its own failure log line (`failureCode` is duplicated in imageUploadCleanup.ts:31-32 and scheduler.ts:30-34). Moving outcome reporting (code, count, duration) into the scheduler would also give `/health` something to report (S4-04).

## Patterns for the cross-cutting pass

- **Error handling**: jobs use `tryCatch` per step and log one line with the job or table name plus `errorCode()`: the Postgres SQLSTATE from `meta.driverAdapterError.cause.originalCode`, otherwise `error.code` or `error.name`. They never log the error object, IDs or URLs. The exception is account deletion, which logs no code at all (S4-05). The scheduler swallows the error and re-arms after `delay`. The cache package throws raw Bun Redis errors (`ERR_REDIS_CONNECTION_*`) and zod parse errors to callers.
- **Fail open vs closed**: rate limiting fails closed everywhere. The tRPC middleware lets the Redis error become a 500. The email-code guess check returns `invalid` when Redis errors. The email sender throws, and its caller logs `[security-alert] could not send …`. `alertsTurnedOff.add` falls back to sending immediately.
- **Timeouts/retries**: there are no timeouts on Redis commands (Bun default `connectionTimeout` 10 s, offline queue on, no per-command limit), on S3 or R2, on Resend, on pg pool acquisition or on statements. Prisma interactive transactions use the 5 s default except `{ timeout: 60_000 }` in pending upload cleanup and `15_000` for group delete. Job retry is "next interval". Account deletion uses `deletionRetryAt` / `retryAt` set to database time + 5 min.
- **Clocks**: jobs and deletion decisions use the Postgres clock (`clock_timestamp()`), converting with `::timestamptz AT TIME ZONE 'UTC'` because columns are `timestamp(3)` without time zone holding UTC. Rate limits use the app server's `Date.now()` rather than Redis `TIME`, so multiple backends with clock skew would refill unevenly. `removeDevice` sets `revokedAt` from the app clock.
- **Locking**: user-row `FOR NO KEY UPDATE` comes first, then group rows `FOR UPDATE` in id order (`lockUserGroups`). Jobs use `FOR UPDATE SKIP LOCKED` so they never wait on API traffic, except account deletion, which deliberately takes the same locks as the API.
- **Batching**: location history 1,000 per statement, 500k per run. Epochs 5,000 per page. Expired records 1,000 × 10 per table. Pending uploads 500 per run. Account deletion 100 accounts and 100 cleanups per run. Pending devices are unbounded (S4-06). Each account's deletion is unbounded in one transaction (S4-02).
- **Storage**: ciphertext, keys and wraps are base64 `TEXT`. Names, group names, emails, device names and models, session IP and user agent are plaintext by design (accepted in `docs/security/beta-1-privacy-draft.md`). Redis keys hold raw user IDs for user-scoped limits, alert holds and signed map URLs, and HMAC-SHA256(`REDIS_HASH_SECRET`) of `type:value` for IP and email.
- **Validation**: the cache validates every input with zod `.strict()` schemas, including calling `now()` at construction. The runner validates env at import through the shared `validateEnv` and prints only setting names.
- **Health**: both the backend and the runner `/health` return static `ok` with version and server name, with no dependency checks.
- **Tests**: good unit and integration coverage of job selection logic, clocks, SKIP LOCKED behaviour and log redaction. Untested: Redis outage and reconnect, account deletion at realistic data volume and its lock impact, and hung external calls in the runner.
