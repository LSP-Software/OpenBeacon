### S10-01: `setLocationSharing` started requiring `requestedAt` without a level bump

- Verdict: CONFIRMED WITH CORRECTIONS
- Severity: low (reviewer said high)
- Launch: post-beta. Recording it in the doc is enough. Raising the level to 5 is optional.
- Evidence:
  - The code is as described. `packages/schemas/src/schemas/account/locationSharing.ts:13` has `requestedAt: z.date()`. `git diff 4c33f1d6 36a34c1a` shows the field was added in #222. Levels stayed at 4/4/4 from 0170937d through HEAD.
  - At ad26893b (1.11.0), `changeLocationSharing` builds its input with no `requestedAt`. The `requestedAt` on line 182 of that version is a local clock-offset variable, not part of the input.
  - `v5_s1001.ts` ran the current `setLocationSharingSchema` on a 1.11.0-shaped payload. Result: `success: false`, `["requestedAt"] expected date, received undefined`. Adding `requestedAt` makes it pass. A level-4 app passes the 426 gate, the procedure exists, and zod returns BAD_REQUEST, so the app shows a validation error and never the update screen.
  - `readPendingChange` (`apps/mobile/lib/locationSharing.ts:59-66`) parses with `locationSharingChangeInputSchema` and calls `storage.remove` on failure. A queued change from 1.10 or 1.11 is therefore dropped silently after the upgrade.
- Distribution history:
  - Level 4 and app 1.10.0 merged in #218 at 06:49 UTC on 12 Nov. 1.11.0 merged in #221 at 13:37. #222, the breaking change, merged at 16:34 the same day, so the window was about 10 hours.
  - The repo has no git tags and no GitHub releases (`gh release list` and `git ls-remote --tags` are both empty). No workflow builds or publishes the app; the three workflows cover checks, image publishing and the backend deploy. `store-assets/` holds Play Store graphics only. No docs mention testers, tracks or released APKs.
  - Project memory says the only 1.11.0 release APK is on the local `pixel_8c` emulator, pointed at a dev backend on `10.0.2.2:3911`. It also says the hosted database was wiped before 0.12.0 deployed with #224 ("almost no data").
  - So as far as the repo and notes show, no one outside development ever ran a level-4 app without `requestedAt`. The failure can't reach a real user unless an untracked sideloaded build exists.
- Corrections:
  - "Apps 1.10.0/1.11.0 at level 4 fail" is true of the code but has no real-world impact, because those builds never shipped.
  - The process gap is real. A narrowed input passed review with "API compatibility: unchanged". Level 4 now covers two incompatible input shapes, which will confuse any later "newest app that still called X at level N" analysis that `docs/development/api-compatibility.md` relies on. That belongs under S10-05.
- Fix assessment:
  - The reviewer's two options both work.
  - Making `requestedAt` optional with a server-side `now` fallback would quietly bring back the bug that #222 fixed for any client that omits it. It's the wrong choice now that no such clients exist.
  - Raising to 5/5/5 before the first public build is clean and cheap: no migration and no encrypted-format change, but rule 14d needs minor bumps on both app and server. It isn't needed, though, since no level-4 builds without `requestedAt` exist outside dev.
  - Minimum action: add a note to the level history in `api-compatibility.md` saying level-4 builds before 1.12.0 (dev only) can't call `setLocationSharing`.
  - The real fix is S10-05's API-surface snapshot, so the next narrowing gets caught.

### S10-02: The tracking-point reader rejects unknown fields; battery can't be "unknown"

- Verdict: CONFIRMED WITH CORRECTIONS
- Severity: medium (reviewer said medium)
- Launch: must-fix. A reader that tolerates new fields only helps if every beta install ships with it, and it can't be added to old installs later.
- Evidence:
  - `packages/encryption/src/trackingPoint.ts:54-90` requires `Object.keys(value).length !== 6`, `value.v !== 1` and exactly two battery keys.
  - `v5_s1002.ts` against the real function:
    - Base point: accepted.
    - Extra top-level key `accuracy`: "Invalid tracking point."
    - Extra battery key: "Invalid tracking point."
    - `battery.level: null`: "Invalid tracking point."
    - `v: 2`: "Invalid tracking point."
  - The only production reader is `apps/mobile/lib/mapTrackingDecrypt.ts:115`. Its catch maps any throw to `undecryptable`.
  - The outer `kind`/`algorithm` check (line 82) returns `ignored` for an unknown kind.
  - The server's upload schema pins `kind: z.literal("trackingPoint")` (`packages/schemas/src/schemas/group/tracking.ts:28`). Moving to a new `kind` therefore needs a server change too, and old apps would just ignore those points. Dual-sending both kinds would double uploads, which conflicts with the battery work in #222 and #205. So there's no cheap escape route, which supports the reviewer's point.
  - The strictness is deliberate. `trackingPoint.test.ts:104` is titled "rejects fields outside the locked plaintext schema". The fix reverses a conscious decision, and that test has to change with it.
- Corrections:
  - The "battery unknown" sub-point matters much less than it sounds. `BatteryReader.kt` sends `level = 0` only when the sticky `ACTION_BATTERY_CHANGED` intent is null or has no level/scale. On real Android phones that almost never happens. It's a format-design gap worth fixing now, not a bug users will see.
  - A tolerant reader alone does not make `battery.level: null` a safe later change. Changing an existing field's type breaks every old reader, tolerant or not. If a nullable level (or `accuracy`) is wanted, it has to go in before beta.
- Fix assessment:
  - The reviewer's fix is right: ignore unknown keys at the top level and inside `battery`, keep validating the known ones, and keep `v === 1` as the hard-break switch.
  - Two details:
    - Return a new object built only from the known fields, not `value as TrackingPointV1`, so unknown keys never reach the UI or React state.
    - Keep `encodeTrackingPointV1` strict, since senders should emit only what they mean to.
  - Update the "locked plaintext schema" test to assert that extra keys are dropped.
  - Compatibility: today's senders all emit exactly six keys, so no API level change and no change to the encrypted bytes. Add a test vector with an extra key so the Kotlin side stays aligned.
  - Recording each device's level server-side for future real breaks is a sensible post-beta follow-up.

### S10-03: "Update Open Beacon" screen has a permanently disabled Update button; the server can't send a message or link

- Verdict: CONFIRMED
- Severity: medium (reviewer said medium)
- Launch: must-fix. The fix is a few lines, and every beta build keeps this screen for as long as it's installed.
- Evidence:
  - `apps/mobile/components/ApiCompatibilityGate.tsx:127-131` renders `<Button disabled className="opacity-50"><Text>Update</Text></Button>` for `appTooOld`, with no handler. `git log -S` shows it has been this way since 1b561e7b.
  - The copy says "Update the app to start sharing again". Nothing in `apps/mobile` opens a store URL; the grep for `market://`, `play.google` and `openURL` finds nothing.
  - The 426 body (`apps/backend/src/helpers/apiCompatibility.ts:16`) is `{ code, minClientApiCompatibilityLevel }`. `/health` (`apps/backend/src/routes/health.ts`) returns the five frozen fields, and the app parses both with plain `z.object` (`apps/mobile/lib/apiCompatibility.ts:46-57`). Optional extra fields are therefore safe to add, but nothing would display them.
  - The "We're updating Open Beacon's servers" copy for `serverTooOld` on hosted is fixed text.
  - The package ID is `net.openbeacon.app` (`apps/mobile/app.json:24,33`).
- Corrections:
  - The impact is smaller than "no way to update" for Play Store installs. Play auto-update and the store's own update prompt still work, and the screen tells users to update.
  - The real trap is the greyed-out primary button, which looks broken. Sideloaded and internal-test users really do have no pointer.
- Fix assessment:
  - Opening `market://details?id=net.openbeacon.app`, with an `https://play.google.com/store/apps/details?id=…` fallback, is right for store builds.
  - Adding optional `updateUrl` and `message` fields to the 426 body and `/health` is additive. The frozen-surface tests in `apps/backend/src/app.test.ts` and the "Frozen surfaces" section of `api-compatibility.md` would need updating.
  - If the server supplies `updateUrl`, accept only `https:` or `market:` schemes. Otherwise a self-hosted (or compromised) server could send the user anywhere from a trusted-looking screen.
  - No level change is needed.

### S8-02: Trailing slash in server URL passes the check, then every API call 404s; blank URL fails validation

- Verdict: CONFIRMED WITH CORRECTIONS
- Severity: medium (reviewer said medium)
- Launch: must-fix. Combined with S8-04, it can leave a self-hoster with no way out inside the app.
- Evidence:
  - `checkServerCompatibility` strips trailing slashes before `/health` (`apps/mobile/lib/apiCompatibility.ts:114`). The startup refresh (line 219) uses the same function on `baseUrl`, so both report "ok".
  - `setServerUrl` (`apps/mobile/lib/server-url.ts`) stores the raw string, and `api.ts:93` builds `${baseUrl}/api/trpc`.
  - `v5_s802.ts` imported the real `apps/backend/src/app.ts` and sent each path with a level-4 header:

    | Path                         | Result                                                                                         |
    | ---------------------------- | ---------------------------------------------------------------------------------------------- |
    | `/health`                    | 200                                                                                            |
    | `//health`                   | 404 "404 Not Found", no level headers                                                          |
    | `/api/trpc/account.version`  | matched the route (500 only because the scratch harness had no cache binding), headers present |
    | `//api/trpc/account.version` | 404, no level headers                                                                          |
    | `/api/auth/get-session`      | 200                                                                                            |
    | `//api/auth/get-session`     | 404, no level headers                                                                          |

  - The 404 is plain text with no headers, so `apiCompatibilityFetch` can't turn it into an out-of-sync screen.
  - `v5tmp.verifytmp.ts` (deleted) ran the screen's zod schema: `""` fails, while `"https://a.com/"`, `"https://a.com/beacon"` and `"ftp://a.com"` pass (`ftp` is then caught by the manual protocol check).
- Corrections:
  - "Every API call 404s" applies to tRPC only. better-auth's client (`node_modules/better-auth/dist/utils/url.mjs`, `withPath`) trims trailing slashes, so with `https://a.com/`, sign-in succeeds. Then `completeAuthenticatedSessionSetup` (tRPC) fails with "Unable to finish sign in" while the session is already stored (S8-12). After that, the index screen hits S8-04's endless retry, because `ensureDeviceKeyRegistration` and `device.status` are tRPC calls that 404. The end result is worse than the reviewer said: from the next launch on, the user can't reach the server URL screen to fix it, and only clearing app data recovers.
  - The reviewer missed a second, related bug. With a path prefix such as `https://a.com/beacon`, better-auth treats the path as the full auth base and calls `/beacon/sign-in/email`, while tRPC calls `/beacon/api/trpc`. Path-prefixed URLs are handled inconsistently, so either reject a path or append `/api/auth` explicitly.
  - The "blank uses default" copy is wrong, but blank isn't the only way back: a "Use Default Server" button (`serverUrl.tsx:135-139`) appears whenever a custom URL is set. That part is a copy fix (low).
  - Behind nginx with `merge_slashes` and a URI in `proxy_pass`, `//api` may be normalised. Behind Traefik (Coolify), Caddy or a direct connection it isn't. Don't rely on the proxy.
- Fix assessment:
  - Normalising in `server-url.ts` and checking the normalised value is right.
  - Either reject a non-root path or pass `basePath`/an explicit `${base}/api/auth` to `createAuthClient`, so better-auth and tRPC agree.
  - Normalise on read too (`getServerUrl`), because a slash-terminated value may already be saved on existing installs.
  - No API level or format impact. Add unit tests for the normaliser.

### S8-04: Launch screen retries every 5 s forever with no message or way out

- Verdict: CONFIRMED WITH CORRECTIONS
- Severity: medium (reviewer said medium)
- Launch: must-fix
- Evidence:
  - `apps/mobile/app/index.tsx:71-97` is as described. When `session` is truthy, `HomeScreen` renders only `LoadingScreen` (no buttons). `route()` re-arms `setTimeout(route, 5_000)` on every `isThisDeviceActive()` error, with no limit and no backoff.
  - `isThisDeviceActive` (`apps/mobile/lib/deviceActivation.ts:34-42`) returns early only when the local active flag is set. Otherwise it needs `ensureDeviceKeyRegistration` (tRPC when nothing is cached) and `device.status`.
  - `_layout.tsx` adds only `ApiCompatibilityGate`, which shows only for a compatibility verdict and not for unreachable, and `OfflineBanner`, which shows only when the OS reports no network.
  - The sign-in, server-URL and sign-out controls all sit on the signed-out branch of `index.tsx` or on other routes. None of them can be reached from the loading state.
- Corrections:
  - "Retries forever" only means stuck for good when the failure persists. When a server outage ends, the next retry succeeds and the app moves on. When the phone has no network, the red "No internet connection" banner does give a message.
  - The cases that really trap users:
    - A misconfigured self-hosted URL (S8-02, reproduced above as tRPC-only 404s).
    - A self-hosted server that is down long-term or returns 500s.
    - A hosted outage, during which a Pending or just-signed-in phone shows a pulsing logo with no explanation.
  - The reviewer's "stale session cookie the server rejects" case mostly isn't real. If `get-session` returns no session, `useSession` goes null and the signed-out screen shows. I didn't check whether a 5xx from `get-session` keeps the cached session.
  - Active phones, the common case, are unaffected because of the local flag.
- Fix assessment:
  - After the first failure, show the error, "Try again" and "Sign out", plus "Change server" if self-hosted. Back off retries (say 5 s, 15 s, 60 s, capped).
  - "Sign out" here should use the existing `signOutOfThisPhone` path so the Pending device is cleaned up properly.
  - Pairing this with the S8-02 normaliser closes the self-host trap.
  - No API level impact.
