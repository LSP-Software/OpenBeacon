# Verifier V3

Commit 94a73b27, Bun 1.4.4. Scratch scripts are in `scratchpad/v3/`. The throwaway Redis container (`v3-redis-outage`, `redis:7` on 127.0.0.1:16481) has been removed. The rows seeded in a throwaway integration database (ids `v3-*`) have been deleted, and counts were checked back to 0.

### S4-01: Redis client never reconnects after an outage, so every API call fails until the backend restarts

- Verdict: CONFIRMED WITH CORRECTIONS
- Severity: high (reviewer said high)
- Launch: must-fix
- Evidence:
  - Code: every `OpenBeaconCache` is `new RedisClient(url, undefined)` (packages/cache/src/cache/OpenBeaconCache.ts:59-61). Production builds three of them with no `redisOptions`: apps/backend/src/cache.ts:4, packages/auth/src/index.ts:28 and packages/email/src/index.ts:43. Nothing calls `connect()`, sets `onclose` or recreates the client. `rateLimitMiddleware` awaits `ctx.cache.rateLimits.consume` with no catch (packages/api/src/middlewares/rateLimitMiddleware.ts:34), so a Redis error becomes a tRPC INTERNAL_SERVER_ERROR. `/health` (apps/backend/src/routes/health.ts) returns static data, and both Dockerfile HEALTHCHECKs only call `/health`, so Docker and Coolify never restart the container.
  - Bun defaults (node_modules/bun-types/redis.d.ts): `autoReconnect: true`, `maxRetries: 10`, `enableOfflineQueue: true`, `connectionTimeout: 10000`.
  - My own repro (`v3/redis-outage.ts`) used a real `OpenBeaconCache.rateLimits.consume` against a throwaway container, with `docker kill` or `docker stop`, then `docker start`, and traffic every 250–1000 ms:
    - Outages of 3 s, 5 s, 12.5 s and 25 s under traffic all **recovered**. Commands issued during the outage sat in the offline queue and finished once Redis returned, so they were delayed by up to the length of the outage (about 25 s at most). Afterwards every command worked.
    - A 40 s outage under traffic left the client **permanently closed**. All 171 commands failed with `ERR_REDIS_CONNECTION_CLOSED`, the first ones after about 30 s, and they still failed 45 s and 75 s after Redis came back. A fresh client connected at once.
    - Idle client (`v3/idle.ts`): a 15 s outage recovered, and a 45 s outage left the client permanently closed.
    - `docker pause` for 5 s and 20 s (TCP open but no replies) recovered. Commands hung for the length of the pause.
    - `v3/reconnect.ts`: after a 33 s outage the client was closed, `onclose` had fired once, and calling `client.connect()` brought it back (`PONG`).
  - I also ran the reviewer's `t8.ts` against my own container with "3000" as the argument. It printed `redis back after 32733 ms`: its loop awaits each PING in series, one PING hung for about 30 s, and so Redis was really down for about 33 s, not 3 s. The "3 s outage" result in the finding is an artefact of the test script.
  - Hosted Redis: the repo uses Dragonfly v1.31.2 in docker-compose.yml and CI. The README says these compose services are only for local development, and nothing in the repo says what the hosted deployment runs. Reconnection is decided in the client, so the server flavour doesn't change the threshold.
- Corrections:
  - The trigger is an outage longer than Bun's retry budget, which is about 25–33 s on this machine. It is not a "short outage under traffic". Outages under about 25 s recover on their own, with traffic or without. That is still very reachable: a Coolify redeploy of Redis or Dragonfly (image pull plus start), a host reboot, a network partition, or a crash loop of more than 30 s all exceed it.
  - During any outage shorter than that, requests hang for its full length (offline queue, no per-command timeout). Each one also holds a Bun request open and goes on to Postgres afterwards. This side effect is real but recovers.
  - The impact list is right: every tRPC call fails (rate-limit middleware), along with email code limits through the auth package's client, `sendEmail`'s per-user cap through the email package's client, and the scheduled-jobs email client. Each of the three clients fails separately, so after an outage near the threshold some may recover while others don't.
- Fix assessment: The direction is right. Correction: a closed `RedisClient` can be revived with `connect()`, so the wrapper doesn't need a new client; an `onclose` handler or a catch on `ERR_REDIS_CONNECTION_CLOSED` that calls `connect()` with backoff is enough. A simpler belt-and-braces option is `maxRetries` set very high. Bun's backoff is capped, so the client would then keep retrying for as long as the outage lasts, but this needs a test to confirm the cap. Adding a timeout on each command plus `enableOfflineQueue: false` is right for the hang. Failing open for the general per-procedure limit is reasonable, but the email-code guess limits (`peek`/`consume` in packages/auth/src/emailCode.ts) must fail closed. Add a Redis ping to `/health`, or a separate readiness endpoint, so Docker restarts the container as a last resort. Keep the version endpoint fast, because the app reads `/health`. Sharing one cache per process is a good clean-up but not required. No API level, encrypted format or migration impact.

### S4-02: Deleting a heavy user's account overruns Prisma's 5 s transaction timeout and locks the user's groups on each attempt

- Verdict: CONFIRMED WITH CORRECTIONS
- Severity: medium (reviewer said high)
- Launch: must-fix (cheap to fix, and it affects the account-erasure promise; see the severity note)
- Evidence:
  - Code: `deleteAccountRecords` runs one `db.$transaction` with no `timeout` option (packages/api/src/lib/account-deletion.ts:19). The PrismaClient (packages/database/src/client.ts) sets no `transactionOptions`, so the 5 s default applies. `lockUserGroups` takes `FOR UPDATE` on every group the user belongs to (packages/api/src/lib/lockUserGroups.ts). Then `groupEncryptedPayload.deleteMany({ senderUserId })` deletes everything in one statement (line 91). On failure, the scheduled job sets `deletionRetryAt` +5 min and logs `Scheduled account deletion failed` with no error code (apps/scheduled-jobs/src/jobs/accountDeletion.ts:30-36).
  - My own seed (`v3/seed.sql`): one pending-deletion user in 3 groups whose owner is another user, 300-character ciphertext rows, plus 20k rows per group from the other member. Postgres 16.15 in a local container with `shared_buffers` 128 MB. Runner: `v3/run.ts`, which also starts an `INSERT` into group 1 from the other member 800 ms in.

    | Rows deleted | Attempt         | Result                         | Other member's insert waited |
    | ------------ | --------------- | ------------------------------ | ---------------------------- |
    | 150,000      | 1st, after seed | success, 324 ms                | 18 ms                        |
    | 345,600      | 1st, after seed | **P2028**, 7.1 s, rolled back  | 6.3 s                        |
    | 345,600      | 2nd             | success, 786 ms                | 20 ms                        |
    | 691,200      | 1st, after seed | **P2028**, 19.2 s, rolled back | 19.5 s                       |
    | 691,200      | 2nd             | **P2028**, 6.1 s               | 5.5 s                        |
    | 691,200      | 3rd             | success, 2.9 s                 | 2.1 s                        |

    P2028 is raised at the next query (`groupEpochRecipientKey.deleteMany`), so the bulk delete runs to the end and then rolls back. That confirms the reviewer's mechanism, and confirms that group uploads by other members are blocked for the whole attempt (FK `FOR KEY SHARE` against `FOR UPDATE`).
- Corrections:
  - "Never completes" is overstated. On this machine, retries succeeded once the user's rows were in cache: the second attempt at 345k and the third at 691k. Whether it ever completes depends on whether the user's heap pages stay cached between attempts 5 minutes apart. My seed puts each user's rows next to each other on disk. Real rows arrive interleaved with every other user's uploads over 60 days, so a deletion needs close to one random page read per row and much more memory to stay warm. On a small hosted or self-hosted box the reviewer's "fails every 5 minutes for ever" is plausible, but not certain.
  - Row volumes are overstated. `CaptureSamplingPolicy.kt` queues a point every 30 s or 10 s only while moving or after moving 25 m. When stationary it queues at most one point every 5 minutes (`MAX_STATIONARY_SKIP_MS`). Location history is deleted after 60 days (apps/scheduled-jobs/src/jobs/locationHistoryCleanup.ts). A typical user, mostly stationary with about an hour of travel a day, makes about 650 points a day, which is about 40k rows per group over 60 days. In 3 groups that is about 120k rows, which deleted in under 0.5 s here. Getting to 345k–700k needs a user who moves several hours a day and is in 3 or more groups (rows are per group). This failure is real for a minority of accounts, not typical ones.
  - The `immediate` path in `accountRouter` (packages/api/src/router/accountRouter.ts:358-366) wraps `deleteAccountRecords` in `tryCatch` and ignores the result, and `deletionDate` is already "now". The user sees no error. The scheduled job takes over and hits the same problem.
  - Sessions are deleted when deletion is scheduled (accountRouter.ts:355), so the deleted user makes no new uploads during the attempt, which supports the batch-delete fix.
  - The leave/remove path (groupMembershipRouter.ts:310) has the same single-statement delete for one group inside a transaction holding the group lock. That needs about 300k+ rows from one member in one group, which means a very heavy mover. The client just gets an error and can retry.
- Severity note: I rated it medium because typical accounts are well under the threshold and retries often succeed once rows are cached. If it hits a heavy account on modest hosted hardware, though, erasure silently never happens, with only a code-less log line, which would be a GDPR erasure failure. The fix is small and needs no schema change, so I still mark it must-fix.
- Fix assessment: The suggested fix is right. Delete `GroupEncryptedPayload` by `senderUserId` in batches (for example `DELETE ... WHERE id IN (SELECT id ... LIMIT 5000)`, as locationHistoryCleanup.ts already does) before the locking transaction, and leave a final `deleteMany` inside it to catch stragglers. The cancellation race must be handled: a sign-in can cancel a pending deletion (`deletionCancellationPending`). Without a "deleting" mark taken under the user lock, an account could lose some history and then be kept. Either mark it first, as the reviewer says, or accept that partial loss of the user's own history is fine for an account that asked to be deleted. Also give the final transaction an explicit `timeout`, and log `errorCode(error)` in the job. Apply the same batching to the leave/remove group path. No API level, encrypted format or migration impact (`@@index([senderUserId, groupId])` already exists).

### S5-01: Resend email calls have no timeout, so a slow Resend stalls requests and piles up background sends

- Verdict: CONFIRMED
- Severity: medium (reviewer said medium)
- Launch: post-beta (reviewer said must-fix); see below
- Evidence:
  - Code: packages/email/src/transport.ts:34, 38 and 49 call `resend.emails.send`, `domains.list` and `domains.get` with no `requestOptions`. In resend 6.37.0, `fetchRequest` (node_modules/resend/dist/index.mjs:1709-1721) passes `options` straight to `fetch`, adds no timeout of its own, and turns any thrown error (including an abort) into `{ error: application_error }`. `createSendEmail` (packages/email/src/sender.ts) adds no timeout either. SMTP has 8 s/8 s/30 s timeouts.
  - `accountRecovery.requestReset` awaits `ctx.emailCodes.send` (accountRecoveryRouter.ts:196), which awaits `sendCodeEmail` after its DB transaction (packages/auth/src/emailCode.ts:123), so the request hangs for as long as Resend does. The better-auth email-code endpoints use `runInBackground` (emailCodePlugin.ts:196), so they return at once but leave a pending promise.
  - Repro (`v3/resend-hang.ts`): `RESEND_BASE_URL` points at a local TCP server that accepts and never replies, and `createEmailTransport({ transport: "resend" })` calls `.send(...)`. After 60 s the send was still pending, on one connection (`still pending at 60s, connections=1`). The process was then stopped before the 120 s mark, so I did not find out whether Bun's `fetch` has any timeout of its own. Either way, the send outlasts the backend's 60 s `idleTimeout` and the app's 30 s request timeout.
  - Fix check (`v3/resend-signal.ts`): `emails.send(payload, { signal: AbortSignal.timeout(2000) })` returned `{ error: { name: "application_error" } }` after 2001 ms, and `domains.list({ limit: 100 }, { signal: AbortSignal.timeout(1000) })` did the same after 1001 ms. Both type-check against `RequestOptions`. The existing `if (result.error) throw` then turns that into a rejection, as intended.
- Corrections:
  - One more impact the finding doesn't mention: in scheduled-jobs, `runAccountDeletion` ends with `await waitForSecurityAlerts()` (apps/scheduled-jobs/src/services.ts:28), which waits on every pending alert email. A hung Resend therefore also delays the account-deletion job from re-arming, and the same applies to `closeServices` on shutdown.
  - The backend's `idleTimeout: 60` (apps/backend/src/index.ts:68) does cap the client-visible wait for `requestReset`. The app's own 30 s request timeout fires first, so the user sees a timeout and can retry. The code row is written, but the user doesn't know a code may still arrive.
- Launch: Resend hanging after accepting a connection is a rare partial outage. Code requests through better-auth still return quickly, and the recovery-reset request fails in a way the user can retry. Pending promises clear once the hung connections close; I saw at least 60 s and didn't measure an upper bound. I rate this post-beta, although the fix is a few lines and worth taking now.
- Fix assessment: The suggested fix is right and safe. Pass `{ signal: AbortSignal.timeout(15_000) }` as the second argument to `emails.send`, `domains.list` and `domains.get`. Create it per call, not once at module level. A unit test with a never-responding `RESEND_BASE_URL` server, as in my script, would cover it. No API level, encrypted format or migration impact.
