## Findings

### [S7-01] Every idle poll re-renders the whole map screen, even when nothing changed

- Location: apps/mobile/lib/mapTracking.ts:493-497 (poll), :449-453 (getLatest); apps/mobile/hooks/useLiveTrackingPositions.ts:38-40; apps/mobile/app/(tabs)/map/index.tsx:216-288; apps/mobile/components/map/NativeMap.tsx:360
- Category: design
- Severity: medium
- Launch: post-beta
- Confidence: high
- Evidence: The server returns `sharing` on every `poll` and `getLatest` (packages/api/src/lib/groupTracking.ts:275-280, 322-323). `liveTick` and `loadLatest` then always call `refreshStatus()` and `notify()`, without comparing the new sharing state to the old one. `useLiveTrackingPositions` answers each notify with `setTracking({ positions: session.getLivePositions(), status: session.getStatus() })`. Both are fresh objects every time: `getLivePositions` rebuilds the map and maps every entry through `toLiveMapPosition`. In `index.tsx`, `markers` and `people` depend on `livePositions` and `trackingStatus`, so the whole pipeline runs again: buildLiveMapMarkers, applySelfDeviceLocation, hideMapGroupMarkers, flagUnreadableMarkers, labelDeviceIcons, classifyMapPeople. NativeMap then gets new marker objects, a new inline `devices` array and new callbacks, and runs `JSON.stringify(mapStyle)` again (66 KB, 71 layers, measured). New `ringColors` arrays and `unreadableGroup` objects also re-run the `annotationRef.refresh()` effect in LiveMapPointAnnotation on iOS. I confirmed this with a temporary test (`apps/mobile/lib/mapTrackingNotify.reviewtmp.test.ts`, now deleted): with 2 groups, one unchanged poll cycle fired 2 notifies.
- Failure scenario: A user in 3 groups with the map open and nobody moving gets about 3 full screen re-renders every 5 s, each rebuilding every marker and pin. This is wasted CPU and battery on the screen people leave open longest, and it gets worse as groups and members grow.
- Suggested fix: In `mapTracking`, only notify when the sharing state actually changes (compare deviceId, paused and revisionPrefix) or positions change, and keep `getLivePositions()`/`getStatus()` referentially stable between changes (cache the last result). Memoise `devices` in index.tsx, and memoise the style string together with `mapStyle` in `useNativeMapStyle`.

### [S7-02] The "Can't reach the server" warning only appears inside the people tray

- Location: apps/mobile/components/map/LiveMapPeopleTray.tsx:64-70; apps/mobile/lib/classifyMapPeople.ts:25; apps/mobile/app/(tabs)/map/index.tsx:142-151
- Category: UX
- Severity: medium
- Launch: post-beta
- Confidence: high
- Evidence: `status.connection === "failing"` reaches the UI only as `people.connectionLost`, and only `LiveMapPeopleTray` reads it (checked with grep). The tray is closed by default (`storage.getBoolean(peopleTrayKey) ?? false`) and hides while any sheet is open (NativeMap.tsx:108-110).
- Failure scenario: The phone goes offline or the server goes down while the map is open. Polls back off to 60 s, but pins keep showing the last known positions with no warning. The clock badge only appears once a location is 10 minutes old. Someone checking where a family member is right now can be shown stale data with nothing on screen to say so.
- Suggested fix: Show a small banner in the map overlay (next to the paused and key banners in index.tsx) whenever `trackingStatus.connection === "failing"` or `membership === "failed"`, whatever the tray state.

### [S7-03] A map that fails to load shows only a spinner, forever, with no explanation

- Location: apps/mobile/components/map/NativeMap.tsx:323-346, 478-485; apps/mobile/components/map/useNativeMapStyle.ts:200-221; apps/mobile/hooks/useSignedPmtilesUrl.ts:24-25
- Category: UX
- Severity: medium
- Launch: post-beta
- Confidence: high
- Evidence: Until the first signed URL arrives, NativeMap returns a bare `ActivityIndicator` labelled "Loading map". The only error with copy is `SERVICE_UNAVAILABLE` ("The server is still preparing the map"). Other failures (offline, timeout, 5xx) keep the spinner up, and `retry` returns true for everything except UNAUTHORIZED, so it retries forever. After a PMTiles source failure, `showRecoverableError` only shows the same small spinner in the corner and auto-retries every 5 s. `retryUrl` and `retryMapLoad` are returned but no button uses them. The early return also hides the people tray and every map control.
- Failure scenario: The user opens the app with no signal, or a self-hosted server has a broken R2/PMTiles config. The map tab spins indefinitely, gives no hint that the network or server is the problem, offers no retry, and even the people list is unavailable.
- Suggested fix: After a short delay or N failures, replace the spinner with copy ("Can't load the map. Check your connection.") and a Retry button wired to `retryUrl`/`retryMapLoad`. Consider rendering the people tray without the base map.

### [S7-04] Signed PMTiles URL refresh ignores server clock offset and misses tile-level expiry

- Location: apps/mobile/hooks/useSignedPmtilesUrl.ts:18-23; apps/mobile/lib/pmtilesUrl.ts:1-14; apps/mobile/components/map/useNativeMapStyle.ts:82-103; packages/api/src/lib/pmtilesUrl.ts:11,29
- Category: bug
- Severity: medium
- Launch: post-beta
- Confidence: medium
- Evidence: The server sets `refreshAt` to `expiresAt - 60_000` (server clock). `getPmtilesUrlRefreshDelayMs` compares it with the device's `Date.now()`, not `serverNow()`, even though `lib/locationSharing.ts:73-78` already keeps a server clock offset. The retry backoff (1, 2, 4, 8, 16, 30 s) uses up the whole 60 s margin after about 5 failures. Failure detection relies on a `LogManager` filter that only matches "Failed to load source protomaps … PMTiles", which covers source/header loads. Range requests for individual tiles that start returning 403 after expiry are not detected.
- Failure scenario: A phone whose clock runs more than 60 s slow, or a minute of flaky network around refresh time, lets the signed URL expire while the map is open. Panning or zooming into new areas then gives blank tiles with no error and no forced refresh until the next scheduled refetch succeeds. Upstream MapLibre reports that errored tiles can stay blank even after recovery (docs/research/map-rendering.md, "tile retry report").
- Suggested fix: Compute the delay with `serverNow()`, or have the server return a relative `refreshInMs`. Widen the refresh window to several minutes. Also treat tile HTTP 403 log lines as a load failure that triggers `forceRefreshSignedPmtilesUrl`.

### [S7-05] A position with a future timestamp pins that device's marker until the screen remounts

- Location: apps/mobile/lib/liveMapReducer.ts:17-31 (`isNewerThan`)
- Category: bug
- Severity: low
- Launch: post-beta
- Confidence: medium
- Evidence: Newer-wins ordering compares the sender-supplied ISO `timestamp` as a string first; server `createdAt`/`id` only breaks ties. `validateTrackingPointV1` accepts any valid UTC timestamp, including ones in the future and with variable fraction digits (`(?:\.\d+)?Z`). The 5-minute reconcile goes through the same reducer, so it does not fix the problem.
- Failure scenario: A phone's clock jumps a day ahead (manual time, a mock-location app, a GPS glitch) and uploads one point, then the clock is corrected. Every later real point loses the comparison, so the map shows the old position, labelled "just now", until the user leaves the tab or restarts the app. A separate edge case: within the same second, string comparison orders "…:00Z" after "…:00.5Z".
- Suggested fix: Compare with `Date.parse`, and ignore or cap sender timestamps more than a few minutes beyond server `createdAt` (or beyond `serverNow()`) when ranking.

### [S7-06] Groups with no visible points call getLatest every 5 seconds indefinitely

- Location: apps/mobile/lib/mapTracking.ts:466-475 (coldTick), 531-534
- Category: design
- Severity: low
- Launch: post-beta
- Confidence: high
- Evidence: `coldTick` switches a group to `live` mode only when `getLatest` returns at least one point. The server filters out paused devices' points (`filterSharedPoints`). So a group where everyone is paused, a brand new group, or a group whose history has passed the 60-day retention stays `cold`. A test confirms this is deliberate ("empty cold start stays cold and retries getLatest on the next tick"). The memory note says getLatest should only run on a full page.
- Failure scenario: A user's family group with everyone paused, open on the map, makes the heavier LATERAL-join `getLatest` query, plus the sharing-state query, every 5 s instead of the cheap cursor poll. Across many hosted users this adds server load and radio wake-ups.
- Suggested fix: Have `getLatest` return the group's current max cursor, even when there are no visible points, and switch to `live` with it. Alternatively, back off cold retries when results stay empty.

## Patterns for the cross-cutting pass

- **Error handling**: `mapTracking` wraps each group tick in `tryCatch`. Failures are tracked as `groups[groupId]: "failed"`, `membership: "failed"` and `connection: "failing"`; nothing is thrown to React. Decryption never throws to the session: `mapTrackingDecrypt` returns `{status: "ok" | "ignored" | "undecryptable"}` and caches missing epoch keys for 60 s. UI components use `tryCatch` around mutations and show inline text (LocationSharingPausedBanner) or `Alert.alert` (GroupMapColorPicker). `hiddenMapGroups.ts` uses a plain try/catch around `JSON.parse`.
- **Timeouts and retries**: All tRPC calls go through `timeoutLink` (20 s query, 30 s mutation). On top of that, `mapTracking` applies its own 15 s abort via `withTimeout`. Each group backs off 5→10→20→40→60 s; membership backs off separately; a successful tick resets it. Signed PMTiles URL: react-query with unlimited retries (except UNAUTHORIZED) and 1–30 s exponential delay. `saveGroupColor` uses a manual 5 s AbortController.
- **Polling lifecycle**: one session per mounted map screen. It is active only when the screen is focused and AppState is `active`. Deactivation aborts in-flight requests and bumps run ids so late results are dropped. `destroy` on unmount (including sign-out, via the `(tabs)` redirect) clears listeners and in-memory epoch keys. Other map queries use `subscribed: isFocused` and the AppState-wired `focusManager`.
- **Loading, error and empty UI**: People are grouped into upToDate, outOfDate, paused, waitingForLocation, cantLocate, cantRead (groupKey or point), hidden, finding and waiting. A pin whose latest point is unreadable but has an older readable one shows a red "!" badge and "Newer location can't be read". Connection loss appears only in the tray (S7-02). Map load errors have almost no copy (S7-03). There is no empty state (S7-09).
- **API shapes**: `groupTracking.poll` returns `{points, sharing, cursor, hasMore}`. `getLatest` returns `{points, sharing}`. The client treats `sharing`, `cursor` and `hasMore` as optional for older servers. Points carry ciphertext plus metadata, and metadata is bound into decryption through `expectedMetadata`.
- **Storage**: MMKV keys `map.showSymbols`, `map.peopleTrayOpen.<userId>`, `map.hiddenGroups.<userId>`, `map.keyBannerDismissed.<userId>.<groupId>` and `group.color.<groupId>`. The group colour is also synced to the server, sealed for self (`purpose: "group-color"`, bound to userId and groupId). `group.color.*` is not namespaced per user, but `clearGroupColors` exists for sign-out. I did not verify that it is called; that belongs to the auth/sign-out section.
- **Logging**: no console logging in scope. A MapLibre `LogManager.onLog` hook swallows PMTiles source errors and turns them into retry state.
