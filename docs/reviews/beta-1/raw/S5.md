## Findings

### [S5-01] Resend email calls have no timeout, so a slow Resend stalls requests and piles up background sends

- Location: packages/email/src/transport.ts:34, packages/email/src/transport.ts:38, packages/email/src/transport.ts:49; awaited in packages/api/src/router/accountRecoveryRouter.ts:196 and packages/auth/src/emailCode.ts:123
- Category: bug
- Severity: medium
- Launch: must-fix
- Confidence: high (that no timeout is set); medium (how long Bun's fetch waits by default)
- Evidence: `resend.emails.send({ from, ...message })`, `resend.domains.list()` and `resend.domains.get()` get no `signal`. In resend 6.37.0, `fetchRequest` passes `options` straight to `fetch` (node_modules/resend/dist/index.mjs:1709-1721) and sets no timeout of its own, while `emails.send(payload, requestOptions)` forwards `requestOptions` into that call, so a `signal` would work. SMTP has `connectionTimeout`/`greetingTimeout`/`socketTimeout`, and every R2 and Protomaps call in this section has a timeout, so Resend is the only outbound call without one.
- Failure scenario: Resend accepts the TCP connection but never answers, as happens during a partial outage. `accountRecovery.requestReset` awaits `emailCodes.send`, which awaits `sendCodeEmail`. The request hangs until Bun's 60 s server `idleTimeout` (apps/backend/src/index.ts:68) drops the connection, and the user sees a network error even though the code row was written. Sign-up, password-reset and email-verification codes and every security alert run through `runInBackground`/`sendInBackground`, so each one leaves a pending promise for as long as Resend hangs. At startup, `checkEmail` (index.ts:18) can hang inside `checkServices`. That call is bounded at 10 s, but the hung fetch is never aborted.
- Suggested fix: Pass `{ signal: AbortSignal.timeout(15_000) }` as the second argument to `emails.send`, `domains.list` and `domains.get`. A test that a never-resolving `fetch` makes `send` reject would prevent this coming back.

### [S5-02] Following the docs with `docker run --env-file .env` turns the inline comments in `.env.example` into values

- Location: .env.example:1-48 (every line with a trailing `# ...` comment); apps/map-tiles/README.md:51 (`docker run -d --name map-tiles --env-file .env ...`)
- Category: UX
- Severity: medium
- Launch: post-beta
- Confidence: high
- Evidence: Copied `.env.example` to `scratchpad/envt/.env`. `bun --env-file=.env` strips the comments (`BETTER_AUTH_URL="http://localhost:3000"`, `SMTP_PORT=""`). `docker run --rm --env-file .env --entrypoint env postgres:16-alpine` keeps them: `MAP_TILES_PORT=                        # Optional, defaults to 8080; ...`, `BETTER_AUTH_URL=http://localhost:3000  # Public URL of the backend`, `TRUSTED_PROXY_PROVIDER=none            # Optional, ...`, and `CLOUDFLARE_ORIGIN_SECRET=              # Required when TRUSTED_PROXY_PROVIDER=cloudflare-authenticated; at least 32 char...`.
- Failure scenario: A self-hoster follows the root README (`cp .env.example .env`) and then the map tiles README (`docker run ... --env-file .env`). `MAP_TILES_PORT` and `MAP_TILES_UPDATE_INTERVAL_DAYS` fail validation (`blankAsUndefined` only drops all-whitespace values), so the service won't start. The backend image fails in the same way on `BETTER_AUTH_URL`, `TRUSTED_PROXY_PROVIDER` and `SMTP_PORT`. One case is quieter: if `TRUSTED_PROXY_PROVIDER=cloudflare-authenticated` is written on a clean line but `CLOUDFLARE_ORIGIN_SECRET` is left as in the example, the secret becomes the public comment text. That text is over 32 characters, so it passes `z.string().min(32)`, and anyone who reads the repo can forge the origin-secret header.
- Suggested fix: Move every comment in `.env.example` onto its own line above the variable, or split it into per-container env examples with comments on separate lines. Optionally refuse env values that contain `#` after whitespace.

### [S5-03] docker-compose publishes Postgres (with a known password) and Dragonfly (with no auth) on every interface

- Location: docker-compose.yml:4-9, docker-compose.yml:18-22
- Category: security
- Severity: medium
- Launch: post-beta
- Confidence: high
- Evidence: `ports: - "5432:5432"` with `POSTGRES_PASSWORD: openbeacon`, and `ports: - "6379:6379"` for Dragonfly with no `--requirepass`. Docker's published ports bypass host firewalls such as ufw. `restart: always` restarts both on every boot. This is the only compose file in the repo, and the README tells self-hosters nothing else about running Postgres or Redis.
- Failure scenario: A developer on shared Wi-Fi, or a self-hoster who reuses this file on a VPS, exposes the whole database (accounts, emails, device names, wrapped keys) to anyone who tries `openbeacon:openbeacon`. Redis can be read or flushed, which resets rate limits and email caps.
- Suggested fix: Bind to loopback (`"127.0.0.1:5432:5432"`, `"127.0.0.1:6379:6379"`), use `restart: unless-stopped`, and add a comment at the top of the file saying it is for development only.

### [S5-05] The map tiles service's localhost API accepts cross-site POSTs

- Location: apps/map-tiles/src/server.ts:66-71, apps/map-tiles/src/server.ts:96-126
- Category: security
- Severity: low
- Launch: post-beta
- Confidence: medium
- Evidence: `/update` and `/rollback` accept any POST and never check `Content-Type`, `Host` or `Origin`. `readUpdateRequest` JSON-parses `request.text()` whatever the content type, so a `text/plain` body `{"force":true}` is a CORS "simple" request with no preflight. Inside the Docker image only that container's loopback can reach it, but the root `package.json` has `"map-tiles": "bun apps/map-tiles/src/index.ts"`, so it can also run on an operator's desktop.
- Failure scenario: An operator runs `bun run map-tiles serve` locally and visits a hostile page. The page `fetch`es `http://127.0.0.1:8080/rollback` (no body needed), or `/update` with `{"force":true}`. That rolls the live map back, or reinstalls a rolled-back build and starts a 130 GiB transfer. DNS rebinding would also expose `/status`.
- Suggested fix: Require `content-type: application/json` on POSTs (which forces a preflight the server never approves), and reject requests whose `Host` isn't `127.0.0.1:<port>`.

### [S5-06] API input schemas mix `z.strictObject` and `z.object`, so additive fields break older servers on some routes

- Location: packages/schemas/src/schemas/auth/accountRecovery.ts:26-68 (strict) and registerDeviceKey.ts:66 (strict) vs. every other input schema (`z.object`, which strips unknown keys)
- Category: design
- Severity: low
- Launch: post-beta
- Confidence: medium
- Evidence: `changeRecoveryPhraseSchema`, `setupAccountRecoverySchema`, `resetAccountRecoverySchema`, `addHistoryWrapsSchema`, `createAccountHistoryKeySchema` and `wrappedHistoryEpochKeySchema` reject unknown keys. Device, group, tracking and feedback inputs silently drop them. CLAUDE.md rule 14 says a level bump is only needed when an older server lacks a feature. With strict schemas, even an optional extra field from a newer app is a breaking change.
- Failure scenario: A future app adds an optional field to `accountRecovery.changeRecoveryPhrase` without raising `minServerApiCompatibilityLevel`, as the rules allow for additive changes. Every server still on the old version answers BAD_REQUEST, and users can't change their recovery phrase.
- Suggested fix: Pick one policy and document it in docs/development/api-compatibility.md. Either use `z.object` everywhere, or keep strict objects but state that any new input field needs a `minServerApiCompatibilityLevel` raise.

### [S5-07] Inconsistent length limits on IDs and passwords; the client accepts passwords the server rejects

- Location: packages/schemas/src/schemas/account/fields.ts:8-10 (`passwordSchema` has no max), changePassword.ts:5; group/tracking.ts:34,42,46,51 (`groupId`, `cursor.id` have no max); group/removeMember.ts:5-7 (`groupId`, `memberId`, `successorMemberId` have no max); group/inviteMember.ts:6 (`groupId: z.string()` with no min or max); auth/accountRecovery.ts:65 (`groupId` has no max)
- Category: bug
- Severity: low
- Launch: post-beta
- Confidence: high
- Evidence: Scratchpad script `names.reviewtmp.ts`: `signUpSchema` accepts a 500-character password. better-auth's default `maxPasswordLength` is 128 (`options.emailAndPassword?.maxPasswordLength || 128` in node_modules/better-auth/dist), and packages/auth/src/createAuth.ts doesn't override it. Elsewhere in the same package and in the routers, IDs use `.min(1).max(128)` (deviceId, epochId, the `groupProcedure` input). The 8 MB body cap (apps/backend/src/index.ts:69) is the only bound on the unbounded ones.
- Failure scenario: A user picks a 150-character passphrase in a password manager. The sign-up form accepts it and the server answers with a generic error, so the user doesn't know why sign-up failed. Unbounded IDs let a member send megabyte-long strings into Prisma `where` clauses and logs. This is harmless today but inconsistent.
- Suggested fix: Add `.max(128)` to `passwordSchema` with a clear message, matching better-auth's limit. Add a shared `idSchema = z.string().min(1).max(128)` to `@openbeacon/schemas` and use it for every ID field, including the inline copies in packages/api routers.

## Refactor candidates

- **Env parsing helpers**: `emptyToUndefined` (email), `blankAsUndefined` (map tiles), `optionalEnvString` (schemas) and four inline preprocessors in apps/backend/src/envSchema.ts do the same job. One exported helper plus a test would also fix S5-11. Small (about 30 lines touched).
- **R2 client construction**: `createR2Clients` in apps/map-tiles/src/r2.ts and packages/api/src/r2.ts both build the same S3Client config with a hard-coded endpoint. Move one factory into `@openbeacon/map-tiles` and add an optional `R2_ENDPOINT`. Small.
- **ID schemas**: Many inline copies of `z.string().min(1).max(128)` across packages/schemas and packages/api routers (groupProcedure, groupSettingsRouter, groupEpochRouter, groupInvitesRouter, groupMembershipRouter), some missing the max. A shared `idSchema` removes the drift. Medium (mechanical, many files).
- **Email package composition**: Replace the module-level singletons in packages/email/src/index.ts with a factory (S5-13). Small to medium; the call sites in packages/auth already accept injected senders.
- **`tryCatch` has no sync variant**: Code wraps sync work in async IIFEs to use it (apps/map-tiles/src/upload.ts:74 `tryCatch((async () => JSON.parse(...))())`) or falls back to `try {}` (schemas refines, email config.ts:92). A `tryCatchSync` would make rule 8 easier to follow. Small.
- **scripts/derby-emulators.py `main()`**: It is about 180 lines mixing argument parsing, env bootstrap, Docker, builds, emulator boot and the GPS loop. Splitting out env bootstrap and the boot loop would make it easier to test. Medium; it is developer-only, so low priority.

## Patterns for the cross-cutting pass

- **Error handling**: `tryCatch` (async only, casts `error as E`, so non-Error throws are typed as Error) is used consistently in email, map tiles and shared. Sync parsing falls back to `try {}`. Map tiles turns every failure into a plain-English `Error` message that reaches the CLI user. The email transport strips server messages and logs only SMTP `code`/`responseCode` or the Resend error name, never addresses or content. `checkServices` and `validateEnv` print variable and service names with error codes only, never values.
- **API response shapes**: The map tiles HTTP API returns `{ error: string }` with 4xx/5xx, or typed JSON validated by zod on the client (`status.ts` schemas shared by server and CLI). No versioning; the CLI and service ship in one image.
- **Validation**: zod 4 everywhere. API inputs mostly use `z.object` (strips unknown keys), but the account recovery and history schemas use `z.strictObject` (S5-06). Key material is checked for canonical base64 and exact length. Names have control-character filters of varying strictness (S5-08). The map manifest uses `.loose()` on purpose so older readers keep unknown fields. Env validation goes through `validateEnv` (backend, map tiles) or `createEnv` (email).
- **Timeouts and retries**: SMTP: 8 s connect, 8 s greeting, 30 s socket. Resend: none (S5-01). R2 in map tiles: `requestHandler` with 30 s connect and 120 s request, plus explicit 10 s `AbortSignal`s on manifest reads and the startup checks (`writeManifest` has no explicit signal). Protomaps: 30 s for HEAD and the list, 60 s for ranges, and a 120 s stall timer per part download. Part uploads retry 5 times with exponential backoff, and SDK retries are turned off for streamed bodies. Scheduled map checks back off from 1 h, doubling to 24 h. Startup service checks are bounded at 10 s but not cancelled. The mobile client CLI uses a 30 s timeout.
- **Logging**: Plain `console.log`/`console.error` with short prefixes (`[email]`, `[security-alert]`, `[rate-limit]`). Rate-limit warnings are throttled to one a minute with a suppressed count. Console email mode logs the recipient and code, and is allowed only when `NODE_ENV` is development or test.
- **Storage**: Map tiles keeps resumable upload state as JSON under `MAP_TILES_STATE_DIR/<bucket>/<key>.json`, written atomically (tmp file, then rename), and drops it when unreadable. Paths come only from env and fixed slot keys, so there is no path traversal. Manifest writes use `If-Match`/`If-None-Match: *` for optimistic concurrency.
- **Privacy**: Emails carry the address, event, time and timezone, Device name, model and platform, and whether the account has a password. All of this is stored in plain text on the server and accepted in docs/security/beta-1-privacy-draft.md (OPE-190 D5). No locations, IPs or E2E material go into emails. Subjects are constants, recipients come from the DB, and the sender is validated with `z.email()`, so there is no header injection. React escapes all user values, which `allEmails.test.tsx` covers.
