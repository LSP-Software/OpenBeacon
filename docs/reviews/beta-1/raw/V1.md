# V1: verification of S2-01, S2-02, S2-03, S8-01

Verified at commit `94a73b27`. All temporary tests were deleted after running. The integration DB was a throwaway integration database; test rows used random prefixes and were cleaned up in `afterAll`.

### S2-01: A session moved to a new phone survives removal of the stolen phone, which can then activate the new phone without the password

- Verdict: CONFIRMED
- Severity: high (reviewer said high)
- Launch: must-fix
- Evidence:
  - Code read: `upsertUserDevice` (packages/api/src/lib/groupEpochs.ts:562-640) runs `session.updateMany({ data: { deviceId: device.id }, where: { id: sessionId, userId } })` whenever it creates a new device, without checking whether the session is already linked to another non-revoked device. That is the opposite of `findDeviceToLink` in deviceRouter.ts, which refuses with "This sign-in already belongs to another phone". `removeUserDevice` (lib/removeDevice.ts:61-69) deletes only sessions with `deviceId = removed` or `deviceId = null`. `device.activationChallenge`/`activate` are `setupDeviceProcedure` (session + session-linked device header). They have no fresh-session check, and the History key is not rotated on device removal (it is only created in `accountHistory.create` and `accountRecovery.reset`).
  - `linkRequestDevice` (lib/requestDevice.ts) deletes the session only when the request's own `x-device-id` header names a revoked device. An attacker sending D2's ID never trips it.
  - Reproduced independently with a temporary integration test (`packages/api/src/router/s201.verifytmp.test.ts`, now deleted). It used real better-auth sessions and built the device context through the real `linkRequestDevice` instead of the test helper. Steps: S0 on phone P creates the History key; S1 registers D1 and activates it with the History key; S1 registers D2; S0 calls `account.removeDevice(D1)`. Output: `S1 after removing D1: exists, deviceId=…-D2`, then `D2 activate { activated: true }`, D2 `activatedBy: "phrase"`, `revokedAt: null`.
- Corrections:
  - Mitigating signals the reviewer didn't mention: D2 shows in the owner's Account › Devices as a Pending device (`listDevices` returns non-revoked devices including Pending ones, and devices.tsx marks `!activatedAt`). The app also shows `NewSignInBanner` for a Pending device that isn't this one. "Sign out other sessions" also kills S1. A careful owner can therefore spot and fix it. But the documented "Remove device" action doesn't do what it says, and an attacker who names D2 like the stolen phone can blend in.
  - Precondition: the attacker needs the raw session cookie and the History private key. Both live in SecureStore (`WHEN_UNLOCKED_THIS_DEVICE_ONLY`), so this needs a rooted or forensically extracted phone, not just an unlocked one. The reviewer's scenario already says this. The rating stays high because the fix is cheap and the failure defeats the main remediation for a lost phone.
- Fix assessment:
  - Best primary fix: in `upsertUserDevice`, refuse to move a session that is already linked to a different non-revoked device (FORBIDDEN, "Sign in again"), matching `findDeviceToLink`. This closes the root cause without signing out a legitimate Pending phone mid-setup, which "delete sessions linked to all Pending devices on removal" would do. I found no normal app flow that registers a new device ID on a session still linked to a live device: `wipeThisPhone` deletes the key and signs out, and the device key and cookie both live in SecureStore. The app should still treat this new error as "sign in again".
  - Add `requireFreshSession` to `device.activate` and `device.activationChallenge`. A legitimate Pending phone activates right after sign-in, so the 30-minute window is fine, and an old extracted session can no longer activate anything. This is defence in depth on its own (a fresh stolen session would still pass), so do both.
  - Compatibility: no API shape, encrypted format or schema change. It is a server-only behaviour change for a path supported apps don't use, so no API level change is needed. Patch bump of `serverVersion`. Add the integration test from the reproduction.

### S2-02: Google sign-in silently links Google to an existing password account

- Verdict: CONFIRMED WITH CORRECTIONS
- Severity: medium (reviewer said medium)
- Launch: must-fix (reviewer said post-beta)
- Evidence:
  - `createAuth.ts` has no `account.accountLinking` option. In better-auth 1.7.14 `dist/oauth2/link-account.mjs` (`handleOAuthUserInfo`), when no Google account matches but a user has the same email, linking is refused only if `(!trustedProvider && !userInfo.emailVerified) || (requireLocalEmailVerified ?? true) && !user.emailVerified || accountLinking.enabled === false || disableImplicitLinking === true`. Otherwise it calls `linkAccount` and signs in. The `databaseHooks.account.create.before` hook only blocks `credential`. No `before` hook touches `/sign-in/social` or the callback.
  - Reproduced independently with a temporary test (`packages/auth/src/s202.verifytmp.test.ts`, now deleted). It signed up a password account via `createAuth`, marked the email verified (as the hosted sign-up path does via `emailCodes`), then called `handleOAuthUserInfo` with a verified Google identity for the same email. Result: `error: null, session: true`, providers `["credential","google"]`.
- Corrections:
  - It only happens when the local account's email is verified. On the hosted server and on self-hosted servers with email enabled, sign-up sets `emailVerified: true`, so it applies. On a self-hosted server without email (`emailCodes === null`), password accounts stay `emailVerified: false` and better-auth refuses the link. The severity is unchanged because the hosted server is affected.
  - Launch: I'd make it must-fix. It breaks a team rule ("password OR Google, never both"), the fix is one config line, and every account linked during beta becomes state with no UI to see or remove it, which must be cleaned up later.
- Fix assessment: `account: { accountLinking: { enabled: false } }` (or `disableImplicitLinking: true`) is right and safe. With it, the id-token sign-in route throws `UNAUTHORIZED` with `code: "OAUTH_LINK_ERROR"` and `message: "account not linked"` (`sign-in.mjs`). The app has no specific handling for this today, so add a clear "This email signs in with a password" message in the Google sign-in path (`apps/mobile/lib/auth.ts`). Add an integration test. No API level change is needed, since only an error is newly returned on a path that should never succeed. Patch server bump. Also check the hosted DB for accounts with both `credential` and `google` before beta.

### S2-03: Unexpected server errors return their internal message to the client

- Verdict: CONFIRMED WITH CORRECTIONS
- Severity: medium (reviewer said medium)
- Launch: post-beta
- Evidence:
  - `createTRPCComponents` errorFormatter (packages/api/src/trpc.ts) rewrites `message` only for `RateLimitContextError` and `TOO_MANY_REQUESTS`. tRPC wraps a thrown non-TRPC `Error` in a `TRPCError` whose message is the cause's message.
  - Reproduced independently (`packages/api/src/s203.verifytmp.test.ts`, now deleted) with `NODE_ENV=production`, the real `createTRPCComponents()` and `fetchRequestHandler`: HTTP 500 body `{"message":"Invalid \`prisma.user.findUnique()\` invocation: Can't reach database server at \`db:5432\`", … "code":"INTERNAL_SERVER_ERROR"}`. There was no stack, but the message was there in full.
  - Confirmed that real producers exist: `packages/email/src/transport.ts` throws `Resend could not send email: <name>` and `SMTP could not send email<details>`.
- Corrections:
  - The suggested fix says "the `onError` hook already logs the location". It does, but `apps/backend/src/routes/trpc.ts` logs only `{ path, location }`, never the message. So today the client sees the message and the operator's logs don't. If the formatter blanks the message, the message is lost entirely unless `onError` starts logging it. Prisma messages can include query arguments, so log it deliberately (possibly truncated).
  - The discriminator "cause isn't a TRPCError" is fiddly, because intentional `INTERNAL_SERVER_ERROR`s in `image-upload.ts` set `cause` to an SDK error. Every intentional `INTERNAL_SERVER_ERROR` message in the API is already generic ("Failed to create group", "Upload verification failed.", and so on). So the simpler and safer rule is: for `INTERNAL_SERVER_ERROR`, always return a fixed generic message.
- Fix assessment: Replace the message for all `INTERNAL_SERVER_ERROR`s in the errorFormatter, log `error.cause?.message ?? error.message` in `onError`, and add a unit test with `NODE_ENV=production`. There is no compatibility impact. The app doesn't branch on these messages. Patch server bump.

### S8-01: Switching server sends the old server's session cookie and raw session token to the new server

- Verdict: CONFIRMED WITH CORRECTIONS
- Severity: high (reviewer said high)
- Launch: must-fix
- Evidence:
  - `@better-auth/expo` 1.7.14 `dist/client.js`: `cookieName = \`${storagePrefix}_cookie\`` (`openbeacon_cookie`). The `init`hook adds`getCookie(await storage.getItemAsync(cookieName))`to every auth request regardless of URL.`apps/mobile/lib/api.ts`copies`authClient.getCookie()`into the`Cookie`header of every tRPC request to`${baseUrl}/api/trpc`. `lib/server-url.ts` `setServerUrl`only writes MMKV`custom_server_url`and clears nothing.`baseUrl`is read at module load, so after the restart the stored hosted cookie goes to the new server.`SESSION_TOKEN_TO_REVOKE_KEY`is unscoped as well. Only`REGISTERED_DEVICE_KEY`is scoped to`baseUrl` (registeredDevice.ts), so the device ID header is _not_ sent to the new server.
  - Signed-in reachability: `ApiCompatibilityGate` links to `/serverUrl` while signed in, and the screen says "Your current session will remain active".
  - I checked the reviewer's claim that the stolen cookie gives broad access on the hosted server, even though the device ID isn't leaked. With only the cookie, `auth.deviceKeyContext` (a `setupProcedure`, which needs only a session) returns `recipients` with the IDs of the user's active devices (`listUserRecipientPublicKeys`). Sending the session-linked one as `x-device-id` passes `linkRequestDevice` (`session.deviceId === header`), which makes every `protectedProcedure` and `groupAdminProcedure` available. Only `freshSessionProcedure` (30 minutes from session creation) is out of reach.
- Corrections:
  - The impact is worse than the reviewer's list. If the victim is a group owner or admin, the receiving operator can call `groupInvites.createShared` (a `groupAdminProcedure`, not fresh-gated) and accept the invite with their own account. Other members' phones then wrap later epoch keys to the new member, giving live locations. Join alerts make this visible to members, but it is still a path from "entered a self-hosted URL" to "a stranger reads the family's locations". I keep it at high rather than critical only because the user has to type the other server's URL themselves. That is a realistic request in a product that promotes self-hosting ("join my server").
  - The raw revoke token is less dangerous than implied. better-auth reads the session from a _signed_ cookie (`getSignedCookie` in `api/routes/session.mjs`) and no bearer plugin is configured, so the raw token alone can't be replayed as a session on the hosted server. The real problems with it are that the old server's session is never revoked, and the token is still a credential-grade identifier.
  - Minor: the launch screen (`app/index.tsx`), sign-in and sign-up also link to `/serverUrl`. Those are only dangerous when a cookie is left behind, for example after a failed sign-out (`signOut.ts` keeps the cookie when the server call fails) or the S8-12 state.
- Fix assessment:
  - Clearing `openbeacon_cookie`, `openbeacon_session_data` and `SESSION_TOKEN_TO_REVOKE_KEY` when `setServerUrl` changes the value is the right minimum. Ideally, make a best-effort `authClient.signOut()` against the old server first, so the old session doesn't stay alive. Also wipe server-scoped local state the way sign-out does (queued points, pending sharing changes) to avoid cross-server leftovers. Change the "session will remain active" copy.
  - Putting a hash of `baseUrl` into `storagePrefix` is stronger, but it signs every existing user out on upgrade, because the cookie key changes. If you do it, migrate the existing `openbeacon_cookie` to the hosted-URL key once. Also store the revoke token as `[baseUrl, token]` and drop it on mismatch.
  - Compatibility: client-only, with no API level change. Patch app bump (`expo.version`, `buildNumber`, `versionCode`).
