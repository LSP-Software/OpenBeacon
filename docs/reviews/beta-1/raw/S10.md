## Findings

### [S10-01] `setLocationSharing` started requiring `requestedAt` without a level bump, so level-4 apps 1.10.0 and 1.11.0 can no longer pause or resume

- Location: packages/schemas/src/schemas/account/locationSharing.ts:13 (`requestedAt: z.date()`), packages/api/src/router/accountRouter.ts:65, packages/shared/src/apiCompatibilityLevel.ts:1-3, apps/mobile/lib/locationSharing.ts:59-66
- Category: bug
- Severity: high
- Launch: must-fix
- Confidence: high
- Evidence: Level 4 was merged in #218 (4c33f1d6, app 1.10.0). Commit 815e2aa6 ("Stop revision-less pause retries…", merged in #222, app 1.12.0) added `requestedAt` as a required field. `git show 4c33f1d6:apps/mobile/lib/locationSharing.ts` sends `change` with no `requestedAt`, and so does 1.11.0 (ad26893b). Levels stayed at 4/4/4, and the #222 PR body says "API compatibility: unchanged". The handshake can't catch this: a level-4 app passes the 426 check, the procedure exists, and zod rejects the input with BAD_REQUEST.
- Failure scenario: A tester on 1.11.0 (the release APK on pixel_8c, for one) talks to the current server (0.12.0 or later). Pausing or resuming sharing fails with a validation error and no "update" screen. Separately, a pending change that a 1.10/1.11 install saved offline has no `requestedAt`, so `readPendingChange` drops it silently after the upgrade to 1.12 (`parseStored` fails, then `storage.remove`).
- Suggested fix: Either raise `apiCompatibilityLevel` and `minClientApiCompatibilityLevel` to 5 before any beta build ships (rule 14b), or make `requestedAt` optional on the server and default it to the server's `now`. Bumping is cleaner while no public installs exist. Add a level-history row either way. S10-05 covers stopping this class of mistake.

### [S10-02] The tracking-point reader rejects any extra field, so every future change to the location payload will force the whole family to update

- Location: packages/encryption/src/trackingPoint.ts:55-87 (`Object.keys(value).length !== 6`, `value.v !== 1`, `Object.keys(value.battery).length !== 2`), apps/mobile/lib/mapTrackingDecrypt.ts:115, apps/mobile/modules/openbeacon-tracking/android/src/main/java/expo/modules/openbeacontracking/capture/BatteryReader.kt:17-30
- Category: design
- Severity: medium
- Launch: must-fix
- Confidence: high
- Evidence: `kotlinJsonCheck.ts` ran Kotlin-style JSON through the real TS encrypt → decrypt → `validateTrackingPointV1` path. A v1 point with one extra key (`"accuracy":12`) comes back "Invalid tracking point.", and so does `v:2`. `mapTrackingDecrypt` turns that into `undecryptable`, and the map shows the person as unreadable. Every beta install will carry this reader, and it can't be changed after shipping. The payload also can't say "battery unknown": `BatteryReader` sends `level = 0` when `levelKnown` is false, and family members see 0%.
- Failure scenario: After beta, someone adds GPS accuracy, altitude or `battery.level: null` to the payload. Every app older than that change marks every point from an updated phone as unreadable. The only fix under rule 14c is to raise `minClientApiCompatibilityLevel`, which locks every older app out of the hosted server.
- Suggested fix: Before beta, make the v1 reader ignore unknown keys at the top level and inside `battery`, and keep validating the known ones. That turns field additions into non-breaking changes, and `v` only changes on a real break. At the same time, decide whether to add `accuracy` and a nullable battery level now, while the format is free to change. For later real breaks, record each device's API level server-side (the header already arrives on every request) so a sender can see whether every recipient in the group can read a new format before switching to it.

### [S10-03] The "Update Open Beacon" screen has a disabled Update button and the server can't send users any guidance, and every installed build keeps this behaviour

- Location: apps/mobile/components/ApiCompatibilityGate.tsx:150-154, apps/backend/src/helpers/apiCompatibility.ts:16, apps/backend/src/routes/health.ts:9-15, docs/development/api-compatibility.md:56-62
- Category: UX
- Severity: medium
- Launch: must-fix
- Confidence: high
- Evidence: `<Button disabled className="opacity-50"><Text>Update</Text></Button>` has had no handler since 1b561e7b. Nowhere in the app opens a store page. The 426 body and `/health` are frozen to the level numbers only. The app parses both with loose `z.object`, so extra fields would be safe for old apps, but nothing reads or renders them.
- Failure scenario: The first time `minClientApiCompatibilityLevel` goes up after beta, every beta install shows "Update Open Beacon" with a greyed-out button and no link. Sideloaded and internal-track testers have no obvious place to get the update. The hosted operator also has no way to show a message such as "maintenance until 15:00" or a link on the "We're updating" screen.
- Suggested fix: Before beta builds go out, have the Update button open the Play Store listing (`market://details?id=net.openbeacon.app` with an https fallback), and/or open an `updateUrl` from the 426 body or `/health`. Add optional `message` and `updateUrl` fields to the 426 body and `/health` (additive, so old apps are unaffected), and show them on the gate when present. Update the frozen-shape test in apps/backend/src/app.test.ts to allow these optional keys.

### [S10-04] A "too old" result taken from a missing procedure flips on and off, because only same-level mismatches stick

- Location: apps/mobile/lib/apiCompatibility.ts:35-46 (`decideUnknownProcedure`), :174-207 (`applyVerdict`), :43-46 in ApiCompatibilityGate.tsx (foreground refresh)
- Category: bug
- Severity: medium
- Launch: must-fix
- Confidence: high
- Evidence: A temporary test (`apiCompatFlap.reviewtmp.test.ts`, deleted) mocked app level 5 with `minServerApiCompatibilityLevel` 4, which is a missed rule-14a bump, against a level-4 server. It alternated `apiCompatibilityFetch(missing procedure)` with `refreshApiCompatibility({ userRequested: false })`. The state went `serverTooOld, null, serverTooOld, null, serverTooOld, null`. `applyVerdict("ok")` clears any problem other than `outOfSync`. `/health` compares only the levels, and the levels look fine, which is exactly the situation the 404 path exists to catch. The mirror case behaves the same way: a server drops a procedure without raising `minClient`, the app concludes `appTooOld`, and `/health` clears it.
- Failure scenario: The app and server disagree after a missed bump. Each time the app comes to the foreground, the gate disappears after `/health`, then comes back as soon as a screen calls the missing procedure. Background uploads start and stop the same way. Tests only cover the sticky same-level case. This logic is the safety net for our own mistakes (S10-01 was one), and beta installs will keep whatever version they ship with.
- Suggested fix: Save where the verdict came from. When it came from `UNKNOWN_PROCEDURE` or a 426, keep it until the user presses Try again or the server's `version` changes, as `outOfSync` already works. Add a test for each level ordering.

### [S10-05] CI can't catch API-narrowing mistakes, and the version check can be bypassed by merge order

- Location: scripts/check-version-bump.ts:6-12, 87-115, 199-229; .github/workflows/pre-merge-checks.yml:60-76 and 151-158; .github/pull_request_template.md:5; AGENTS.md rules 13a, 13c, 14e
- Category: design
- Severity: medium
- Launch: post-beta
- Confidence: high (merge-order and path gaps), medium (whether a merge queue is actually enabled)
- Evidence:
  - Nothing checks the API surface. The script only checks that levels never go down, rise by at most 1, keep each minimum at or below the level, and come with minor bumps. S10-01 got through with "API compatibility: unchanged" in the PR body. Nothing in CI reads that line (rule 14e), and nothing flags changes to procedure inputs, outputs or `packages/encryption/src/testVectors`.
  - The `version-bump` job only runs on `pull_request` against the PR's merge base, and the aggregate job treats `skipped` as passing, so it doesn't run in the `merge_group`. In the `mergetest/` scratch repo, two branches that each raised `0.16.1`→`0.16.2` merged without conflict and left one bump for two changes. The same thing happens to `apiCompatibilityLevel`: two PRs that each raise it 4→5 merge into a single level 5, even if a level-5 server shipped from the first one.
  - Coverage gap: `packages/schemas` imports `@openbeacon/database/enums` (DeviceIcon, GroupRole), which is generated from `packages/database/prisma/schema.prisma` and bundled into the app. A schema-only enum change counts as server-only, so no client bump is required. Rule 13a has the same omission.
  - Rule 13c says "CI enforces this" about patch versus minor. CI only checks that the version went up, and only requires minor for level changes.
- Failure scenario: A future PR tightens an input or removes an output field the app reads, ticks "unchanged", and every check passes. Self-hosters and older apps then break with generic errors that the handshake can't attribute to a version (same pattern as S10-01).
- Suggested fix: Snapshot the API surface: `z.toJSONSchema(input, { io: "input", unrepresentable: "any" })` for every procedure in `appRouter._def.procedures`, plus the procedure list and the testVectors file list, committed as JSON. Fail CI when the snapshot changes without a matching `API compatibility:` line in the PR body. That forces a decision rather than automating it. Run the version check in `merge_group` against `github.event.merge_group.base_sha`. Add `packages/database/prisma/schema.prisma` to the client paths, or move the shared enums into `packages/schemas`. Fix the wording of rule 13c.

### [S10-06] The compatibility rules miss two kinds of skew: new fields on loose schemas, and the better-auth surface

- Location: docs/development/api-compatibility.md:20-31 and 50-56; apps/backend/src/routes/trpc.ts:13-21; apps/backend/src/routes/auth.ts:20-27; packages/schemas (all inputs except accountRecovery and history wraps are loose `z.object`)
- Category: design
- Severity: medium
- Launch: post-beta
- Confidence: high
- Evidence:
  - The input dump shows 77 of the 84 procedures take loose objects. Zod strips unknown keys there, so an older server drops a new field without any error. The doc says "a new optional input" needs no level change, but that only holds if the app doesn't depend on the server acting on the field. Example: app 1.12 sends `requestedAt` to a 0.11 server. The field is dropped, and the bug it fixes (a revision-less pause undoing a later resume) quietly comes back on that server. The schemas don't follow one rule either: `groupEpochBundleSchema` is loose at the top but its `historyKeys` items are strict, so adding a field to a history wrap breaks `create`, `rotate`, `accept`, `acceptShared` and `remove` on older servers.
  - The `UNKNOWN_PROCEDURE` check covers tRPC only. If a newer app calls a better-auth or `/email-code/*` path that an older server lacks or has disabled (`/reset-password` is off without email codes), the server returns better-auth's own 404. `readApiCompatibilityResponse` falls back to the level headers and decides "ok", so the user just sees a generic error.
  - Minor: in the doc's "Level history", only level 1–2 are table rows. Levels 3 and 4 sit outside the table as loose paragraphs.
- Failure scenario: Someone follows the doc and adds an optional guard field the app relies on for correctness, with no level change. Apps then misbehave silently against self-hosted servers that haven't updated.
- Suggested fix: Extend rule 1 and rule 14a: "…or a new input the app needs the server to act on, whether or not the schema is strict." Write down one strict/loose convention (for example, strict only inside cryptographic bundles) and say why. Either return the frozen `UNKNOWN_PROCEDURE` body for unknown `/api/auth/*` paths too, or document that auth endpoints must never be added without a minServer bump. Fix the table.

### [S10-07] Four server procedures are no longer called by any app, and two of them return more than they need to

- Location: packages/api/src/router/authRouter.ts:53-70 (`listMyDeviceKeys`), packages/api/src/router/group/groupEpochRouter.ts:122-147 (`listRecipientPublicKeys`), packages/api/src/router/group/groupMembershipRouter.ts:57-61 (`get`), :81-98 (`members`)
- Category: design
- Severity: low
- Launch: post-beta
- Confidence: high
- Evidence: The diff of app calls against the server list leaves exactly these four. `git log -S` shows the app stopped calling `members`/`get` at level 1 (db2af5f9) and `listMyDeviceKeys` at level 2 (3a88581b). No app has ever called `listRecipientPublicKeys`. With `minClientApiCompatibilityLevel` at 4, the doc allows removing them without a level change. `listMyDeviceKeys` returns revoked devices and their public keys. `get` spreads the whole `Group` row, so any new column becomes API output automatically.
- Failure scenario: The extra surface has to be secured, rate-limited and kept compatible for no benefit, and `get` will expose future `Group` columns without anyone reviewing them.
- Suggested fix: Delete all four in one PR, with "API compatibility: unchanged" and a note in the PR body that the newest app that called them was at level 2. Also see S10-10.

### [S10-08] The Kotlin tracking-point encoder doesn't validate the way the TS encoder does

- Location: apps/mobile/modules/openbeacon-tracking/android/src/main/java/expo/modules/openbeacontracking/crypto/GroupPayloadEncrypt.kt:65-75, capture/TrackingCaptureService.kt:356-360
- Category: bug
- Severity: low
- Launch: post-beta
- Confidence: medium (I didn't confirm that Android can deliver a non-finite speed)
- Evidence: TS `encodeTrackingPointV1` runs `validateTrackingPointV1` before encoding. Kotlin builds the JSON by string interpolation, using `Double.toString()`. `kotlinJsonCheck.ts` confirms that Kotlin's exponent forms (`1.0E-4`, `-0.0`, `1.0E7`, `1.399999976158142`) parse and validate in TS. A `NaN` or `Infinity` speed, though (`location.speed` from a mock or buggy provider with `hasSpeed()` true), produces `"speed":NaN`, which fails `JSON.parse`. That point then shows as unreadable to every recipient and stays on the server for the whole retention window. Otherwise the TS and Kotlin encryptors agree: both are pinned to the shared `group-payload-interop-v1.json` vectors (the JVM test reads the same file through `jvm/build.gradle.kts`), with byte-identical AAD and ciphertext.
- Failure scenario: A device with a misbehaving GPS provider uploads points that no family member can read.
- Suggested fix: In `encodeTrackingPointV1Json`, write `null` for non-finite speed and skip non-finite coordinates. Add a JVM test with NaN and Infinity inputs.

### [S10-09] Unknown crypto versions show error messages that blame the user, not "update the app"

- Location: apps/mobile/lib/recovery.ts:221-235, packages/encryption/src/deviceLink.ts:59-71, packages/encryption/src/personalData.ts:94-95
- Category: UX
- Severity: low
- Launch: post-beta
- Confidence: high
- Evidence: If a newer app stores `derivationVersion: 2` or a new escrow algorithm, an older app restoring from the phrase reports "That phrase doesn't match this account." or "recovery data doesn't match". A newer `openbeacon-link:2:` QR code makes `parseDeviceLinkCode` return null, which looks like an invalid code. ### [S10-10] Some mutations return whole database rows, so a migration silently changes their API output

- Location: packages/api/src/router/group/groupSettingsRouter.ts:34 (`rename` returns `tx.group.update`), packages/api/src/router/group/groupMembershipRouter.ts:396-399 (`updateRole` returns the full `GroupMember`), :60 (`get`)
- Category: design
- Severity: low
- Launch: post-beta
- Confidence: high
- Evidence: There's no `select` on these returns. The app doesn't read these results, but the output type is whatever the Prisma model is at the time. A column rename then counts as "removed an output field" under rule 2 without anyone noticing, and new columns (such as `epochRotationRequired`) reach clients automatically.
- Failure scenario: A later migration adds an internal or sensitive column to `Group` or `GroupMember`, and it ships in API responses unreviewed.
- Suggested fix: Return `{}` or an explicit `select` from these mutations.

## Patterns for the cross-cutting pass

- **Handshake.** Hono middleware on `/api/*` sends the 426 and level headers. The tRPC route pre-checks procedure names and returns the frozen 404. `/health` is outside `/api`. On the app side, one `apiCompatibilityFetch` wraps both the tRPC and better-auth clients. The feedback client sends the header but ignores the result. The state is a module-level store saved to MMKV under the server URL and app level, and read by the gate, the root layout (accessibility hiding) and the headless task.
- **Validation.** Inputs are zod 4 schemas, mostly loose `z.object`. Strict objects are used only for recovery and history-wrap crypto bundles. Literal `algorithm`/`kind` checks sit on the API boundary. Outputs are never validated at runtime in the app; it relies on the shared `AppRouter` type plus superjson. Enum outputs are compared with `===` or have fallbacks (`deviceIconFor` falls back to phone, an unknown role is treated as a plain member, an unknown deviceLink state keeps polling every 2 s). Nothing in the app crashes on a new enum value.
- **Encrypted blobs.** Tracking payloads carry outer `algorithm` and `kind` strings (unknown → ignored) and an inner `v:1` (strict, see S10-02). Personal data uses a JSON envelope with `version` 2 or 3 (zod discriminated union; unknown throws and is caught). Epoch-key wraps and escrows carry `algorithm` strings that are checked on open. HPKE `info` strings carry a `.v1`/`.v2`/`.v3` context. Device-link codes use an `openbeacon-link:1:` prefix and the handover has `v:1` (strict). Session and activation challenges are short-lived and have only the context version. Only the group payload is implemented in both Kotlin and TS, and both are pinned to shared vectors.
- **Errors.** The server's tRPC `errorFormatter` adds `data.cause` (device removed/pending/unverified) and `zodError`. The app's `deviceRemovedLink` acts on `cause`. Compat errors (426/404) aren't tRPC-shaped, so they reach queries as generic `TRPCClientError` and React Query retries them up to 3 times.
- **Timeouts.** `/health` 10 s. tRPC 20 s for queries and 30 s for mutations (`timeoutLink`). better-auth 30 s through a custom fetch that turns network failures into a 503 `SERVER_UNREACHABLE`. The server's key-state lookup after upload is capped at 2 s.
- **Logging.** Only `[trpc] internal server error` with path and a source location; no request data.
- **Not in this section, but noticed:** group names (`groupSettings.rename`, `groupLifecycle.create`) and account names (`account.updateName`) go to the server as plaintext `name` strings. Whoever reviews the end-to-end encryption promise should confirm that's intended. `feedback.submit` sets `ipLimit: 3`, which may conflict with the stated plan to remove IP-based limits.
