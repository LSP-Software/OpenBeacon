### [S6-01] Cold app launch stops sharing and wipes native keys before permissions load; offline, sharing stays off

- Location: apps/mobile/providers/TrackingProvider.tsx:51-54 and :186; apps/mobile/providers/LocationPermissionProvider.tsx:42 and :112-120; apps/mobile/lib/tracking.ts:221-235, :273-290, :493-498
- Category: bug
- Severity: high
- Launch: must-fix
- Confidence: high
- Evidence: `startCapture = permissionState?.isReadyForSharing ?? false`, and `permissionState` starts as `null`. It is only set after `requestNotificationPermissions()` and two native permission reads. TrackingProvider's first cycle runs after one dynamic import, so it almost always reads `startCapture: false` first. The test "provisions keys without starting capture before location sharing is ready" shows that path is `{ startCapture: false, force: true }`. No test covers the real `null` start. In `reconcileTrackingKeys`, `startCapture: false` calls `stopCapture()` straight away, and the internal function then calls `revokeEpochKeys()` (which also sets capture disabled and cancels the resume worker) before it makes any network call. I reproduced the offline sequence with a temporary test, `apps/mobile/lib/tracking.reviewtmp.test.ts` (deleted afterwards), using the existing tracking test harness. First an online `reconcile({startCapture:true, force:true})` provisions keys. Then `groupMembership.list` throws, as it does offline. `reconcile({startCapture:false, force:true})` rejected, and `reconcile({startCapture:true, force:false})` resolved "ok" through the fresh-key-check branch with `hasKeys: false`. Result: `captureRunning: false`, `provisionedKeys: 0`, and `startCapture` was not called again.
- Failure scenario: Android kills the app process. The capture service keeps running or is restarted sticky. Later the user opens the app, for example to look at the map while hiking with no signal. The first reconcile stops the foreground service and deletes the native epoch keys. The second reconcile either can't reach the server or treats the recent key check as fresh with no keys, so capture never restarts. Then the user backgrounds the app. No service, alarm or worker is left to restart it, so the phone captures nothing until the app is opened again online and the 4 to 30 minute key-check window has passed. No notice is shown; the persistent notification just disappears. Online, every cold launch still stops and restarts the service, drops fixes in between, and re-fetches and decrypts every group key wrap. That undoes part of the API-call reduction work.
- Suggested fix: Don't run tracking cycles until `permissionState` is known: treat `null` as "unknown, do nothing", not as "not ready". Keep the revoke-and-stop path for a known `isReadyForSharing === false`. Separately, in the `!startCapture` branch, don't revoke native keys before the server confirms that anything changed. Add a TrackingProvider test that starts with `permissionState: null`.

### [S6-03] Queue rows the server permanently rejects are retried forever and never leave the queue

- Location: apps/mobile/lib/tracking.ts:608-649, :535-541; apps/mobile/modules/openbeacon-tracking/android/src/main/java/expo/modules/openbeacontracking/queue/CiphertextQueueDao.kt:83-97; packages/api/src/procedures/auth/group.ts:12-14; packages/api/src/lib/groupTracking.ts:156-173
- Category: bug
- Severity: medium
- Launch: post-beta
- Confidence: high
- Evidence: Every non-success except `UNAUTHORIZED` ends in `requeueCiphertexts`. `attemptCount` grows forever, and the backoff caps at 5 minutes. There is no dead-letter state and no maximum attempt count. The test "retains rejected batches" shows this is deliberate. Permanent rejections include: FORBIDDEN "You are not a member of this group" (the user left, was removed, or the group was deleted); FORBIDDEN "The active device is not registered" (rows from an earlier device ID of this phone); and a single-item BAD_REQUEST. Nothing deletes queued rows for a group the user has left. Each BAD_REQUEST batch is bisected, so a page of 100 bad points costs up to 199 requests per retry, against a 240/min limit.
- Failure scenario: A user leaves a family group while 2,000 points for it are queued from a day offline. Those rows fail with FORBIDDEN on every flush, every ≤5 minutes for as long as the app is installed. Each failure makes `syncBackgroundTracking` throw, and the rows hold queue space until eviction. Rows from an old device ID, kept after re-registration, behave the same way.
- Suggested fix: Treat "not a member", "device not registered" for a device that isn't this one, and a single-item BAD_REQUEST as terminal: delete those rows, or move them to a failed state that is purged. When reconcile finds that a group has disappeared from membership, delete its queued rows. Add a test for each terminal error.

### [S6-04] Several start paths stop the service before `startForeground` after `startForegroundService`, which Android treats as a crash

- Location: apps/mobile/modules/openbeacon-tracking/android/src/main/java/expo/modules/openbeacontracking/capture/TrackingCaptureService.kt:116-120, :136-144, :204-211; OpenBeaconTrackingModule.kt:70-111; SharingResumeWorker.kt:144-162; TrackingBootReceiver.kt:194-208
- Category: bug
- Severity: medium
- Launch: post-beta
- Confidence: medium
- Evidence: `startCapture`, `refreshCapture`, the resume worker and the boot receiver all use `startForegroundService`. In `onStartCommand`, the `ACTION_START` branch with a stale generation and capture disabled, the `ACTION_REFRESH` branch when `!isCaptureRunning`, the default branch when `!shouldRestoreCapture`, and the SecurityException path in `startCapture` all call `stopSelf()` without promoting first. JS `stopCapture` also calls `stopService` right after a `startCapture` that may not have reached `onStartCommand` yet. Since Android 9, `ActiveServices` posts `SERVICE_FOREGROUND_CRASH_MSG` when a service with `fgRequired` is brought down before `startForeground` ("Context.startForegroundService() did not then call Service.startForeground()"). The code comment on line 145 acknowledges this for one path, and the test `aForegroundStartDuringAnIndefinitePausePromotesBeforeParking` handles it there. Robolectric doesn't enforce the crash, so tests like `aStartRequestedBeforeStopIsIgnored` pass on a path that would crash on a device. I didn't reproduce this on a device.
- Failure scenario: Sign-out, or a permission-driven `reconcile({startCapture:false})`, runs right after `startCapture`. JS calls `stopService` before the service promotes, and the app crashes. The same happens when permission changes between the boot receiver's or resume worker's check and `onStartCommand`.
- Suggested fix: On every branch reached by a `startForegroundService` intent, call `startForeground` with the paused or idle notification before `stopSelf`, as the indefinite-pause branch already does. Alternatively, mark foreground starts with an extra and always promote when it is present. Avoid `stopService` from JS while a foreground start is pending: send an `ACTION_STOP` intent instead (the action exists but is never used).

### [S6-05] High-accuracy GPS runs every 30 s all day even when the phone isn't moving

- Location: apps/mobile/modules/openbeacon-tracking/android/src/main/java/expo/modules/openbeacontracking/capture/TrackingCaptureService.kt:227-251, :385-394; CaptureSamplingPolicy.kt:127-153, :172-173
- Category: design
- Severity: medium
- Launch: post-beta
- Confidence: high
- Evidence: Every request uses `Priority.PRIORITY_HIGH_ACCURACY`, with `minUpdateInterval` and `maxUpdateDelay` equal to the interval, so there is no batching. When stationary, the interval is 30 s (60 s in battery saver). The stationary logic only decides whether a fix is queued, not whether GPS runs. "Moving" is a single threshold at 1.0 m/s from the fix's speed, so walking pace or GPS speed noise flips the interval between 10 s and 30 s. Each flip removes and re-adds the location request.
- Failure scenario: A phone on a desk or nightstand keeps GPS active through the day and night for a heartbeat that is queued only every 5 minutes. On many devices that is the largest battery cost of the app, and it is the usual reason people uninstall location sharing apps.
- Suggested fix: When stationary (several fixes within 25 m), drop to `PRIORITY_BALANCED_POWER_ACCURACY` or `PRIORITY_LOW_POWER` with a longer interval and `setMaxUpdateDelayMillis` for batching. Switch back to high accuracy on movement, using hysteresis (for example, enter moving at 1.5 m/s and leave below 0.5 m/s across two fixes), or the Activity Recognition transition API. Extend `CaptureSamplingPolicyTest` to cover the hysteresis.

### [S6-06] A sharing change the server will never accept blocks uploads forever

- Location: apps/mobile/lib/locationSharing.ts:164-198, :87-89; apps/mobile/lib/tracking.ts:747; apps/mobile/components/LocationSharingCard.tsx:179-182; packages/schemas/src/schemas/account/locationSharing.ts:38-41
- Category: bug
- Severity: medium
- Launch: post-beta
- Confidence: medium
- Evidence: `synchronizeSharing` replays each pending change and throws on any error before it reaches `account.locationSharing.query()`. That query is also what measures the clock offset. `flushPendingTrackingPointsInternal` returns silently while any pending change exists, pause or resume (`hasPendingSharingPause` checks both). Only "superseded" and success remove a pending change. A change the server rejects outright stays forever. Example: the server rejects `requestedAt` more than 24 hours in the future (BAD_REQUEST), and with no measured offset the app uses the phone clock. Because the replay throws first, the offset never gets measured. A device-scope NOT_FOUND has the same effect.
- Failure scenario: A phone whose clock is more than a day fast pauses before it has ever synced, or after its offset key was cleared. Every retry gets BAD_REQUEST, uploads stop for good, and the queue fills to 10 MiB and starts evicting. After a resume, the card says "We'll update your groups when you're back online" while the phone is online.
- Suggested fix: In `synchronizeSharing`, run the `locationSharing` query (and measure the offset) even when a replay fails. Drop a pending change on terminal codes (BAD_REQUEST, NOT_FOUND, FORBIDDEN) and reload state, as "superseded" already does. Show a distinct "couldn't apply" message rather than the offline copy.

### [S6-07] Points captured after a group key rotation can still be encrypted to the old epoch and are accepted indefinitely

- Location: apps/mobile/modules/openbeacon-tracking/android/src/main/java/expo/modules/openbeacontracking/capture/CapturePipeline.kt:38-92; apps/mobile/lib/tracking.ts:665, :843-845; packages/api/src/lib/groupTracking.ts:134-145, :224-229
- Category: security
- Severity: medium
- Launch: post-beta
- Confidence: medium
- Evidence: Capture encrypts with whatever epoch key is provisioned. The phone only learns about a rotation at the next key check, or from the `keyState` hash in an upload response, after that upload has already been sent. Queued rows keep their original `epochId`. The server accepts any epoch that still exists for the group, from `createdAt >= memberSince`; only a deleted epoch comes back as `expired` (and is then dropped from the queue). Nothing compares capture time with rotation time.
- Failure scenario: A member is removed and the group rotates. A phone that is offline for a day keeps encrypting fixes with the old epoch key, which the removed member still holds, and uploads them when it reconnects. The server stores them under the old epoch. A removed member working with the hosted operator can decrypt a day of locations captured after the removal. Online, the window is about one upload interval. Removal-triggered rotation exists to prevent exactly this.
- Suggested fix: After provisioning a new epoch, re-encrypt or drop queued rows for the old epoch whose plaintext timestamp is after the new epoch's `createdAt`. The phone still holds the old key, so it can decrypt to check. Alternatively, have the server reject old-epoch uploads once the successor epoch was created for a removal and is older than some grace period. Coordinate with S1/S3.

## Answers to the focus questions (summary)

- **Background upload path.** Capture service → `TrackingUploadService` (HeadlessJsTaskService, 60 s timeout, its own wakelock) → `syncBackgroundTracking` → reconcile, then flush. Every network call goes through `trpcClient`, whose `timeoutLink` defaults to 20 s for queries and 30 s for mutations. If the task times out, the service stops and releases its wakelock while JS keeps running; nothing is left stuck. Rows are claimed with `markInFlight` (attempt and time recorded). If the process dies mid-batch, rows stay `IN_FLIGHT` until the next `listByStatus`, which returns anything older than 2 minutes to `PENDING`. A lost response leads to a re-upload, and the server reports the points as `duplicates` by `clientPointId`, after which they are deleted. Duplicates are therefore harmless and points aren't lost. The weak spots are permanent rejections (S6-03) and the wipe gap (S6-10).
- **Concurrency.** The foreground app and headless tasks share one JS runtime, so `flushPromise` and `reconcilePromise` single-flight both. Kotlin only inserts rows and checks whether any are pending. Overlapping headless tasks do share and reset the module-level `uploadRejectedKeys` flag (tracking.ts:837), which can skip one follow-up reconcile; the next key check catches it. `useSingleFlight` is correct for UI double taps.
- **Queue limits.** 9 MiB of live pages plus a WAL capped at 1 MiB, with oldest-PENDING-first eviction inside the insert transaction. Evictions are recorded per owner and shown on the map. This behaves as documented.
- **Pause/resume.** I couldn't find a way for points captured while paused to be stored. Native removes the location callback, `CapturePipeline` checks the sharing state before and after encrypting, uploads wait while a change is queued, and the server discards points with an obsolete revision prefix or an active pause. The default native state with no stored preference is "paused" (fails closed).
- **Key rotation.** Queued rows keep their epoch and upload as is. A deleted epoch comes back as `expired` and is dropped from the queue. See S6-07 for the forward-secrecy window.
- **Battery.** See S6-05. Wakelocks are only the HeadlessJsTaskService's, bounded at 60 s, plus WorkManager's. Alarms are `setAndAllowWhileIdle`, at most every 5 minutes, and only during a timed pause.
- **Manifest.** The capture service declares `foregroundServiceType="location"` and the `FOREGROUND_SERVICE_LOCATION` permission. Services aren't exported. The boot receiver is exported, as BOOT_COMPLETED requires, but it checks the action, and both actions are protected broadcasts that third-party apps can't send. POST_NOTIFICATIONS is declared and requested at launch on Android 13+. Notices check `areEnabled` and return "not shown" so they can be retried.
- **iOS.** Not supported for capture. See S6-02.
- **Permissions revoked mid-session.** Android kills the process. The sticky restart sees `!shouldRestoreCapture` and posts the "Location sharing stopped" notice once. The next app open stops capture through reconcile. Location toggled off in settings is not handled (S6-08).

## Refactor candidates

- **`lib/tracking.ts` (1,020 lines, about 12 module-level mutable variables).** `reconcileTrackingKeysInternal` is about 260 lines with two branches (`startCapture` true and false) that each repeat the pending check, sharing sync, backfill, reseal and key-check recording. Split it into a key reconciler, a queue uploader (`flushGroup` and `uploadClaimedItems`) and session lifecycle (revoke, sign-out, recovery). Keep the single-flight state in one small object per concern. Rough size: medium, 1 to 2 days, and the test file would need to be split to match.
- **`TrackingCaptureService.onStartCommand`.** Five action branches with overlapping "restore, park or stop" logic, and the rule about promoting before stopping applied inconsistently (S6-04). Lock usage is mixed (S6-12). An explicit lifecycle state (Stopped, Parked, Paused, Capturing) with one `promoteThen(stateChange)` helper would make it easier to reason about. Rough size: medium.
- **Duplicated identity and key helpers across TS and Kotlin.** The owner string `JSON.stringify([baseUrl, userId])` is built in both `tracking.ts:69` and `locationSharing.ts:113`. Kotlin then rebuilds a scope with `JSONArray(listOf(owner, deviceId))` and parses the revision prefix format (`s<a>.<d>:`) separately from the shared TS resolver. A shared constant or helper on each side, plus a cross-language test vector for the revision prefix ordering, would stop the two drifting apart. Rough size: small.
- **SharedPreferences names spread across Kotlin files.** `openbeacon_tracking_queue`, `openbeacon_tracking_sharing`, `openbeacon_tracking_capture` and `openbeacon_notices` are raw strings in TrackingRuntime and Notices. One small preferences object would help. Rough size: small.

## Patterns for the cross-cutting pass

- **Error handling.** TS mostly uses `tryCatch` and checks `getErrorCode(error) === "UNAUTHORIZED"` to escalate to a revoke. `getErrorCode` is a local helper in `tracking.ts`, not shared. `try/finally` is used for cleanup only (allowed). Kotlin catches `Exception`, `IllegalStateException` or `SecurityException` and logs with `Log.e`. Nothing reports to the user except Notices.
- **API responses.** The uploader relies on `{accepted, duplicates, discarded?, expired?, keyState?}` and treats missing optional fields as empty, which is compatible with older servers. Sharing changes return `{status: "applied" | "expired" | "superseded"}`.
- **Validation.** Stored local state (pending sharing changes, synced preferences) goes through superjson plus zod `safeParse`, and is dropped if invalid. Native bridge inputs are checked by Kotlin `require` and `throw IllegalArgumentException`. Queue items are filtered by algorithm and kind before upload.
- **Loading and error UI.** The sharing card has explicit "Checking…", "Couldn't check", "Pausing…" and offline-pending copy. Background failures are shown only through native Notices (compatibility, permission, signed out, sharing changed), which are suppressed while the app is active.
- **Timeouts and retries.** Every network call uses `timeoutLink` (20 s/30 s). Queue retry backoff is exponential, capped at 5 minutes, with no maximum attempt count. Sign-out flush is capped at 10 s, the headless task at 60 s and the resume worker's JS sync at 90 s. In-flight rows recover after 2 minutes. React Query retries 3 times except on 4xx and timeouts.
- **Logging.** Kotlin `Log.e`/`Log.w` with static messages and no coordinates or keys. The TS tracking code does no logging of its own; the tRPC logger link logs paths only.
- **Storage.** JS state lives in MMKV (`storage`), with keys namespaced by `JSON.stringify([baseUrl, userId, …])`. Native state lives in SharedPreferences (owner, sharing state, capture enabled, notice flags), in Keystore-wrapped AES-GCM SharedPreferences (epoch keys) and in Room (ciphertext queue). Per-account scoping uses the same owner string on both sides.
