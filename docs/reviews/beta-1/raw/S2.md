## Findings

### [S2-01] A session moved to a new phone survives removal of the stolen phone, which can then activate the new phone without the password

- Location: packages/api/src/lib/removeDevice.ts:61-69; packages/api/src/lib/groupEpochs.ts:634-639 (`upsertUserDevice` moves the session link); packages/api/src/router/deviceRouter.ts:103-182 (`activationChallenge`/`activate` need no fresh sign-in)
- Category: security
- Severity: high
- Launch: must-fix
- Confidence: high
- Evidence: Reproduced with a throwaway integration test (`packages/api/src/router/removedSessionMove.reviewtmp.test.ts`, deleted afterwards) against a throwaway integration database. Steps: the owner has phone P (session S0). A second phone D1 signs in (session S1), registers and activates with the History key. Using S1, a third device ID D2 is registered, so S1 now links to D2 (Pending). The owner calls `account.removeDevice(D1)` from S0. Output: `s1 after removing stolen phone: still exists`, then `activationChallenge` + `activate` on S1/D2 with the History private key returned `{"activated":true}` and D2 had `activatedAt` set and `revokedAt` null. `removeUserDevice` only deletes sessions whose `deviceId` is the removed device or that have no device at all, and registering a new device moves the session's link away from D1.
- Failure scenario: A phone is stolen while unlocked, or seized and rooted. The attacker copies its session token and History private key (stored in SecureStore on every phone that holds history) and, before the owner reacts, registers a new device ID from that session with their own client. The owner removes the stolen phone in Account › Devices, which per CONTEXT.md should mean "the server signs the device out, refuses its requests from then on". The attacker's session is still alive on the Pending D2. It activates D2 by answering the History-key challenge, with no password, no fresh sign-in and no email code. Every group is flagged for rotation, and the owner's and family's phones then wrap the next epoch keys to D2, so the attacker gets live locations again. D2 can use any name and icon, for example the same "Pixel 9" as the removed phone. The only signal is the optional new-sign-in email.
- Suggested fix: Treat Pending devices as untrusted at removal time. In `removeUserDevice`, also delete sessions linked to the account's Pending devices, or track the device a session was linked to before `registerDeviceKey` moved it and delete those sessions too. Also consider (a) refusing to move a session that is linked to a non-revoked device onto a newly registered device (make the phone sign in again), and (b) requiring a fresh sign-in for `device.activate`, as `accountRecovery.reset` already does. Add an integration test for this sequence.

### [S2-02] Google sign-in silently links Google to an existing password account

- Location: packages/auth/src/createAuth.ts:29-214 (no `account.accountLinking` option); better-auth `oauth2/link-account.mjs:136-193`
- Category: security
- Severity: medium
- Launch: post-beta (the fix is one config line, so it is worth doing before beta)
- Confidence: high
- Evidence: There is no `accountLinking` setting, so better-auth's default implicit linking applies: when a verified Google identity's email matches a user whose email is verified, it calls `linkAccount` and signs in. `databaseHooks.account.create.before` only blocks `credential` accounts. Reproduced with a throwaway test (`packages/auth/src/googleLink.reviewtmp.test.ts`, deleted) that signs up a password account through `createAuth` and passes a verified Google user info for the same email to better-auth's `handleOAuthUserInfo`. The result was a new session, and the account's providers became `["credential","google"]`. No existing test covers this.
- Failure scenario: This breaks the product rule that an account uses a password or Google, never both. Anyone who controls the address's inbox, even briefly (a compromised mailbox, or a Google account created for a non-Gmail address the attacker can verify), signs in with Google and attaches a second sign-in method. No security alert is sent for the link. The owner can't see it, because there is no account UI for it, and can't remove it, because `/unlink-account` is disabled. It survives the owner's password change, password reset and "sign out other sessions", so the attacker keeps a durable way back in. `deletionVerificationMethods`, the hasPassword logic in alert emails and the support advice all assume one method.
- Suggested fix: Set `account: { accountLinking: { enabled: false } }` (or `disableImplicitLinking: true`) in `createAuth`. The app then needs a clear error for "this email uses a password" (better-auth returns `account not linked`). Add an integration test. Decide what to do with accounts that already have both.

### [S2-03] Unexpected server errors return their internal message to the client

- Location: packages/api/src/trpc.ts:79-122 (errorFormatter keeps `shape.message` for INTERNAL_SERVER_ERROR)
- Category: security
- Severity: medium
- Launch: post-beta
- Confidence: high
- Evidence: Throwaway test (`packages/api/src/errorShape.reviewtmp.test.ts`, deleted) run with `NODE_ENV=production`, using `createTRPCComponents()` and `fetchRequestHandler`, with a procedure that throws `new Error("Invalid \`prisma.user.findUnique()\` invocation in /app/packages/api/src/x.ts:12:3 -> Can't reach database server at \`db:5432\`")`. The response was HTTP 500 with that exact message in `error.json.message`, and `isDev` was false. tRPC copies the cause's message onto the wrapped TRPCError, and the formatter only replaces the message for rate-limit errors.
- Failure scenario: Any unhandled Prisma error (constraint names, model and field names, query arguments, file paths, DB host), an S3/R2 SDK error (bucket, endpoint), `"SMTP could not send email (ECONNECTION)"` or `"Resend could not send email: ..."` from `accountRecovery.requestResetCode`, or `"Cannot identify group image for cleanup."` is shown to any caller, including anonymous callers of public procedures and failures inside `createTRPCContext`. This exposes internals on the hosted server and gives the app raw text where it expects user-facing copy.
- Suggested fix: In the errorFormatter, when `error.code === "INTERNAL_SERVER_ERROR"` and the cause isn't a `TRPCError` the code threw on purpose, replace `message` with a generic string. The `onError` hook already logs the location. Add a unit test that pins this.

### [S2-04] Password guessing has no per-account limit; only better-auth's implicit per-IP limiter applies

- Location: packages/auth/src/createAuth.ts:29-214 (no `rateLimit` option, no sign-in hook); better-auth `context/create-context.mjs:170-175`, `api/rate-limiter/index.mjs:305-318`
- Category: security
- Severity: medium
- Launch: post-beta
- Confidence: high
- Evidence: `/sign-in/email` and `/change-password` have no app-side attempt limit. better-auth's built-in limiter is on in production by default (`enabled: options.rateLimit?.enabled ?? isProduction`). It keys on the `x-openbeacon-client-ip` header (3 requests per 10 s per IP for `/sign-in*`, `/sign-up*` and `/change-password`, 100 per 10 s for other auth paths) and keeps counts in process memory. That is the only throttle on password attempts. By contrast, `account.requestDeletion` limits password checks to 5 per minute per user.
- Failure scenario: An attacker spreading guesses over many IPs gets unlimited online guesses against one account's password. Passwords only need 8 characters. Once the team removes IP-based limits as planned, there will be no throttle at all. The implicit better-auth limiter is also an IP limit the team may not know is on: everyone behind one NAT or one reverse proxy (self-hosters who leave `TRUSTED_PROXY_PROVIDER=none` behind nginx/Caddy) shares 3 sign-ins per 10 s, and the counts reset on restart and aren't shared across instances.
- Suggested fix: Add a per-account failed-attempt budget for `/sign-in/email` and `/change-password` in a better-auth `before`/`after` hook, keyed on the normalised email or user ID in the existing Redis `rateLimits` (as the email-code wrong-guess limit does). Prefer progressive delay over hard lockout to limit lockout abuse. Then set `rateLimit: { enabled: false }` (or a deliberate config) so the IP limiter isn't on implicitly.

### [S2-05] A session can create unlimited Pending devices, each sending a new-sign-in email

- Location: packages/api/src/router/authRouter.ts:28-52; packages/api/src/lib/groupEpochs.ts:615-657
- Category: security
- Severity: low
- Launch: post-beta
- Confidence: high
- Evidence: `registerDeviceKey` is a setup procedure limited to 120 calls per minute per user. Each call with a new `deviceId` creates a Pending `UserDevice` and calls `securityAlerts.send(..., { type: "new-sign-in" })`. There is no cap on Pending devices per account. The cleanup job removes them only after 7 days.
- Failure scenario: Anyone holding a session (including one with no device) can send up to 120 alert emails a minute to the owner and add thousands of rows to Devices. On the hosted server this burns the email quota and sending reputation, and it hides real new-sign-in alerts in noise.
- Suggested fix: Cap Pending devices per account (for example 3 to 5; refuse or replace the oldest), or coalesce new-sign-in alerts per account per time window.

### [S2-06] Unused better-auth endpoints are still enabled, including an open redirect

- Location: packages/auth/src/createAuth.ts:30-50
- Category: security
- Severity: low
- Launch: post-beta
- Confidence: high
- Evidence: Listed every `auth.api` endpoint against `disabledPaths` with a throwaway test (deleted). Still enabled and unused by the app, which uses Google id-token sign-in: `GET /expo-authorization-proxy`, `/callback/:id`, the redirect flow of `/sign-in/social`, `GET /list-accounts`, `POST /revoke-session`, `/error`, `/ok`. `/expo-authorization-proxy` (in @better-auth/expo `index.js:7-35`) redirects to any `https:` URL in `authorizationURL`. It is blocked today only because `apiCompatibility` returns 426 to a browser that doesn't send the level header.
- Failure scenario: If the compat gate is ever relaxed for GET (it already is for the Google deletion callback), `https://<server>/api/auth/expo-authorization-proxy?authorizationURL=https://phish.example` becomes an open redirect on the server's domain. The other routes add attack surface that no test pins.
- Suggested fix: Add these paths to `disabledPaths` (keep `/sign-in/social`, which the id-token flow uses) and extend the "routes the app doesn't use are switched off" test.

### [S2-07] Outbound calls inside requests have no timeout

- Location: packages/auth/src/googleDeletion.ts:40-60 (token exchange `fetch` and `verifyGoogleIdToken` JWKS fetch) used by packages/api/src/router/accountRouter.ts:242-248; packages/api/src/router/accountRecoveryRouter.ts:196-201 (awaits `emailCodes.send`, which for Resend calls `resend.emails.send` without a signal, packages/email/src/transport.ts:33)
- Category: bug
- Severity: low
- Launch: post-beta
- Confidence: high
- Evidence: Neither `fetch` has a `signal`/`AbortSignal.timeout`. The Resend SDK's `fetchRequest` passes only the caller's signal and sets no default timeout. SMTP has 8 s, 8 s and 30 s timeouts. Neither call holds a DB transaction or lock, so this stalls one request rather than the server.
- Failure scenario: Google's token endpoint or Resend hangs. `account.requestDeletion` with Google, or `accountRecovery.requestResetCode`, waits until the app's 30 s client timeout, and the server keeps the dangling promise. The user sees a generic timeout instead of "try again".
- Suggested fix: Pass `signal: AbortSignal.timeout(10_000)` to the Google token fetch, and wrap the Resend send in a timeout in `createEmailTransport` (S5 owns the transport).

### [S2-08] tRPC batches have no size limit

- Location: apps/backend/src/routes/trpc.ts:22-48
- Category: security
- Severity: low
- Launch: post-beta
- Confidence: medium
- Evidence: `fetchRequestHandler` is called without `maxBatchSize` (supported in @trpc/server 11.15). Measured with a throwaway Bun server script (`scratchpad/urllen.ts`): Bun accepts a 15,009-character path, which is about 1,000 `auth.providers` names, and returns 431 by 60,000 characters.
- Failure scenario: One HTTP request carries about 1,000 calls. Each runs the middleware chain and a Redis `consume`, and every call after the 60th is rejected one by one, so one request costs about 1,000 Redis round trips.
- Suggested fix: Set `maxBatchSize` to a little above the largest batch the app sends (for example 20 to 50).

- Location: apps/backend/package.json (hono 4.13.11); apps/backend/src/app.ts:8-17
- Category: security
- Severity: low
- Launch: post-beta
- Confidence: high
- Evidence: GHSA-4m76-xfj5-7975 concerns `mount()`/`app.mount()`, which the backend doesn't use (`app.route` and `basePath` only). ### [S2-10] A failed immediate account deletion is swallowed with no log

- Location: packages/api/src/router/accountRouter.ts:358-367
- Category: bug
- Severity: low
- Launch: post-beta
- Confidence: high
- Evidence: `await tryCatch(deleteAccountRecords(...))` ignores the result. If it fails (a race that turned the user into a sole owner, a storage-key error, a DB error), the procedure still returns `{ deletionDate }`. The account stays `pendingDeletion` with a past deadline, so sign-in is refused, and the runner retries later.
- Failure scenario: The operator sees nothing in the logs when an immediate deletion fails. If the failure is permanent, for example the "Cannot identify group image" error, the account sits undeleted until someone notices the runner's failures, while the user was told it was deleted.
- Suggested fix: Log a non-identifying line on failure (as the email paths do), and let the runner's retry be the documented fallback.

## Patterns for the cross-cutting pass

- **Gates:** `publicProcedure` (rate limit, then timing), `setupProcedure` (session required), `setupDeviceProcedure` (setup plus a linked device), `protectedProcedure` (linked and Active), `freshSessionProcedure` (session created in the last 30 min, based on `createdAt`, not better-auth's `updatedAt`). The setup list matches the doc and is pinned by `authentication.test.ts`. The device ID header is only trusted when it equals `Session.deviceId`; spoofing it gets nothing (wrong device leads to DEVICE_PENDING or UNVERIFIED, another account's device is ignored). One small quirk: an unauthenticated request naming any revoked device ID gets DEVICE_REMOVED.
- **Client IP:** the backend resolves it once in `index.ts`, overwrites `x-openbeacon-client-ip` on `/api/auth/*`, and passes it to tRPC through `c.env`. The tRPC path doesn't strip a client-sent `x-openbeacon-client-ip`, but nothing on that path reads it. Spoofing XFF only works with `trusted-proxy` or `cloudflare` when the origin is reachable directly, and only changes the rate-limit bucket. IP-keyed limits still in this section: `EMAIL_CODE_IP_LIMIT` (off by default), feedback `ipLimit: 3`, anonymous `publicProcedure` buckets, join endpoints (S3), and better-auth's implicit limiter (S2-04). Once IP limits go, anonymous `feedback.submit` and `auth.providers` have no key left to limit on.
- **Errors:** `TRPCError` with user-facing English messages, plus a `cause` class turned into `DEVICE_REMOVED`/`DEVICE_PENDING`/`DEVICE_UNVERIFIED` in `data.cause`. better-auth routes use `APIError` with string `code`s (`INVALID_CODE`, `INVALID_SIGN_UP_TOKEN`, `PASSWORD_NOT_ALLOWED`). Two shapes for one app. Internal messages leak (S2-03). Hono has no `onError`; its default 500 is generic.
- **Validation:** zod on every input; `z.object` (loose) everywhere in this section, never `strictObject`. String IDs are capped at 128.
- **Timeouts:** startup checks race a 10 s timeout. In-request outbound calls (Google, Resend) have none (S2-07). Every request awaits Redis for rate limiting with Bun `RedisClient` defaults (offline queue, reconnect), and the Prisma pg adapter is created without `connectionTimeoutMillis` or `statement_timeout` (S4 owns both). Bun's `idleTimeout: 60` is the only cap on a hung request.
- **Background work:** email-code sends run through better-auth `runInBackground`, so response time doesn't reveal whether the account exists. Security alerts are fire-and-forget with `tryCatch` and log only the alert type. `accountRecovery.requestResetCode` sends inline.
- **Locking:** User row (`FOR UPDATE` in the session hook, `FOR NO KEY UPDATE` elsewhere), then Groups (`lockUserGroups`, ordered by id). The order was consistent in every path I read. The email-code check uses `pg_try_advisory_xact_lock` and fails closed.
- **Accepted risks not filed:** the email-code wrong-guess lockout (10 per day per address; the user accepted it, and email links are the planned fix), and password-only Start fresh on email-less self-hosted servers (documented in the privacy draft's Recovery threats).
- **Logging:** prefixes such as `[email-code]`, `[security-alert]`, `[trpc]`, `[rate-limit]`, `[feedback]`. No emails or IDs are logged, except that feedback logs the feedback ID.
