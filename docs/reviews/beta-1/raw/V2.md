# V2: verification of S3-01, S3-02, S3-03, S3-05, S1-02

Commit 94a73b27. I ran two temporary integration tests against a throwaway integration database and deleted them from the repo afterwards. Copies are in the scratchpad: `<scratchpad>/v2leave.verifytmp.test.ts` and `<scratchpad>/v2delete.verifytmp.test.ts`. I wrote them from scratch rather than reusing the reviewer's test. They use a different setup (three members plus a later joiner) and check the honest owner's key resolution directly.

### S3-01: A member who leaves creates, and keeps, the group key used after they leave

- Verdict: CONFIRMED
- Severity: high (reviewer said high)
- Launch: must-fix
- Evidence:
  - `groupMembershipRouter.ts` `remove` (from line 212) always calls `persistGroupEpoch` with `input.nextEpoch` and `deviceId: ctx.deviceId`, including when `actor.id === input.memberId`. `persistGroupEpoch` (groupEpochs.ts:350) checks only that the creator device belongs to the caller, that the caller is still a member (the row is deleted afterwards, in the same transaction) and that the recipient set excludes `excludedUserId`. Nothing stops the departing user from creating the epoch.
  - On mobile, `buildRemoveGroupMemberInput` (groupEncryption.ts:135) is the only remove builder, and `MembersTab.tsx:125` also uses it for self-leave. An honest app throws the key away, but a modified one can keep it.
  - My test: owner O creates the group, A joins (epoch 2) and L joins (epoch 3). L leaves and submits epoch 4. O's honest path (`groupEpoch.getLatest`, then `getEpochKeyWraps`, then `unwrapEpochKey`) resolves epoch 4 to a key that is byte-for-byte the one L generated (`OWNER_RESOLVED_KEY_EQUALS_LEAVER_KEY true`). `rotationContext` returns null afterwards, so nothing rotates the key away. O's upload under epoch 4 is accepted. L rejoins with a shared code, polls from a null cursor and decrypts O's post-departure point (`REJOINED_LEAVER_DECRYPTS o-e4 {"latitude":51.5,"longitude":-0.1}`).
  - While L is out of the group, `poll` returns FORBIDDEN. Without rejoining, L needs the ciphertext from somewhere else (the operator, a DB leak or a backup).
  - This breaks the stated requirement in `docs/security/beta-1-privacy-draft.md` line 128: "Member removal must prevent the removed member from receiving future epoch keys". That isn't an accepted risk.
- Corrections:
  - The exposure ends at the next epoch change. A new join creates an epoch on the joiner's phone; in my test N's join made epoch 5, so L's key covers only the gap.
  - It needs a modified client. That doesn't lower the severity, because the threat is a hostile leaver (for example an estranged partner).
- Fix assessment:
  - The suggested fix is right, and the codebase already uses the same pattern. Device removal (`removeDevice.ts:71`), first-device registration (`groupEpochs.ts:642`), device activation and account deletion all set `epochRotationRequired = true`. A remaining member's phone then rotates through `rotationContext`/`rotate`, which `reconcile` calls for every group (`tracking.ts:245`, `:314`). The `keyState` hash on `uploadBatch` includes `rotationRequired`, so remaining phones notice on their next upload (about 60–120 s).
  - On self-removal: don't persist `input.nextEpoch`, delete the member, and set the flag. Keep the schema as it is so older apps keep working; they still send `nextEpoch` and the server ignores it. New apps must keep sending it while older servers require it. API compatibility: unchanged.
  - Remaining phones already keep encrypting under epoch N until their next reconcile in the admin-removal case. Lazy rotation adds only one rotate call on top of that lag.
  - Update `groupDeparture.integration.test.ts` and add a test that a self-leave leaves no epoch created by the leaver's device and sets the rotation flag.
  - Edge case to check: the last or only member leaving. The app uses `delete` with `onlyIfLastMember` there, but the server must not leave a flagged group with no members to rotate it. Deleting the group, or making it a no-op, is fine.

### S3-02: Tracking reads ignore when the reader joined, and uploads under superseded epochs are accepted indefinitely

- Verdict: CONFIRMED WITH CORRECTIONS
- Severity: medium (reviewer said medium)
- Launch: must-fix (read half only)
- Evidence:
  - `pollGroupTrackingPoints` (groupTracking.ts:233) filters by `groupId` and cursor only. `getLatestGroupTrackingPoints` (:285) returns each current device's latest row with no epoch filter. The wrap endpoints filter by `joinedEpochNumber` (groupEpochRouter.ts:162, 192, 256, 348), but the ciphertext endpoints don't.
  - My test: after L left, A uploaded under epoch 3 and the upload was accepted. A brand-new member N then polled from a null cursor and got both pre-join rows, with sender user, sender device and `createdAt` (`NEW_MEMBER_SEES_PREJOIN_ROWS o:e4:…,a:e3:…`). After rejoining, L decrypted A's post-departure epoch-3 point with the key L had kept (`REJOINED_LEAVER_DECRYPTS a-e3 {"latitude":52,"longitude":1}`).
- Corrections:
  - The upload half is not a new finding. It is a documented owner decision: `beta-1-privacy-draft.md` line 128 ("Remaining active devices may upload queued ciphertext encrypted under older epochs. A removed person who retained an old key can decrypt such ciphertext if they obtain it.") and line 137 ("The owner chose to retain old-epoch uploads … accepting the confidentiality limitation after removal"). Don't fix it before beta. At most, add the test that documents the trade-off.
  - The read half isn't accepted anywhere. The docs promise only that new members get no pre-join keys (line 144). It is the channel through which a re-admitted member actually gets the ciphertext that S3-01 and the accepted old-epoch risk expose. It also gives any new member up to 60 days of pre-join activity metadata: who uploaded, from which device, when, and how often.
- Fix assessment:
  - Filter `poll` and `getLatest` by `GroupEpoch.epochNumber >= ctx.groupMember.joinedEpochNumber`. The epoch filter is what makes this correct.
  - Clamping a null or older cursor to the join epoch's `createdAt` is only an optimisation, so `poll` doesn't scan 60 days of filtered rows. Do both.
  - In `getLatest`, put the epoch filter inside the LATERAL subquery, so each device returns its latest readable point and not nothing.
  - This is safe for honest apps. A new or rejoined member can never decrypt rows under earlier epochs: there are no wraps for them, and history wraps are already limited by `joinedEpochNumber`.
  - Server-only. API compatibility: unchanged. This filter alone also stops the rejoin route for S3-01's epoch N+1, because the rejoin creates N+2 and sets `joinedEpochNumber` to N+2. It doesn't stop the operator or DB-leak routes, so S3-01 still needs its own fix.

### S3-03: Any signed-in user can write about 100 MB of ciphertext a minute, with no quota

- Verdict: CONFIRMED
- Severity: high (reviewer said high)
- Launch: must-fix
- Evidence:
  - The schema allows `ciphertext` up to 4096 characters and 100 points per batch (`packages/schemas/src/schemas/group/tracking.ts`).
  - `uploadBatch` has `rateLimit 240/60s`. `rateLimitMiddleware.ts` keys it on userId plus procedure path, so the limit is per account, not per group, and creating many groups doesn't multiply it.
  - A full batch is about 435 KB, well under Bun's `maxRequestBodySize` of 8 MB (`apps/backend/src/index.ts:69`). The only per-point checks are a known device, a known epoch, and a `clientPointId` prefix that the attacker controls.
  - The real Kotlin payload (`GroupPayloadEncrypt.kt:74`) is a JSON object of about 170 characters at most: v, latitude, longitude, ISO timestamp, speed and battery. With the 16-byte tag that's about 250 base64 characters, so the 4096 cap is about 16× real usage.
  - Random ciphertext defeats Postgres TOAST compression, so about 100 MB/min per account is realistic.
  - Additional accounts are limited only by email verification, when email is configured. Self-hosts without email have no limit at all.
- Corrections: none of substance.
- Fix assessment:
  - The per-account options are right and don't need IP limits:
    1. Lower `ciphertext.max` to about 1024. That leaves room for new payload fields and cuts the volume by 4×. Real queued items are about 250 characters, so no client has items that would be rejected and stuck in its queue.
    2. Add a cost-based limit like `groupInvites.send.recipients`, keyed per user or per device with `cost: points.length`. The app handles TOO_MANY_REQUESTS by requeueing (`tracking.ts`, `requeueCiphertexts`), so data isn't lost. Set the limit high enough that a backlog flush after a day offline still drains in minutes.
    3. Add a per-account daily point budget. The rate limit bounds the throughput, but only a budget bounds the 60-day storage. Remember that one location is uploaded once per group, so scale the budget by the account's group count.
  - Sybil accounts remain a residual risk. Add a storage or row-growth alert per account so the operator can act.
  - Narrowing the schema is server validation that every shipped client already satisfies. API compatibility: unchanged.

### S3-05: Group deletion calls storage with no timeout while it holds the group lock

- Verdict: CONFIRMED WITH CORRECTIONS
- Severity: medium (reviewer said medium)
- Launch: post-beta. The `s3Client` timeout is a small change and worth doing before beta anyway.
- Evidence:
  - `groupLifecycleRouter.ts` `delete` takes `Group FOR UPDATE` and then awaits `deleteFile` (ListObjectVersions plus DeleteObjects) for pending uploads and the current image, inside a 15 s transaction.
  - `s3Client` (s3client.ts) sets no request handler. The installed `@smithy/node-http-handler` 4.14.2 defaults `requestTimeout` to 0, and there is no default socket timeout unless one is configured. `deleteImageVersions` is at storage.ts:57-110, not 219-287.
  - Group delete is the only place where storage is called inside a transaction. `setPendingImageUploadForUser` and `confirmGroupImageUpload` call storage outside theirs.
  - My test mocked `deleteFile` to take 17 s:
    - A member's `uploadBatch` that started 0.5 s later was blocked for 14.6 s on `Group FOR SHARE`. It then failed with "A query cannot be executed on an expired transaction" (its own 5 s transaction had already expired, but the query kept waiting for the lock) and returned a 500.
    - The delete failed at 17 s, and the group still existed.
- Corrections:
  - The lock is held for at most 15 s, because Prisma rolls back the transaction at its timeout. The stall is bounded and affects only the group being deleted.
  - Each blocked request holds a pg connection for the whole window, not just 5 s. The pg pool is the `pg.Pool` default of 10, set by `PrismaPg({ connectionString })`. A large group could therefore briefly use up much of the shared pool, but this needs storage to be slow, which a user can't cause.
  - The "inconsistent state" is recoverable. If the image is deleted and the transaction then rolls back, the group shows a broken image. A retried delete succeeds, because `deleteImageVersions` on a key with no versions sends a plain `DeleteObject`, which S3 accepts for a missing key. The outcome is a broken avatar until the retry, not stuck data.
  - Outside transactions, a black-holed HEAD in confirm hangs only that request, until Bun's 60 s `idleTimeout` closes it.
- Fix assessment:
  - Give `s3Client` a `NodeHttpHandler` with `connectionTimeout` and `requestTimeout` (a few seconds), or pass an `abortSignal` on every send. A shared client config is simpler and covers scheduled jobs too.
  - For delete, do the DB deletion first and queue the image keys for the cleanup job, as account deletion already does. Alternatively, delete storage objects before taking the lock and re-check them inside it.
  - No API, format or migration impact, unless a cleanup-queue table is added; that needs a migration.

### S1-02: The client accepts any "latest" epoch, and epoch numbers aren't bound to the key

- Verdict: CONFIRMED WITH CORRECTIONS
- Severity: low (reviewer said medium)
- Launch: post-beta (fold into OPE-213)
- Evidence:
  - `reconcile` (tracking.ts:315-409) takes `getLatest().epochId` and uses `observedGroupEpochs` only to fire `notifyGroupEpochChange`. Nothing stores or compares epoch numbers.
  - `getWrapInfo` (encryption index.ts:64) binds only `epochId` and `recipientDeviceId`. The payload AAD binds `groupId` and `epochId`, but not `epochNumber`.
  - With an honest server no rollback is possible. `getLatest` is authoritative, and `persistGroupEpoch` requires `epochNumber === latest + 1`.
- Corrections:
  - The attack needs a malicious server (or a TLS MITM). In that case it adds nothing beyond the risk accepted for Beta 1 (`beta-1-data-flow-review.md` line 8, `beta-1-privacy-draft.md` lines 9 and 85: the server-supplied device key directory is trusted until OPE-213). The server supplies the recipient list for every new epoch, and `createEpochBundle` (groupEncryption.ts:18) wraps to whatever devices it is given. A malicious server can therefore add the removed member's device to epoch N+1 directly, with no rollback needed.
  - The suggested monotonicity check alone also wouldn't close the rollback. `reconcile` keeps the old provisioned key whenever the newest epoch's key can't be resolved: on an error or a missing wrap, the group goes into `preserveGroupIds` and its current keys are kept (tracking.ts, around lines 330-372). A server that returns the new epoch but withholds that device's wrap freezes the phone on the old epoch without any rollback.
  - The same applies across groups. The wrap doesn't bind `groupId`, so a malicious server could serve another group's epoch wrap. That too is inside the accepted directory-trust risk.
- Fix assessment:
  - The fix is reasonable but belongs with OPE-213: a signed directory plus wrap info v2 binding `groupId` and `epochNumber`.
  - If it's done:
    - Store the highest `(epochNumber, epochId)` per group in MMKV and refuse to go lower.
    - When the server reports a newer epoch whose wrap can't be resolved, fail closed after a bounded time instead of preserving the old key indefinitely. Otherwise the freeze variant above stays open.
  - Changing the wrap info is an encrypted-format change. Unwrapping happens only in JS; Kotlin receives provisioned keys. So it needs a new `WRAPPED_EPOCH_KEY_ALGORITHM` value or a version field, with dual support until 60-day epoch expiry. That would be a little cheaper before beta, but not enough to justify doing it ahead of OPE-213.
  - Add rollback and freeze to the threat list in the privacy draft now. It's documentation only.

## How S3-01, S3-02 and S1-02 interact

- They all come down to one property: after someone leaves, location data must only be encrypted under keys that the remaining members created and that only they received. Each finding breaks it in a different way:
  - S3-01: the leaver creates the next key.
  - S3-02: the server hands the resulting ciphertext back to a re-admitted leaver. It also hands out old-epoch ciphertext (accepted risk) and pre-join metadata.
  - S1-02: a malicious server can steer phones back to, or keep them on, a key the leaver knows.
- No single fix covers all three:
  - **S3-01 fix (server-only):** ignore the leaver's `nextEpoch` and flag the group for rotation. This removes the leaver's knowledge of any post-departure epoch, against every adversary: rejoin, DB leak and operator. It is necessary, and nothing else replaces it.
  - **S3-02 read filter (server-only):** blocks the one route an ordinary leaver has to the ciphertext. That route is re-admission, which needs an admin to let them back in. It covers both S3-01's epoch N+1 and the accepted old-epoch uploads, but does nothing against the operator or a DB leak.
  - **S1-02 (client, OPE-213):** concerns only a malicious server, which can already defeat S3-01's fix by adding the leaver's device to the recipient set, an accepted Beta 1 risk. Monotonicity and fail-closed handling only matter once the directory is authenticated.
- Recommendation for beta: ship the S3-01 and S3-02 (read) fixes together as one server-only change, with API compatibility unchanged. Leave the accepted old-epoch upload behaviour as it is, and defer S1-02 to OPE-213 with a note in the threat list.
