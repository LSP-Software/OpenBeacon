## Findings

### [S9-01] Group screen state carries over from one group to the next (unsaved rename can hit the wrong group)

- Location: apps/mobile/app/(tabs)/groups/[groupId]/index.tsx:53-57; apps/mobile/app/(tabs)/groups/[groupId]/SettingsTab.tsx:282,302-317; apps/mobile/app/(tabs)/groups/[groupId]/MembersTab.tsx:39-52
- Category: bug
- Severity: medium
- Launch: post-beta
- Confidence: medium
- Evidence: `routes.cjs` shows `groups/[groupId]/index` is a route in the `(tabs)` bottom-tab navigator, not in a stack. React Navigation 7 tabs stay mounted, and navigating to a tab route that already exists updates its params on the same instance. Nothing is keyed by `groupId`: not `GroupScreen`, not `SwipeTabs`, not `SettingsTab`. So `value` (selected tab), `historyWarningDismissedFrom`, SettingsTab's `name` and MembersTab's dialog state all survive a change of `groupId`. Only `verifyFailedFor` is keyed by group.
- Failure scenario: An admin opens group A and goes to Settings. They type "Grandparents" in the rename box, don't save, and go back. Then they open group B. The screen opens on Settings, the field still says "Grandparents", and the placeholder now shows B's name. "Save name" renames group B. Separately, dismissing the history warning for group A can hide group B's warning, because the in-memory dismissal time takes priority over B's stored value.
- Suggested fix: Render the group body with `key={groupId}`. A simple way is to split `GroupScreen` into a wrapper that reads params and an inner component keyed by `groupId`. Moving group detail into a stack (see S9-02) also fixes it.

### [S9-02] MembersTab, SettingsTab and HistoryTab are routable screens

- Location: apps/mobile/app/(tabs)/groups/[groupId]/MembersTab.tsx, SettingsTab.tsx, HistoryTab.tsx; apps/mobile/app/+native-intent.tsx:4-7
- Category: bug
- Severity: low
- Launch: post-beta
- Confidence: high
- Evidence: Expo-router treats every file under `app/` as a route. `routes.cjs` prints `groups/[groupId]/SettingsTab`, `groups/[groupId]/HistoryTab` and `groups/[groupId]/MembersTab` as tab routes. `redirectSystemPath` passes every incoming path through unchanged.
- Failure scenario: The link `openbeacon://groups/<id>/SettingsTab` (or a mistyped internal link) renders `SettingsTab` with `groupId` undefined. The screen has no back button and no group. MembersTab fires `listMemberDevices({ groupId: undefined })`, which the server rejects. It also gives a confusing route tree to anyone adding screens later.
- Suggested fix: Move the three tab components to `components/groups/`, or anywhere outside `app/`, and import them from there.

### [S9-03] Groups list shows "No groups yet" when loading fails; group page "Try again" can do nothing

- Location: apps/mobile/app/(tabs)/groups/list.tsx:28-55,245-286; apps/mobile/app/(tabs)/groups/[groupId]/index.tsx:85-127; apps/mobile/hooks/useCachedGroup.ts:4-19
- Category: UX
- Severity: medium
- Launch: post-beta
- Confidence: high
- Evidence: list.tsx only checks `isPending`. A failed query has `status: "error"` and `isPending: false`, and there is no query persistence (`lib/api.ts`). So `groupList ?? []` renders the empty state, which offers "Create a Group" and says "Groups keep your family connected…". `OfflineBanner` only covers loss of device connectivity, not a server that is down or a self-hosted server that can't be reached. On the group page, when the list query has errored with no data, `isMissing` is false. The page then shows "Group not found" + "Try again", and the button only bumps `verifyAttempt`, which feeds an effect that returns early when `!isMissing`.
- Failure scenario: The server is down, or a self-hoster's box is offline, while the phone has internet. A user with three groups opens the app and is told they have no groups and should create one. Some will create a duplicate group. If they reach a group page by deep link, "Try again" does nothing and the copy says "not found" when the real problem is the network.
- Suggested fix: Add an error state to list.tsx ("Couldn't load your groups" + Retry → `refetch()`), shown when `isError && !data`. On the group page, tell "failed to load" apart from "not a member": the retry should call `refetch()` on the list query, and the copy should say the group couldn't be loaded.

### [S9-04] Remove member and Leave group can be submitted twice while the new epoch is being built

- Location: apps/mobile/app/(tabs)/groups/[groupId]/MembersTab.tsx:115-149,380-389; apps/mobile/lib/groupEncryption.ts:51-67,135-159
- Category: bug
- Severity: medium
- Launch: post-beta
- Confidence: high
- Evidence: The button is disabled with `removeMember.isPending || deleteGroup.isPending`. `submitEpochChange` first awaits `build()`, which runs `ensureDeviceKeyRegistration()`, a `removalContext` query and key wrapping, and only then calls `mutateAsync`. While the build runs, nothing is pending: no spinner, and the buttons stay enabled. Create group, accept invite and join all use `useSingleFlight` for exactly this reason. Remove and leave don't.
- Failure scenario: An owner taps Remove on Alice and confirms. On a slow network nothing visible happens for a second or two, so they tap Remove again (or remove Bob). Two epoch builds start from the same `latestEpoch`. The second submission fails with "Unable to update group" (stale epoch or member not found), or a second leave runs after the screen has already navigated away.
- Suggested fix: Wrap `confirmRemoval`'s onPress in `useSingleFlight` keyed by member id. Disable the remove/leave buttons and show `loading` on the pressed one while the flight is pending.

### [S9-05] Theme text colours fail contrast: `text-muted` in dark mode, `text-muted-foreground` in light mode

- Location: apps/mobile/global.css:13-14,54-55; 38 uses of `text-muted` (e.g. MembersTab.tsx:431-477, TabBar.tsx:72, ui/Card.tsx:52 `CardDescription`, list.tsx:255, account/overview.tsx:471, signIn/signUp/forgotPassword/serverUrl/index, map sheets); 142 uses of `text-muted-foreground`
- Category: UX
- Severity: medium
- Launch: post-beta
- Confidence: high
- Evidence: `contrast.py` on the tokens. Dark: `--muted` (259 20% 31%) on background is 2.05:1, on card 1.94:1. Light: `--muted-foreground` (0 0% 63.9%, the same grey in both themes) on background is 2.24:1, on card 2.52:1. WCAG AA needs 4.5:1 for body text. `--text-secondary` passes (5.2 light, 4.0–4.3 dark).
- Failure scenario: In dark mode, the member card's "Location updated 3 min ago", "Battery unavailable", inactive tab-bar labels and every `CardDescription` (e.g. "3 members") come out dark purple on near-black. In light mode, every `text-muted-foreground` description (dialog descriptions, settings section labels, field descriptions) is light grey on lavender. Both are hard to read outdoors or with low vision.
- Suggested fix: In dark mode, raise `--muted` to about 65–70% lightness, or stop using `muted` as a text colour. Give `--muted-foreground` a light-mode value of about 40–45% lightness. Pick one "secondary text" token and use it everywhere: today `text-muted`, `text-muted-foreground` and `text-secondary` are mixed with no clear rule.

### [S9-06] Image upload PUT has no timeout; the avatar spinner can stay forever

- Location: apps/mobile/lib/image-upload.ts:18-34; apps/mobile/components/image/EditableImage.tsx:97-134
- Category: bug
- Severity: medium
- Launch: post-beta
- Confidence: medium
- Evidence: tRPC calls go through `timeoutLink`, but `uploadToPresignedUrl` is a bare `fetch` with no `AbortSignal`. React Native's Android OkHttp client sets no connect, read or write timeout. `EditableImage` keeps `isUploading` true, and the edit button disabled, until the promise settles.
- Failure scenario: The phone moves into a dead zone during the PUT, or a self-hosted S3/MinIO stops answering. The group or profile avatar shows a spinner with the edit button disabled until the app restarts, and no error ever appears. The presigned URL expires after 5 minutes anyway, so waiting longer can't succeed.
- Suggested fix: Pass `AbortSignal.timeout(60_000)`, or a value under the 5-minute presign lifetime, to the fetch, and map an abort to "Upload timed out. Try again."

### [S9-07] Invite dialog content can't scroll; many email rows push "Send invitation" off-screen

- Location: apps/mobile/components/dialogs/InviteMemberToGroupDialog.tsx:37-67,129-170; apps/mobile/components/ui/Dialog.tsx:46-83
- Category: UX
- Severity: low
- Launch: post-beta
- Confidence: medium
- Evidence: `DialogContent` is a plain centred `View` with no max height and no ScrollView. The invite form allows up to 50 rows (`inviteMemberToGroupSchema.max(50)`), each 48 dp, plus the tabs, the explanation and the role text. `AlertHost` already works around this for alerts (`maxHeight: height - 32` + ScrollView), but the invite dialog does not.
- Failure scenario: An owner adds 6–8 emails on a small phone, or 3–4 with the keyboard open. The top and bottom of the dialog are clipped, and "Send invitations" can't be reached without deleting rows.
- Suggested fix: Give `DialogContent` an optional `scroll` mode, as `AlertHost` does, and use it for the invite dialog. Or cap the visible email list in a ScrollView.

### [S9-08] Pull-to-refresh refetches the entire query cache

- Location: apps/mobile/components/RefreshablePage.tsx:7-11
- Category: design
- Severity: low
- Launch: post-beta
- Confidence: high
- Evidence: `queryClient.refetchQueries()` with no filter refetches every query in the cache that isn't disabled, active or not (TanStack v5 `findAll` defaults to `type: "all"`). That includes queries for other screens with `subscribed: false`, `listMemberDevices` for every group visited, recovery status, devices and personal nicknames, which are decrypted again. The spinner waits for the slowest request, and failures are swallowed with no feedback.
- Failure scenario: A user pulls to refresh on the groups list after visiting five groups. The app fires a dozen or more requests and decrypts nickname payloads again, on a battery-sensitive app that has deliberately cut its request count (see OPE-281/285). If the server is down, the spinner stops and nothing tells the user it failed.
- Suggested fix: Pass `{ type: "active" }`, or have each page pass its own query keys. Show an inline error or toast when any of those refetches fail.

### [S9-09] Owner who leaves must always pick a successor, even when another owner exists

- Location: apps/mobile/app/(tabs)/groups/[groupId]/MembersTab.tsx:96-102
- Category: UX
- Severity: low
- Launch: post-beta
- Confidence: high
- Evidence: The successor dialog opens whenever `isSelf && role === "OWNER" && !isLastMember`. The server (`groupMembershipRouter.remove`) treats `successorMemberId` as optional and relies on `removeGroupMemberWithOwnerGuard`, so a co-owned group needs no successor. `docs/groups/permissions.md` says "Leave the group: Yes, with an owner remaining".
- Failure scenario: A group has two owners. One leaves and is forced to pick a "new owner". If they pick a plain member, that member gets promoted to owner for no reason. The Continue button won't proceed until they choose.
- Suggested fix: Skip the successor dialog when another member already has role `OWNER`.

### [S9-15] Join code is a 32-character hex string with no grouping, and the share link only works on the default server

### [S9-17] `ui/Input` spreads the RHF `field` (including `onChange`) onto TextInput

- Location: apps/mobile/components/ui/Input.tsx:35-38; components/formInputs/FormSelectInput.tsx:65-73
- Category: design
- Severity: low
- Launch: post-beta
- Confidence: medium
- Evidence: `{...field}` passes RHF's `onChange` to RN `TextInput`. RN calls `onChange(event)` and then `onChangeText(text)` (TextInput.js:499-502). RHF's `getEventValue` turns the RN event into `event.target.value`, which is `undefined`, so every keystroke writes `undefined` and then the text, and runs validation twice under `mode: "all"`. FormSelectInput types itself as `TextInputProps`, spreads those props onto `Select`, and falls back to the sentinel `"N/A"` when the value is cleared.
- Failure scenario: Today the final value is correct because React batches the two updates. But any `watch`/`useWatch` subscriber or async resolver sees a transient `undefined`, which makes field-level side effects flaky and hard to debug.
- Suggested fix: Pass only `value`, `onBlur` and `ref` from `field` (not `onChange`). Give FormSelectInput its own props type, and have it use `undefined` rather than "N/A".

## Patterns for the cross-cutting pass

- **Error handling**: Mutations use `tryCatch(mutateAsync(...))` and report failures through the custom `Alert.alert` (lib/alert.ts, a queue rendered by `AlertHost` as a Dialog). Messages are usually `result.error.message` straight from the server; SharedInvite drops it. Form validation errors are inline via `FieldError` under `ui/Input`. Query errors are mostly not handled in group screens (S9-03). Some account/setup screens do have inline "Try again" states (devices, recovery, setup/name, setup/link). There are no toasts.
- **Double-submit**: `useSingleFlight` is used for create group, accept invite and join. Elsewhere `mutation.isPending` disables the button, which misses async work done before `mutateAsync` (S9-04). Button `loading` gives a spinner and disables the button.
- **Destructive confirmation**: Always through `Alert.alert` with a `destructive` button (delete group, remove/leave, role change). Destructive button colours vary (S9-11).
- **Loading UI**: Full-screen `LoadingIndicator` for first loads (including inside a tab: MembersTab), button spinners for mutations, a plain "Loading..." string in join. No skeletons. Pull-to-refresh only on the groups list and group detail (`RefreshablePage`, which refetches everything, S9-08). Other screens rely on `useRefetchWhileFocused` and focus refetch.
- **Empty states**: Groups list has a designed empty state. Members can't be empty. History is a placeholder.
- **Timeouts/retries**: tRPC goes through `timeoutLink` with a custom retry predicate (lib/api.ts). Direct `fetch` for image upload has no timeout (S9-06). `submitEpochChange` retries once on `HISTORY_RECIPIENT_MISMATCH`.
- **Optimistic updates**: None that need rollback. Cache writes (`setQueryData`) happen only after the server succeeds (create group, accept invite, group image), followed by `invalidateQueries`.
- **Authorisation in UI**: Matches `docs/groups/permissions.md`: invite for owner/admin, admin invites for owner only, rename and image for owner/admin, delete for owner, role changes for owner, admins can remove only members. Only S9-09 deviates.
- **Storage**: MMKV (`storage`) for dismissed banners, keyed by user and group. Hidden map groups go through `lib/hiddenMapGroups`. Images are unencrypted, with random-UUID object keys, by accepted Beta 1 decision.
- **Logging**: `console.error(error)` in `uploadImageFromUri`. No other logging in scope.
- **Accessibility**: Most custom Pressables set role and state (radio, tab, checkbox). Gaps are icon-only buttons, the tab bar and touch-target sizes (S9-10). Contrast tokens fail (S9-05).
