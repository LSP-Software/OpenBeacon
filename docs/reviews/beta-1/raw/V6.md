### S1-01: Wrap sender keys come from the server response, so HPKE auth mode doesn't authenticate the epoch key, and History wraps accept any sender

- Verdict: CONFIRMED WITH CORRECTIONS
- Severity: medium (reviewer said medium). It is a known, explicitly accepted Beta 1 risk, and the impact is wider than the reviewer described (see Corrections).
- Launch: post-beta for the code. Before beta, correct the docs and the OPE-213 scope (see Fix assessment).
- Evidence:
  - `unwrapEpochKey` (packages/encryption/src/index.ts:212-241) passes `wrappedEpochKey.senderPublicKey` to `openAuth`, and `unwrapHistoryEpochKey` (recovery.ts:200-234) does the same. Neither takes an expected sender. `epochKeys.ts:19-74` spreads the server's wrap objects straight into these calls. No mobile caller reads `createdByDeviceId` or compares a sender key with `listRecipientPublicKeys` (I grepped `apps/mobile/lib`, `hooks` and `app`).
  - The server's Device wrap sender is `GroupEpoch.senderPublicKey` (groupEpochRouter.ts:44). Each History wrap returns its own stored `senderPublicKey` (groupEpochRouter.ts:18, 47-52). That is the creator device for wraps made at epoch creation (groupEpochs.ts:445, 523) and the user's own device for Backfill (groupEpochRouter.ts:330-334, 360-368). An honest server enforces both. Nothing on the client does.
  - Repro 1: a "server" key pair wraps a key it chose as the Device wrap for the latest epoch. `resolveEpochKey`, the function `tracking.ts:368` uses to provision the upload key, returns it. A point the victim encrypts under the returned key then decrypts with the server's key. **So the server can read live locations from now on, not only forge them.**
  - Repro 2: for a History-only epoch (a restored phone), a History wrap from an unknown sender resolves. A point sealed under that key as `senderDeviceId: "dev_mum"` passes `decryptGroupPayload` with matching metadata.
- Corrections:
  1. **The reviewer's claim that "signing the directory under OPE-213 won't stop it, because no caller compares" is wrong about the plan.** OPE-213 names this attack ("Forge a sender. It can wrap an epoch key of its choosing with its own key pair and report that key as the epoch's creator") as accepted for Beta 1. Its scope item 3 already requires "When unwrapping, a phone only accepts a wrapped key if its `senderPublicKey` belongs to such a device". The finding is right about the code as it stands. It isn't a gap OPE-213 overlooks.
  2. What is new, or under-specified, in OPE-213:
     - History wraps aren't mentioned. Their valid senders differ: the epoch's creator device, or one of the reader's own account's devices (Backfill). Checking only "a device signed by some pinned identity" would still let any verified member's device be the sender.
     - Its agent notes list stale call sites (`groupEpoch.getWrappedKey`, `groupKeyAccess.ts`). The real ones are `apps/mobile/lib/epochKeys.ts` (`unwrapDeviceWrap`, `unwrapEpochKeyFromWraps`), which reach `tracking.ts`, `mapTrackingDecrypt.ts`, `hooks/useGroupKeyAccess.ts` and `lib/recovery.ts:189`.
     - Verifying old epochs needs the keys of devices that have since been revoked or deleted. `listRecipientPublicKeys` returns only active, non-revoked devices, and account deletion removes device rows.
  3. Impact is wider than the reviewer described. Forged Device wraps for the latest epoch get provisioned to native capture, so the attack breaks confidentiality as well as integrity. That makes it the same strength as the directory-injection attack the docs already accept, with the same detectability today. Both are "actively malicious backend", which privacy-draft line 9 places outside the Beta 1 threat model.
  4. Privacy-draft line 43 isn't false for Device wraps: the client does use the key "the backend records as the epoch's creator". But two things are wrong. It ties the guarantee to "as far as the device key directory is trusted", when the check never touches the directory; it trusts a separate per-epoch field. And it says nothing about History wraps. It should be reworded rather than called a false claim.
- Severity reasoning: against the product's core promise, "the hosted operator learns nothing and can't tamper undetectably", this is a total break. A malicious hosted backend can silently get every phone to upload under a key it chose. But that equals the risk the owner has already accepted in writing (privacy draft line 9, data-flow review row 8, OPE-213). A code fix before OPE-213 can't close it, because any "expected sender" today would come from the same untrusted server. So medium, as a documentation and design-gap finding, is right. It would be critical if Beta 1 marketing or in-app text promised protection against a malicious operator. The in-app "Location data is encrypted end-to-end" (groups/list.tsx:278) and the README's "people running servers are not in…" wording should be checked against line 9 before beta.
- Fix assessment:
  - **No encrypted-format change is needed.** HPKE auth mode already binds the sender public key into the key schedule. The gap is only where the client gets the expected key from. Adding sender identity to `info` or AAD gives nothing on top of auth mode while the directory is server-supplied. Binding `groupId` and `epochNumber` into the Device wrap info is S1-02's concern, not this one's.
  - The API changes needed for OPE-213 are additive and don't raise the compatibility level:
    - return `createdByDeviceId` with `deviceWrap` in `getEpochKeyWraps` and `listEpochKeyWraps`, and the already-stored `GroupEpochHistoryWrap.senderDeviceId` with each History wrap;
    - add a directory read that includes revoked devices' keys.
  - Old wraps are not frozen. Epochs replaced more than 60 days ago are deleted, and the server can set `epochRotationRequired` on every group to force fresh epochs. So beta data doesn't lock in the current behaviour.
  - Minimal pre-beta work, docs and tickets only:
    - (a) reword privacy-draft line 43 to say the sender key comes from the backend's epoch and wrap records, isn't compared with the directory, and that History wraps accept the creator's key or any of the account's own device keys as the backend reports them;
    - (b) say plainly near line 9 that an actively malicious backend can make phones accept a key it chose and so read and forge locations, not only by substituting directory keys;
    - (c) update OPE-213 with the History-wrap sender rule, the real call sites and historical-key lookup.
  - The reviewer's suggested API change (an explicit `expectedSenderPublicKey` parameter on both unwrap functions) is right and cheap, but it is only worth anything once OPE-213 exists. It can ship with OPE-213.

### S1-03: Nothing checks that all wraps of an epoch hold the same key, so a malicious member can quietly break other members' live view or history

- Verdict: CONFIRMED
- Severity: medium (reviewer said medium)
- Launch: post-beta
- Evidence:
  - `createEpochBundle` (apps/mobile/lib/groupEncryption.ts:20-51) wraps a single key in honest clients. `persistGroupEpoch` (groupEpochs.ts:429-528) can only check algorithm, epochId, sender key, recipient sets and ephemeral keys. It can't compare plaintexts, and no commitment field exists anywhere in the schema or the bundle schema.
  - Repro 3: the creator puts K1 in a member's Device wrap and K2 in their History wrap, both sealed with the real creator key. `unwrapEpochKeyFromWraps` returns K1 on the live phone and K2 on a restored phone with no Device wrap. Both count as readable. A point under K1 fails to decrypt with K2. The existing test "prefers the device wrap when a history wrap also exists" (epochKeys.test.ts) already uses two different keys and passes, so the code is written to tolerate a mismatch.
  - `useGroupKeyAccess.ts:95-104` caches any epoch whose wraps open as resolvable. `listHistoryBackfill` skips epochs that already have a wrap for the current History key version (`historyWraps: { none: … }`), and `addHistoryWraps` uses `skipDuplicates`. So an Enrolled device that holds the correct key through its Device wrap can never replace the bad History wrap.
  - Reachability: any member can make themselves the creator at will, by joining, or by adding or removing their own device so that `epochRotationRequired` is set and their phone rotates. It needs a modified client.
- Corrections: "the app still reports the history as complete" is accurate for the key-access count. The map would show the points as undecryptable rather than hiding the problem completely, so the loss isn't entirely silent to an attentive user. The confidence level understates it: I reproduced this, so it is high, not medium.
- Severity reasoning: under the brief, "exploitable by a group member" usually means high. But the attacker already sees everything the group shares and gains nothing confidential. The harm is denial of availability: lost history on restore, and a split live view until the next rotation. Points are kept for only 60 days, and other members can see something is wrong. Medium stands.
- Fix assessment:
  - The reviewer's commitment approach is right. Make it `HMAC-SHA256(epochKey, JSON array ["openbeacon.epoch-commit.v1", groupId, epochId])`, using the newer array convention and binding `groupId`. Send it in the epoch bundle, store it on `GroupEpoch`, and return it with the wraps. A key that fails the check counts as missing. The commitment reveals nothing about the key. A malicious server could alter it, but that only causes a denial of service, which the server can already do.
  - For repair, detection alone isn't enough. Backfill needs to be allowed to replace a History wrap that the owner's Enrolled device has found doesn't match its Device-wrap key, or that a restored device reports as mismatched. Today `skipDuplicates` and the `none` filter block that.
  - Compatibility: no encrypted-format change; it's an additive nullable column plus an additive API field. Old clients ignore it. New clients accept epochs that have no commitment, and can require one later with a forced rotation and a `minClientApiCompatibilityLevel` raise.
  - **Nothing here gets more expensive after beta**, because epochs expire and the server can force rotation, so post-beta is fine. If the team is touching the epoch bundle schema before beta anyway (for example for S1-02's v2 wrap info), adding `keyCommitment` in the same change costs almost nothing.
