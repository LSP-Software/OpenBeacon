# Map asset distribution research

Research date: 2026-11-02. This is a proposal, not an implemented or device-verified solution.

## Recommendation

Prefer bundling the glyphs and sprites required by the mobile style, subject to a native build and device verification gate. This removes glyph and sprite requests from the runtime network path for both hosted and self-hosted installations and avoids running a separate asset service. It also ties asset updates to native app releases and adds to every installation's size. Hosting is the fallback if complete assets prove too large, local sprites cannot be loaded reliably on either platform, or independent asset updates become essential. If hosting is chosen, the assets must be included in the self-hosted deployment as well as the hosted service.

## Current state and feasibility

- The app's `apps/mobile/assets/map/fonts` contains 768 files across Noto Sans Regular, Medium and Italic. Their total file contents are 11,079,256 bytes (about 10.6 MiB); filesystem allocation is about 14 MiB. Neither number predicts compressed app download size or installed package growth. The existing Expo plugin copies the files into Android assets and adds an iOS folder resource; changing assets requires a native build. See `apps/mobile/plugins/withMapFonts.js` and `apps/mobile/assets/map/README.md`.
- The installed Protomaps style dynamically selects `Noto Sans Devanagari Regular v1`, including for local names even though the configured language is English (`node_modules/@protomaps/basemaps/src/language.ts`). That directory is absent from our bundle. The [pinned upstream font directory](https://github.com/protomaps/basemaps-assets/tree/028c18f713baecad011301ff7a69acc39bcc2ae7/fonts) does include it. Obtain the matching positioned-glyph stack and establish its complete size and required ranges; do not assume the ordinary Devanagari Unicode range is the only range needed.
- The [MapLibre sprite specification](https://maplibre.org/maplibre-style-spec/sprite/) requires a JSON index and PNG image; high-density devices use the `@2x` variants. [Upstream v4](https://github.com/protomaps/basemaps-assets/tree/main/sprites/v4) includes light and dark JSON/PNG pairs at both densities. Our current style still requests these from the public Protomaps host. The actual incremental byte count remains to be measured from the exact pinned revision.
- MapLibre documents [`asset://` for Android bundled resources](https://maplibre.org/maplibre-native/android/api/-map-libre%20-native%20-android/org.maplibre.android.maps/-style/-builder/from-uri.html); a [native issue demonstrates it for glyphs](https://github.com/maplibre/maplibre-native/issues/4498). The existing app uses an iOS bundle file URI for glyphs. These are evidence of a plausible approach, not proof that sprite URL resolution, density suffixes, escaping and resource packaging work in the installed versions on both platforms. Verify those with native builds and rendering. In particular, an [upstream iOS issue](https://github.com/maplibre/maplibre-native/issues/3196) illustrates local glyph URL pitfalls.
- [Upstream asset licensing](https://github.com/protomaps/basemaps-assets) identifies SIL Open Font License for fonts and MIT-derived Tangram icons for sprites. Include and verify the exact notices with both source and binary distributions. Preserve the separate style and map-data attribution obligations.
- Local glyphs and sprites do not make the complete map offline or hide all map activity: the app obtains its PMTiles source separately. Validate privacy and availability of that source independently.

## Decision gates and delivery plan

1. Pin the upstream asset revision and style version. Enumerate literal and expression-selected font stacks from both generated themes and confirm ranges against real tile labels, including positioned glyphs and non-Latin cases. Check upstream license notices and all light/dark, 1x/2x files. Record total raw bytes and compare clean production builds before and after, including downloadable and installed size on both platforms.
2. Build a small native proof using the existing plugin extended to include the complete candidate assets. On Android and iOS, render actual labels and icons with the third-party asset host blocked, covering both themes, both density paths, Latin, Devanagari and other representative supported scripts. Inspect native errors and requested paths. Use a known working renderer or device; the SwiftShader emulator problem is tracked separately in OPE-183.
3. If the added size and native results are acceptable, package the pinned assets and licenses, generate platform-specific local URLs, and test the generated style, every referenced stack/range and sprite pair, missing files, upgrades, and native resource packaging. Ensure CI detects style/asset drift. Document the native release requirement and asset refresh process.
4. If the gate fails, serve the same pinned complete set from the configured OpenBeacon backend or its own static storage, shipped with self-hosted deployment artifacts. Use immutable versioned URLs with old versions retained while older apps need them, appropriate cache headers and missing-asset behavior. Validate hosted and self-hosted installation, upgrades, asset availability, and memory/startup costs. Do not silently fall back to a third-party host.

Open decision: agree an app download/installed-size budget after measuring the complete candidate; no complete or compressed bundle size is established yet. Existing OPE-184 explicitly specifies backend serving, so change its acceptance criteria if bundling is chosen rather than treating this proposal as already authorized scope.
