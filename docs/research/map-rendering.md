# Map rendering research

Research snapshot: 1 November 2026. These sources describe supported approaches; they do not establish the cause of the emulator failures.

On emulator 5554, a stationary view with map symbols enabled showed five solid white boxes and no readable labels. A screenshot check of five fixed locations found 0 of 5 boxes after disabling symbols and 5 of 5 after re-enabling them. This is a view-specific check of the white boxes, not an automated test of the transient flashing or proof of the shader cause. The MapLibre log also contained PMTiles header and tile timeout errors; their timing relative to the reported flashes has not been established.

## Markers

OpenBeacon uses MapLibre React Native 10.4.2. Its [PointAnnotation implementation](https://github.com/maplibre/maplibre-react-native/blob/v10.4.2/src/components/PointAnnotation.tsx) documents that Android renders child views into a bitmap. It recommends ShapeSource and SymbolLayer for many points with static images and MarkerView for interactive views. Its [MarkerView implementation](https://github.com/maplibre/maplibre-react-native/blob/v10.4.2/src/components/MarkerView.tsx) notes that static PointAnnotation or SymbolLayer is faster. The current [annotation comparison](https://maplibre.org/maplibre-react-native/docs/guides/annotations/) distinguishes style-layer features, view interactivity, and platform differences. A move between APIs should be measured on both platforms, including custom avatars, heading changes, selection, movement, and overlapping points; a family-sized group does not by itself demonstrate a many-point scaling problem.

MapLibre React Native [11.0 and later](https://github.com/maplibre/maplibre-react-native/blob/main/CHANGELOG.md) requires React Native's new architecture and changes many APIs. Its release notes list an Android map memory-leak fix among other fixes. OpenBeacon enables the new architecture, but upgrading is a migration and should not be presumed to fix the observed issue without a comparison.

On the current Android emulator, bitmap-backed annotations were invisible or appeared as white squares, while view-backed markers rendered and could be selected. View-backed markers also appeared to lag the map during swipes. An initial comparison included overlapping pins whose simulated positions change and is not reliable. In a follow-up that temporarily rendered only emulator 5554's stationary self pin, rough frame matching during repeated horizontal swipes measured a median offset of 1.1 physical pixels and a peak of 35 pixels. The screen-recording method and 10 Hz sampling limit the precision; repeat on more hardware and use a renderer-aware measurement before attributing the peak to an exact cause. A rendering approach that keeps markers in the map's own rendering pipeline still needs to be evaluated for custom avatars, heading, and selection.

The emulators report the SwiftShader OpenGL renderer. [MapLibre Native issue 3648](https://github.com/maplibre/maplibre-native/issues/3648) reports missing text and symbols with Android emulators on Native 11.8 and newer. The open [shader fix](https://github.com/maplibre/maplibre-native/pull/4625) describes a SwiftShader-specific uniform-block ordering issue and includes a targeted rendering test. This matches the environment and missing symbols but does not by itself prove the cause of every coloured artifact observed here. In a short comparison, removing symbol layers suppressed those artifacts; the application must retain labels, so this was only a diagnostic experiment.

A temporary build with Native 11.12.1 Vulkan failed to create a Vulkan instance on emulator 5554 with both texture and surface modes. A temporary 11.7.1 OpenGL build required a compatibility adjustment to compile the React Native wrapper and then failed to parse this app's signed PMTiles URL. Neither renderer change was retained. The original APK and dependency source were restored. Verify fixes on a physical Android device as well as the emulator before choosing a production rendering path.

The proposed [SwiftShader workaround](https://github.com/maplibre/maplibre-native/pull/4625) remains open. Its author reports that font loading and shaping can succeed while the symbol fragment shaders produce transparent pixels; the same ordering issue affects dashed lines and patterned backgrounds. This is a specific possible explanation for missing text, not proof that white boxes or flashing tiles have the same cause. A separate [Vulkan flickering report](https://github.com/maplibre/maplibre-native/issues/3490) concerns a physical Samsung device and Vulkan, so it does not establish an OpenGL emulator cause.

In a subsequent comparison, the shader changes from upstream commit `fa893e9` applied to Native Android 11.12.1 after adjusting the generated-header directory from `mln` to `mbgl`. An x86_64 OpenGL library built from that source with Android NDK 27.1 and CMake 4.4.4 was substituted into a copy of the installed debug APK. On emulator 5554, names and icons became visible. The user reported that emulator 5556 also rendered correctly and that flashing and pop-ins stopped. This supports the shader workaround as the cause of the observed emulator improvement, although the comparison also changed the native build toolchain. The APK was temporary; the repository still uses the published 11.12.1 library. Establish a reproducible distribution strategy and test physical Android devices before shipping a patched native library.

## Style changes

The installed [React Native 10.4.2 Android wrapper](https://github.com/maplibre/maplibre-react-native/blob/v10.4.2/android/src/main/java/org/maplibre/reactnative/components/mapview/MLRNMapView.java) calls `removeAllSourcesFromMap`, then `setStyle`, and reattaches wrapper-managed sources after the new style loads when `mapStyle` changes. The names-and-symbols toggle changes the entire style JSON, so it takes this path; that establishes a style reload but does not demonstrate that it causes the observed flashing during gestures. MapLibre's [style-switching discussion](https://github.com/maplibre/maplibre-react-native/discussions/898) recommends changing `mapStyle` for switching themes and says unchanged tiles should be reused. Measure the toggle independently from panning and distinguish style-load frames from failures to fetch or render tiles.

A separate upstream [tile retry report](https://github.com/maplibre/maplibre-native/issues/4773) describes failed vector or raster tiles remaining in an error state while visible, even after network recovery and an identical `setStyle`, in Native Android 11.5.0. This is a reported failure scenario, not evidence that it is occurring in OpenBeacon; correlate missing tiles with network errors before applying it here.

## Tiles and latency

[PMTiles](https://docs.protomaps.com/pmtiles/) reads an archive over HTTP byte ranges; its header and directories are intermediate requests that can be cached. A self-hosted origin must correctly support range requests, and each range request can incur a storage GET. [Protomaps cloud storage guidance](https://docs.protomaps.com/pmtiles/cloud-storage) explains range support and cross-origin requirements. The reported emulator metadata, header, directory and tile timeouts require timing and status measurements at these boundaries; they do not identify which network component is slow.

[Protomaps' `pmtiles serve`](https://docs.protomaps.com/pmtiles/cli) can instead expose a ZXY tile API from a private bucket and can reduce latency by decoding archives server-side; it maintains a shared header and directory cache. This adds an operational service and changes the request path. Compare it with direct ranged access, including cold and warm caches, concurrent devices, self-host deployment, and privacy implications before choosing it.

## Fonts and sprites

The [Protomaps assets repository](https://github.com/protomaps/basemaps-assets) supplies pre-generated glyph ranges and sprites. Its font directory carries the SIL Open Font License and its sprites derive from MIT-licensed icons; preserve the applicable notices when redistributing. The current [Protomaps example](https://github.com/protomaps/basemaps/blob/main/examples/basic.html) uses v4 light sprites and glyphs separately from tiles. Host both glyphs and light/dark sprites, including required density variants, to remove the GitHub Pages runtime dependency. Verify the exact font stacks and glyph ranges required by the installed style and retain license files.

The [MapLibre self-hosting guide](https://maplibre.org/martin/recipe-basemap-selfhosted/) describes glyph URLs using `{fontstack}` and `{range}` and a separate sprite endpoint. It also describes Martin as one option for generating glyphs and sprite sheets from source files. A static asset server is another option for pre-generated files. A self-hosted deployment needs those resources available on its own configured origin; replacing GitHub with a single OpenBeacon-hosted endpoint alone would leave self-hosted users dependent on a third party.
