# Pausing location sharing

Account has a location sharing card. Pauses default to this device; the owner can choose all devices instead. The durations are 15 minutes, 1 hour, 8 hours, 24 hours, or until the owner resumes. Account → Devices also lets the owner manage an individual device from another phone.

A device pause applies in every group. An account pause overrides each device's preference, including devices added during the pause. Resuming an account never clears a device's own pause. Pausing leaves group access and encryption keys intact, so a tablet can stay at home and view other members without sharing its location.

## State and visibility

Both User and UserDevice store a pause flag, optional deadline, last change time, monotonic revision, and the ID of the last change request applied. The shared resolver computes the effective preference. A deadline expires when server time reaches it; no scheduled database job is needed. The account query returns both preferences and the server's current time to the owner. Live tracking responses tell group members only whether each active device is paused and its current revision prefix. They never include pause deadlines or resume times.

## Change requests

Each change carries:

- `requestId`: generated by the app when the owner taps.
- `expectedRevision`: the revision of that scope shown when the owner tapped. It is null only for a pause made before the app has ever loaded the preference.
- `replacesRequestId`: the queued change this one replaces, if any.
- For a timed pause, `durationMinutes` and `pausedUntil`: tap time plus the duration, on the server's clock as estimated by the app.

The server applies these rules per scope, under the account row lock:

1. A request whose ID matches the last applied request is acknowledged without changing anything. A retry after a lost reply therefore cannot restart a timer.
2. A request is applied only if the scope's revision still equals `expectedRevision`, or the scope was last changed by `replacesRequestId`. Otherwise it returns `superseded` and changes nothing, so a replayed change cannot undo a newer one made on another phone. A pause with a null `expectedRevision` is applied unconditionally. The app sends a pause that way on its first attempt, because pausing is the owner's current intent and the safe direction; once queued for retry, the pause carries the revision shown when it was tapped. Resumes are always conditional.
3. The deadline is `pausedUntil`, capped at the chosen duration from now. A pause lasts from when the owner tapped, not from when it reached the server.
4. If that deadline has already passed, the result is `expired`: nothing is paused, but the revision still advances so points captured before the pause stay discarded.
5. A resume when nothing is paused, or a pause identical to the active one, records the request ID without advancing the revision.

The app keeps at most one queued change per scope for this device. A new change replaces the queued one and names it in `replacesRequestId`. A superseded result removes the change from the queue and the app reloads the current state. Signing out first tries to send queued changes. Anything still queued is then dropped, along with the points held back behind a queued pause, so an old pause is never replayed at the next sign-in.

These controls are server-readable operational metadata, like device names and group membership. The server needs them to enforce upload and retrieval rules. Locations remain encrypted. The ribbon and person details disclose that sharing is paused, without showing a device's previous coordinates, battery reading, or location age. A member appears in Paused when all of their active devices are paused. Otherwise their sharing devices remain visible and the device list identifies the paused devices.

Each captured point's clientPointId includes the account and device revisions. Unchanged accounts and devices retain the original ID format. The server discards points with an obsolete revision or an active pause and acknowledges them separately, so the uploader removes them rather than retrying forever. This also discards unuploaded points from before a pause; already stored ciphertext is retained.

Uploads and pause changes lock the account row before other tracking work, so an upload cannot commit after a pause based on an obsolete preference. Live queries filter points using the current preference. Poll responses carry the last scanned cursor even if every scanned point was filtered out.

The map removes cached positions when a pause or revision change arrives. Older responses from another group cannot overwrite a newer revision. Decrypted points must match the current revision. Every pause advances the revision, and a resumed sender's capture runtime only uses the new revision for fixes taken after the resume cutoff. Resuming therefore waits for a fresh fix rather than restoring a previous pin, including when a phone's clock was ahead before pausing. Viewers don't compare the sender's capture time with the cutoff: the capture time comes from the sender's clock, so a sender whose clock runs slow would stay hidden after resuming.

## Android capture and offline behavior

The native capture runtime persists the effective state by account and server. It removes location callbacks during a pause and rejects fixes already being encrypted when the preference changes.

Timed pauses keep the foreground service running, and its notification says sharing is paused. A native timer and an alarm that can run while the device is idle end the pause. Android may delay an alarm; capture resumes when Android delivers it. The service restores the preference and timer after restarting. During a timed pause it checks for remote preference changes every 30 seconds while awake and uses the idle alarm for checks about every five minutes, subject to Android scheduling.

A pause with no end stops the foreground service, so no location service or notification stays active. This applies only after the server confirms the pause; an unconfirmed local pause behaves like a timed pause until the next sync. A WorkManager job then checks for remote changes about every 15 minutes while the device has a network connection. The app also checks whenever it opens. Each check runs the same headless sync as the timed-pause checks. After a reboot or app update, the boot receiver schedules the job instead of starting the service. Stopping capture, signing out or changing account cancels the job.

When a check finds that the pause has ended, or has changed to a timed pause, the job tries to start the foreground service. Android 8 to 11 allow this when the app holds background location. Android 12 and later block most foreground service starts from background jobs. The start only succeeds if the app is exempt at that moment, for example when the owner has turned off battery optimization for Open Beacon. If Android refuses, or background location isn't granted, the job posts a notification asking the owner to tap to open the app, and capture restarts when the app opens. A resume from another phone can therefore take up to about 15 minutes, plus Android's job delays, and on Android 12 and later it may need someone to open the app on the paused device.

Timed pauses end by the server's clock. The app estimates the offset between the phone and server clocks from each preference query and converts deadlines and resume cutoffs to the phone's clock before passing them to the capture runtime.

The owner can stop capture locally even without a connection. Device and account requests are persisted separately and retried before applying remote state. Uploads wait while a change is queued. Until confirmation, the UI explains that groups and other devices may not know about the change. An offline timed pause ends locally at the tapped time. Capture may then resume before the server has heard of the pause; those fixes carry the old revision, which the pause advances when it arrives, so the server discards them. An offline resume replaces a queued pause and restarts capture only if no other known pause still applies. A remote device may continue capturing until it receives the change, but the server rejects its obsolete revision, including uploads attempted after the account resumes.

An offline viewer cannot learn about a new pause until it reconnects. The app cannot erase a location someone has already received, copied, or recorded.

The native tracking implementation currently exists on Android. The Account controls and server visibility rules also apply when viewing on other platforms.

## Compatibility and validation

Compatibility level 4 requires both updated apps and an updated server. Older apps do not understand the changed clientPointId meaning, discarded uploads, or paused map state. Client version 1.10.0 and server version 0.11.0 include the change.

Tests cover preference composition and expiry, native capture revisions and cached fixes, offline retry and late responses, request IDs and superseded changes, tap-time deadlines and clock offsets, sign-out clearing the queue, map cache removal, server authorization, delayed uploads, new devices during an account pause, and upload/pause races against PostgreSQL.
