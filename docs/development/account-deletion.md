# Account deletion

Account deletion is a cross-service operation. The API schedules deletion after seven days and revokes the user's sessions. Successful authentication cancels the request. The scheduled job uses the PostgreSQL clock to select due accounts and rechecks the deadline under the account lock. It records storage cleanup so it can be retried. Keep deadline and retry decisions on the database clock; the runner host clock may differ. A remaining group member's device rotates the group epoch after a departure.

When email is configured, the owner is emailed when deletion is scheduled, unless they turned that alert off, and when the account is actually deleted, either immediately or by the runner at the end of the grace period. The address is read inside the deletion transaction and the email is sent after it commits. The operator's `delete-account` command sends no email.

## When adding data

For every new feature, identify all database rows, object-storage keys, caches, logs, third-party services, and backups that may contain information about an account. Document who owns each record and how it is removed. Add a user relationship with an appropriate deletion policy where possible; a copied name or email without a user reference cannot reliably be attributed later. Include records created for other users, such as notifications. Add deletion and failure-retry tests for the new data, including concurrent writes and the effect on other users.

Keep user-uploaded objects below `user/<userId>/` and ensure direct-upload URLs cannot recreate an object after cleanup. Changes to presigned URL lifetime must be reflected in the cleanup delay. Image cleanup must remove object versions and delete markers. Do not remove the cleanup record before successful storage deletion.

Do not delete a group epoch merely because its creator is deleted: remaining group members may still need it. Flag affected groups for rotation and continue to accept old-epoch uploads from remaining members, including while rotation is pending, for offline continuity. A former member who retained an old key may be able to read those uploads. A successful join, departure, or deferred rotation clears the pending flag through the same epoch persistence path. Remaining devices retry pending rotations automatically. Test multiple members rotating at once, offline queues, and a device with unavailable keys.

Device private keys stay in SecureStore on the user's devices after deletion. Deletion revokes every session, so the backend cannot reach signed-out devices to erase them. A retained key gives no further access: deletion removes the device's wrapped epoch keys and device record, and remaining members rotate the group epoch. Combined with a wrapped epoch key copied before deletion, such as from a backup, the key can unlock that old epoch. That exposes data in the copy and anything remaining members upload under the old epoch afterwards, which is the same limit that applies to any former member who kept an old key. The Beta 1 threat model already trusts the backend to protect those copies, and rotation stops new uploads using the old epoch once remaining devices move on. Local decrypted data and provisioned epoch keys are the greater risk, and the app clears them when the session ends (see "When a session ends on the phone" in `docs/security/beta-1-privacy-draft.md`). Android removes SecureStore entries on uninstall; iOS Keychain entries survive uninstall, so revisit this before shipping iOS.

Recovery and history rows are removed with the `User` row (`packages/database/prisma/schema.prisma`; asserted in `packages/api/src/lib/account-deletion.integration.test.ts`):

- `RecoveryKey` is deleted.
- Every `AccountHistoryKey` version is deleted, and with it the Recovery escrow, which is stored on the same row.
- Every `GroupEpochHistoryWrap` addressed to the account's History keys is deleted, through the cascade from `AccountHistoryKey`.
- `GroupEpochHistoryWrap` rows that the account's devices sent to other members stay, because those members need them to read old epochs. Deleting the device sets `senderDeviceId` to null. `senderPublicKey` is kept, because opening the wrap needs it.
- Personal nicknames and colours are deleted with the account's `GroupMember` rows: the nicknames it set, the nicknames other members set for it, and its group colours. Other members' nicknames for each other stay. The test asserts both the nicknames and the colours.
- Places the account created are deleted through the cascade from `Place.createdByUserId`. A place is its creator's data even though the group shares it. Places other members created stay; where this account made the last edit, `Place.updatedByUserId` is set to null. Every group where the account created or last edited a place gets a new `placesRevision`, so other members' phones refetch. Those groups are locked with the account's own groups, in one id-ordered statement, including groups the account has left. Leaving a group or being removed from it keeps the places a person created there, until the group or their account is deleted. `packages/api/src/router/group/groupPlaces.integration.test.ts` asserts all three cases.
- Each group the account is still in gets an `ACCOUNT_DELETED` group event. Group events point at accounts through `actorUserId` and `subjectUserId` instead of copying names, and both are set to null when the account goes, so the group history shows "a deleted account" and the server keeps no copy of the name. `packages/api/src/lib/account-deletion.integration.test.ts` asserts this.
- Notification settings (`NotificationSetting`) and phone notices (`AccountNotice`) are deleted with the `User` row. Push tokens (`PushToken`) are deleted with each `UserDevice` row; removing a device deletes its token straight away. A push that is already waiting finds no token and sends nothing.
- Place Alert Mutes reference the group membership of both the member who set them and the member they mute, so they are deleted through the `GroupMember` cascade when the account goes, and also when either member leaves or is removed. `packages/api/src/router/group/placeAlerts.integration.test.ts` asserts this.

History private keys also stay in SecureStore on the user's phones after deletion, for the same reason as device private keys. With the escrows and History wraps deleted, a retained History key only unlocks a History wrap copied before deletion, such as from a backup. That's the same limit as a retained device key.

Review deployment-specific logs, caches, backups and external processors separately; database deletion does not erase copies retained by other people. Database constraints require new shared invitations to have an account reference. Feedback is sent anonymously to the hosted API, including by self-hosted users, so it has no account reference. Deleting a hosted account removes feedback carrying the account email. Deleting a self-hosted account does not remove feedback held by the hosted API; those users must ask through the in-app Contact Us form. Feedback sent without an email cannot be attributed, so it cannot be removed on request.

## Operations

Run the scheduled job runner with the same database and image bucket as the backend and permissions to list and delete object versions. When the backend has email configured, give the runner the same email settings and `REDIS_URL` too, so it can send the account-deleted email. Failed operations are retried. To delete an account immediately with the root `.env` locally, run `bun --env-file=../../.env run --cwd apps/scheduled-jobs delete-account <email>`. In a configured deployment, run `bun run --cwd apps/scheduled-jobs delete-account <email>`. The same sole-owner guard applies; groups with no other members are deleted. Image cleanup is performed by the runner after the presigned upload window. Verify job health and investigate failures without logging account identifiers or image URLs. Passwordless accounts need to request deletion from the server operator.
