# Beta 1 data-flow review

This is a source review for OPE-164, not a deployment audit or independent security review. The Beta 1 contract accepts backend visibility of account and group names, email addresses and membership, and unencrypted images. Tracking plaintext and unwrapped group keys must stay on devices. The backend-supplied device key directory is trusted in the Beta 1 threat model.

| Flow                   | Code-level observation                                                                                                                                                                                                                            | Visibility and limitations                                                                                                                                                                                                                                          |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Tracking               | Android encodes location, capture time, speed and battery into a payload and encrypts it before queueing. The mobile upload sends ciphertext, nonce and routing identifiers. The API stores those fields and derives the sender from the session. | The backend sees group, epoch, sender and device IDs, point ID, kind, receipt time, payload size and traffic timing. It cannot infer from the schema alone that an arbitrary client supplied valid ciphertext.                                                      |
| Device and group keys  | Device private keys are held in SecureStore. Clients create epoch keys and send per-device wrapped keys; native capture stores provisioned epoch keys encrypted using Android Keystore.                                                           | The API stores public keys, wrapped keys and associated device and epoch metadata. The backend supplies public keys, so a malicious backend substituting keys is outside the selected threat model. A compromised member or device can disclose keys and plaintext. |
| Accounts and sessions  | Better Auth stores account and session records in PostgreSQL, including session IP and user agent fields and provider token fields.                                                                                                               | Names, email addresses, authentication metadata and potentially provider credentials are server-visible. Actual provider behavior, access controls and retention depend on deployment.                                                                              |
| Groups and invitations | Group names, membership, roles and timestamps are stored in PostgreSQL. Account-specific invitations store recipient and inviter relationships; shared invitation codes are stored as hashes.                                                     | Group relationships and invitation activity are server-visible.                                                                                                                                                                                                     |
| Images                 | The client uploads image bytes directly to object storage using a presigned URL; the API stores the resulting image URL.                                                                                                                          | Images are not end-to-end encrypted. Access via a reachable URL and storage or CDN behavior depend on deployment.                                                                                                                                                   |
| Feedback               | The app sends feedback without a session to the hosted OpenBeacon API, never to a self-hosted server. It stores user-provided text, optional email and app, Android, map and server version information. Self-hosted backends reject feedback.    | Feedback is readable by OpenBeacon and can contain sensitive information entered by the user. The app discloses that it goes to OpenBeacon rather than a self-hosted operator. The hosted API sees the client IP.                                                   |
| Maps                   | The API returns a signed PMTiles object URL; the mobile map uses it to retrieve map data.                                                                                                                                                         | The object provider can observe requests and byte ranges, timing and client network information. Map access patterns may reveal an approximate viewed area. Exact visibility and retention depend on the provider and deployment.                                   |

## Diagnostics

The mobile tRPC logger prints direction and procedure path; API timing and rate-limit logs print procedure paths and operational measurements. Map URL issuance logs the user ID, object key, expiration and cache source, but not the signed URL. Android capture and key-store errors and image-upload errors retain exception details for debugging. Tracking upload failures can store an error message in the local ciphertext queue. These paths warrant deployment-specific review, but this source review did not establish that they currently emit tracking plaintext or unwrapped keys. Arbitrary library or server error messages are not guaranteed to be free of sensitive data. Avoid logging request bodies, credentials or keys when adding diagnostics, and investigate a concrete leak before changing existing error detail.

## Evidence and remaining checks

- `CapturePipeline.kt`, `GroupPayloadEncrypt.kt`, `tracking.ts` and `groupTracking.ts` describe the tracking path. The capture pipeline, encryption vector, upload and authorization tests exercise parts of this path; they do not prove the behavior of every installed app or provider.
- `deviceKeys.ts`, `groupEncryption.ts`, `groupEpochs.ts` and `groupEpochRouter.ts` describe key registration, wrapping, persistence and retrieval. Tests cover wrapping, interoperability, recipient selection and member authorization. Device revocation remains deferred to OPE-167; key recovery and account-level multi-device support remain deferred to OPE-155.
- `schema.prisma`, `accountRouter.ts`, `groupInvitesRouter.ts`, `image-upload.ts` and `mapsRouter.ts` identify the server-visible records and external storage flows. The privacy information work in OPE-163 must communicate the accepted exposures.
- OPE-159 and OPE-161 must verify deployed provider and proxy configuration, logs, analytics, storage and CDN access, backup retention and deletion, device behavior and independent review. This source review cannot establish those properties or prove that no third party can observe protected content.
