# Beta 1 data-flow review

This is a source review for OPE-164, not a deployment audit or independent security review. The Beta 1 contract accepts backend visibility of account and group names, email addresses and membership. Tracking plaintext, pictures and unwrapped group and picture keys must stay on devices. The backend-supplied device key directory is trusted in the Beta 1 threat model.

| Flow                   | Code-level observation                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               | Visibility and limitations                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Tracking               | Android encodes location, capture time, speed and battery into a payload and encrypts it before queueing. The mobile upload sends ciphertext, nonce, routing identifiers and whether the point is a history point, a stay or live-only. The API stores the nonce and ciphertext as one payload in a stream for the group, epoch, device and sharing revision, and derives the sender from the session. Stays overwrite their stored point; live-only uploads only replace the device's latest point for the map. An hourly scheduled job deletes points 14 days after the server first received them, and latest points 14 days after their last update, and a daily one deletes epochs a newer epoch replaced more than 14 days ago once no point or place uses them; the latest epoch is kept. Backups keep deleted rows until they are replaced.  | The backend sees group, epoch, sender and device IDs, point ID, kind, receipt time, payload size and traffic timing. It cannot infer from the schema alone that an arbitrary client supplied valid ciphertext.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| Device and group keys  | Device private keys are held in SecureStore. Clients create epoch keys and send Device wraps (epoch keys wrapped per device); native capture stores provisioned epoch keys encrypted using Android Keystore. Every account has a History key, so clients also send History wraps (epoch keys wrapped to each member's current History key). Only accounts with a recovery phrase send Recovery escrows, one per History key version. History private keys are held in SecureStore; the phrase and Recovery private key are never stored.                                                                                                                                                                                                                                                                                                             | The API stores public keys, Device wraps, History wraps, escrows and the associated device, epoch and History key version metadata. It can see which accounts have a phrase and when History wraps are added. The backend supplies device and History public keys, so a malicious backend substituting keys is outside the selected threat model until OPE-213. A compromised member or device can disclose keys and plaintext.                                                                                                                                                                                                                                                                                                              |
| Devices                | Each device registers its public key, platform, model, Device name and Device icon. The server records when it last saw each device (`lastSeenAt`) and last stored a location from it (`lastLocationAt`). A session is linked to one device (`Session.deviceId`) when it registers it or proves it holds its Device key. Pending devices are deleted 7 days after they first signed in if never set up, or 7 days after removal; removed devices that were ever active are kept until the account is deleted.                                                                                                                                                                                                                                                                                                                                        | Device names, icons, platform and model are stored in plain text. Group members can list the name and icon of each other's Active devices. `lastSeenAt` and `lastLocationAt` reveal when each device was last used and last shared a location.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| Device links           | When an Active device approves a new one, it seals every History private key it holds to the new device's key with HPKE AuthPSK, using a secret from the QR code that is never sent. The server stores a `DeviceLink` row with the new and approving devices, the handover ciphertext and its timestamps. The row is deleted a day after the code expires, as soon as the new device is removed, or when the account is deleted.                                                                                                                                                                                                                                                                                                                                                                                                                     | The server sees which device approved which and when, and the handover size, which reveals roughly how many History key versions the account has. It can't open the handover.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| Device challenges      | To activate a device after a restore, or to link a session to a device, the server seals 32 random bytes to the History or Device public key. A `DeviceChallenge` row keeps only their SHA-256 hash, the device, the session (session links only), the purpose and the History key version (activation only), for 5 minutes.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         | The server sees when a device proves it holds a key. A challenge is single-use and expires after 5 minutes. The hourly scheduled job deletes expired rows, so one can stay up to about an hour after it expires.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| Accounts and sessions  | Better Auth stores account and session records in PostgreSQL, including session IP and user agent fields and provider token fields. The server keeps a session until it's signed out, its device is removed or deleted, the account is deleted, or it expires. The hourly scheduled job deletes expired sessions, so one can stay up to about an hour after it expires.                                                                                                                                                                                                                                                                                                                                                                                                                                                                              | Names, email addresses, authentication metadata and potentially provider credentials are server-visible. Actual provider behavior, access controls and retention depend on deployment.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| Groups and invitations | Group names, membership, roles and timestamps are stored in PostgreSQL. Account-specific invitations store recipient and inviter relationships until accepted or declined, for 30 days at most, and are deleted when the inviter leaves the group; shared invitation codes are stored as hashes and deleted a day after they expire. Each group keeps a history of its creation, joins, departures, removals, account deletions, role changes, renames (old and new name), picture changes and places added, edited or deleted (name and emoji), with who did it and when. The hourly cleanup targets entries older than 14 days; they can remain longer between runs or during a backlog or failure. Reads exclude expired entries. Members see only entries from their latest join onwards, and entries about a deleted account no longer name it. | Group relationships and invitation activity are server-visible.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| Personal data          | Nicknames and group colours are encrypted on the phone, to the current History key.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  | The API sees who nicknamed whom, that a colour is set, the envelope and History key version, ciphertext length and timing.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| Pictures               | The phone encrypts each profile or group picture with a fresh key and uploads the encrypted file directly to object storage using a presigned URL; the API stores the file's URL. The picture key is encrypted with the group's latest epoch key and stored on the group, or on the member's row in each group for a profile picture, plus a copy of the account's own key sealed to its History key. Members' phones re-encrypt stale keys with the latest epoch key after membership changes, and an owner's or admin's phone re-uploads a group picture whose key no longer opens it. Uploads that are never confirmed are deleted after an hour, and a daily scheduled job deletes stored pictures that no account or group uses any more.                                                                                                       | The backend sees whether an account or group has a picture, the encrypted file's size, when it changes, who changed a group picture, and which phone re-encrypted or repaired a key and when. It can't open the pictures or keys. Anyone with a reachable URL may be able to download the encrypted file; storage or CDN behavior depends on deployment.                                                                                                                                                                                                                                                                                                                                                                                     |
| Feedback               | The app sends feedback without a session to the hosted OpenBeacon API, never to a self-hosted server. It stores user-provided text, optional email and app, Android, map and server version information. Self-hosted backends reject feedback.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       | Feedback is readable by OpenBeacon and can contain sensitive information entered by the user. The app discloses that it goes to OpenBeacon rather than a self-hosted operator. The hosted API sees the client IP. Feedback is deleted 30 days after it was received.                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| Maps                   | The API returns a signed PMTiles object URL; the mobile map uses it to retrieve map data.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            | The object provider can observe requests and byte ranges, timing and client network information. Map access patterns may reveal an approximate viewed area. Exact visibility and retention depend on the provider and deployment. The phone caches map data it has fetched, up to the size chosen in Account → Map storage. With server 0.22.1 or later, the signed URL asks for private caching for a year, so the phone doesn't request a cached range again. Ranges from older servers, or cached before this release, are re-checked with a conditional request. When the cache is full, the areas looked at longest ago are removed first. The whole cache is deleted when the map is updated, the user deletes it or the session ends. |

## Diagnostics

The mobile tRPC logger prints direction and procedure path; API timing and rate-limit logs print procedure paths and operational measurements. Map URL issuance logs the user ID, object key, expiration and cache source, but not the signed URL. Android capture and key-store errors and picture upload errors retain exception details for debugging; picture decryption, catch-up and repair failures are swallowed without logging. Tracking upload failures can store an error message in the local ciphertext queue. These paths warrant deployment-specific review, but this source review did not establish that they currently emit tracking plaintext or unwrapped keys. Arbitrary library or server error messages are not guaranteed to be free of sensitive data. Avoid logging request bodies, credentials or keys when adding diagnostics, and investigate a concrete leak before changing existing error detail.

## Evidence and remaining checks

- `CapturePipeline.kt`, `GroupPayloadEncrypt.kt`, `tracking.ts` and `groupTracking.ts` describe the tracking path. The capture pipeline, encryption vector, upload and authorization tests exercise parts of this path; they do not prove the behavior of every installed app or provider.
- `deviceKeys.ts`, `groupEncryption.ts`, `groupEpochs.ts` and `groupEpochRouter.ts` describe key registration, wrapping, persistence and retrieval. Tests cover wrapping, interoperability, recipient selection and member authorization. Device removal shipped in OPE-290. History key rotation on device removal remains deferred to OPE-167, and signing device keys to OPE-213.
- `accountRecoveryRouter.ts`, `recovery.ts`, `historyKeys.ts`, `epochKeys.ts` and `personalData.ts` describe the recovery phrase, History keys, History wraps, backfill, restore and personal data sealing. Tests capture every API input during setup, backfill, restore, phrase change and reset and check that no phrase, private key or epoch key is sent. See `docs/security/beta-1-privacy-draft.md` for the lifecycle and threats.
- `schema.prisma`, `accountRouter.ts`, `groupInvitesRouter.ts`, `image-upload.ts`, `imageKeys.ts` and `mapsRouter.ts` identify the server-visible records and external storage flows. The privacy information work in OPE-163 must communicate the accepted exposures.
- OPE-159 and OPE-161 must verify deployed provider and proxy configuration, logs, analytics, storage and CDN access, backup retention and deletion, device behavior and independent review. This source review cannot establish those properties or prove that no third party can observe protected content.
