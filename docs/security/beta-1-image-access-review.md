# Beta 1 image access review

Profile and group pictures are end-to-end encrypted on the phone since server 0.26.0 and app 1.23.0 (OPE-313). The stored file is ciphertext, so the storage provider and operator can't see the picture. The hosted-service owner reports that pictures are stored in a public, non-browsable S3 bucket with random UUID filenames. This is owner-supplied configuration information, not an independent verification of the deployed bucket or CDN. Anyone who obtains a reachable URL may be able to download the encrypted file without signing in, and learn its size and when it was uploaded, but not the picture. Self-hosted behavior depends on its storage and CDN configuration. See [Profile and group pictures](beta-1-privacy-draft.md#profile-and-group-pictures) for the keys.

## Source review

- Profile image upload requests require an authenticated session. Group image requests require an owner or admin, and group authorization is checked again when recording and confirming an upload. The API creates a random UUID filename. The phone encrypts the picture with that name bound in, then the API issues a five-minute presigned upload URL for the encrypted file's size and hash. The phone uploads the encrypted file straight to storage as `application/octet-stream`. The API checks only its size and deletes anything outside the limits. See `packages/api/src/router/accountRouter.ts`, `packages/api/src/router/group/groupSettingsRouter.ts`, `packages/api/src/lib/image-upload.ts` and `apps/mobile/lib/image-upload.ts`.
- The API saves an unsigned URL built from the configured CDN base, bucket and object key. The storage provider and operator can access the encrypted file; whether an unauthenticated request succeeds depends on deployment configuration. See `packages/api/src/lib/storage.ts`.
- On replacement, the API commits the new URL and attempts to delete the previous object, including listed object versions. Cleanup errors are ignored, so replacement does not guarantee removal. Superseded pending uploads are also cleaned up on a best-effort basis. A presigned upload may remain usable until it expires.
- Group deletion attempts to delete the current group picture and pending group uploads before deleting the group record. Storage errors prevent successful group deletion, but CDN caches, backups and copies held by others are outside this source-level guarantee. Profile pictures that no account uses any more, including after account deletion, are left to the daily scheduled job that deletes unused stored pictures.
- Server 0.26.0's migration cleared every stored picture URL, so the daily job deletes every picture uploaded before encryption. Google sign-in no longer copies the Google photo.

Check abandoned uploads, profile picture retention and that the bucket held no plain pictures after the 0.26.0 migration. Record results without publishing picture URLs or credentials.
