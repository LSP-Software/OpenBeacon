# Beta 1 privacy and key lifecycle: working draft

Status: working contract with owner decisions, 29 October 2026. Updated 8 November 2026 for the recovery phrase and History key (OPE-155), which are part of Beta 1, 9 November 2026 for email (OPE-218), also part of Beta 1, 11 November 2026 for a History key on every account (OPE-289), 11 November 2026 for Pending devices (OPE-292), 11 November 2026 for Device links (OPE-293), 11 November 2026 for Session links, and 11 November 2026 for limiting Pending devices to setup. This is not an independent security review or evidence of real-device behavior. Complete the inventory and verification before release.

## Trust boundaries

Beta 1 includes Android and both hosted and self-hosted backends. Devices capture and decrypt tracking data; the API, database and storage operator mediate access and store ciphertext and metadata. TLS, authentication, operating system security, authorized members and their devices remain trust dependencies. A compromised member or device can disclose data it has received. Encryption cannot retract previously learned keys, plaintext or copies.

The service cannot claim to know nothing about user activity: it can see account and group relationships and traffic patterns. For Beta 1 the owner accepts trusting the backend to supply device public keys; an actively malicious backend substituting keys is outside the selected threat model. A compromised backend or account can therefore undermine confidentiality. The current server-supplied device-key directory is not independently authenticated, and neither are the History public keys it publishes for every account. This does not mean the backend can normally decrypt tracking data or that server access to plaintext is acceptable.

## Email

The hosted API sends email through Resend. A self-hosted server sends through Resend or its own SMTP server, or sends no email (see `apps/backend/README.md`). Every email the server can send is listed in the Code emails and Security alert emails rows above. The server decides when to send; no route takes an address to send an alert to.

The email provider sees every email in full: the recipient's address, which kind of email it is, when it was sent, and its content, meaning a code or alert text. Each email's footer also names the server (`SERVER_NAME`). The recipient's mailbox provider sees the same.

Emails never contain locations, IP addresses, recovery material, keys or anything else that is end-to-end encrypted. They have no links and load nothing from the internet. Resend can add open and click tracking to a sending domain; it must be off for the domain in `EMAIL_FROM`. The backend never logs email addresses. A failed send is logged with the kind of email only.

Anyone who can read the account's email, including the email provider, can reset its password with a code. Accounts that only sign in with Google have no password to reset. The reset signs out every other session and gives no earlier history. Once the account has ever had an Active device, the new session can only register a Pending device, which receives no epochs. To set it up without the phrase they must Start fresh, a Recovery reset that needs another emailed code, as in [Recovery threats](#recovery-threats). The owner is emailed about the password reset and the Recovery reset and, unless they turned it off, the new sign-in, but a provider that reads the codes can also withhold those emails. The reset gives a fresh sign-in, so they can then reset the recovery phrase with another emailed code. That deletes the escrows and History wraps but gives them no earlier history.

## Current key lifecycle

- A device generates an X25519 key pair. The mobile client stores the private key with Expo SecureStore and registers the public key under the authenticated account (`apps/mobile/lib/deviceKeys.ts`, `packages/api/src/router/authRouter.ts`).
- Group epoch keys are generated on a client and wrapped per recipient using HPKE auth mode (RFC 9180: DHKEM(X25519, HKDF-SHA256), HKDF-SHA256, ChaCha20-Poly1305) with the creating device's key as the sender key (`packages/encryption/src/hpke.ts`). The wrap binds the ephemeral, recipient and sender public keys, the epoch and the recipient device. A recipient only accepts a wrapped key created by the device key the backend records as the epoch's creator. Because the backend supplies that key, this proves origin only as far as the device key directory is trusted; it does not protect against a malicious backend until device keys can be verified independently. Tracking payloads use XChaCha20-Poly1305 with authenticated metadata (`packages/encryption/src/index.ts`).
- Creation, invite acceptance and member removal build epoch bundles from server-supplied recipient lists. Server persistence checks an active acting device, sequential epoch number and exact active-device recipient IDs (`apps/mobile/lib/groupEncryption.ts`, `packages/api/src/lib/groupEpochs.ts`).
- A device is active as soon as it registers only if the account has never had an Active device, counting removed ones (`upsertUserDevice` in `packages/api/src/lib/groupEpochs.ts`, under the account's row lock). That is a new account. Any other new device is a Pending device (`activatedAt` is null), including the next one after every device has been removed. It becomes active only by Device link, Restore or Recovery reset, below. A Pending device gets no group keys: recipient lists, epoch persistence and `getLatest` only include active devices that aren't removed. A Pending device isn't trusted. Either it's set up, or the user cancels and it's removed.
- Every signed-in procedure needs a session linked to an Active device unless it's on the setup list (`protectedProcedure` in `packages/api/src/procedures/auth/base.ts`). A session with no device that names one gets `DEVICE_UNVERIFIED`. Any other request that doesn't come from a linked Active device gets `DEVICE_PENDING` ("Finish setting up this phone first."): one that names a Pending device, names no device, or names a device the session isn't linked to. Only these procedures accept a Pending device (`setupProcedure` and `setupDeviceProcedure`): `auth.deviceKeyContext` and `registerDeviceKey`; `device.status`, `sessionChallenge`, `linkSession`, `activationChallenge` and `activate`; `deviceLink.create` and `status`; `accountRecovery.status`, `escrows`, `requestResetCode`, `verifyResetCode` and `reset`; and `account.removeThisDevice`, `deletionVerificationMethods` and `version`. `packages/api/src/router/authentication.test.ts` pins this list. So a Pending device can't upload or read locations, read groups, accept or decline invites, list or rename devices, remove another device, approve or decline a Device link, sign out other sessions, change email alerts, set up or change a phrase, or request account deletion. Registering a Pending device doesn't flag any group for rotation; it sends the new sign-in email.
- Better Auth's own routes follow the same rule where they matter. `/change-password` needs a session linked to an Active device that hasn't been removed, and otherwise fails with "Finish setting up this phone first." (`packages/auth/src/createAuth.ts`). These routes are turned off: `/send-verification-email`, `/verify-email`, `/request-password-reset`, `/change-email`, `/update-user`, `/revoke-other-sessions`, `/revoke-sessions`, `/list-sessions`, `/delete-user`, `/delete-user/callback`, `/account-info`, `/get-access-token`, `/link-social`, `/refresh-token`, `/unlink-account`, `/update-session` and `/verify-password`. `/reset-password` is off when email isn't configured, and `/reset-password/:token` always returns not found.
- The app keeps a Pending phone on the setup screens (`Stack.Protected` in `apps/mobile/app/_layout.tsx`). It can open setup, the Device link and waiting screens, Restore and Recovery reset, the removed-phone screen and the signed-out screens, and nothing else. Nothing runs in the background while the phone is Pending: no location capture or uploads, no location permission prompts and no notice that account deletion was cancelled.
- A Pending device becomes active in three ways in Beta 1. The main one is a Device link: the new device shows a QR code, an Active device of the same account scans it, and the server activates the new device when the approving device stores its handover (`packages/api/src/router/deviceLinkRouter.ts`); see [Device links](#device-links). After a Restore, it proves it holds the current History key: the server seals 32 random bytes to the current History public key with HPKE base mode (info `["openbeacon.device-activation.v1", userId, deviceId]`), keeps only their hash for 5 minutes, and accepts the opened value once, compared in constant time (`packages/api/src/router/deviceRouter.ts`). Or it runs a Recovery reset ("Start fresh"), which needs a session linked to a device and activates that device; an unlinked session gets `DEVICE_UNVERIFIED`. Activation flags each of the account's groups for rotation, so a member's device creates a new epoch that includes it. The device can read an older epoch only through a History wrap for a History key it holds. The scheduled job runner deletes Pending devices that aren't set up within 7 days, with their sessions (`apps/scheduled-jobs/src/jobs/pendingDeviceCleanup.ts`). It also deletes a removed Pending device 7 days after it was removed, so the phone has a week to get `DEVICE_REMOVED` and wipe itself. A removed device that was ever active stays until the account is deleted. Once a removed Pending device is deleted, the server treats its ID as unknown: a request naming it gets no device, and signing in on that phone registers it again as a new Pending device. Invite acceptance creates a new epoch for active devices, not wrappers for old epochs. Without a recovery phrase, a lost or reinstalled device cannot recover history.
- A session acts as a device only once it's linked to it (`Session.deviceId`). Registering a new device links the session that registers it, moving the link from any device it had before; the new device is Pending unless it's the account's first. A session with no device that names one gets `DEVICE_UNVERIFIED` from every procedure outside the setup list, and from the setup procedures that act on this phone's device, until it proves it holds that device's Device key: the server seals 32 random bytes to the device's registered public key with HPKE base mode (info `["openbeacon.session-link.v1", userId, deviceId]`), keeps only their hash for 5 minutes, and accepts the opened value once, compared in constant time (`device.sessionChallenge` and `device.linkSession` in `packages/api/src/router/deviceRouter.ts`). Only a session with no device can link this way. A linked session that names a different device gets `DEVICE_PENDING`, or "This phone isn't registered yet" where any device would do. The app runs this proof when it registers a device the server already knew (signing in again on the same phone) and whenever a request fails with `DEVICE_UNVERIFIED` (`apps/mobile/lib/sessionLink.ts`). If the phone can't open the challenge, or the server refuses the proof with any 4xx error except a rate limit or `DEVICE_REMOVED`, the app signs out once and shows "Sign in again to keep using this phone." After a network failure, a 5xx error or a rate limit, it tries again after 10 seconds. After 5 failures in a row it stops trying until the app returns to the foreground, is relaunched or signs in again. Device IDs and public keys aren't secret, so without this someone with only the password could sign in, name the owner's Active device and approve their own Pending device.
- Removing a device (`account.removeDevice`, OPE-290) needs a fresh sign-in on an Active device. It sets `revokedAt`, deletes that device's sessions and any session not yet linked to a device except the caller's, and flags every group of the account for rotation, so the next epoch leaves the device out. Registration rejects a revoked device ID with `DEVICE_REMOVED` and never clears `revokedAt`. A request whose `x-openbeacon-device-id` names a revoked device gets the same error, and its session is deleted. Wrap reads skip revoked devices. When the removed phone sees the error, it wipes its Device key, History keys, upload queue and caches, then signs out.
- Removal can't recall anything the device has already seen. Epoch keys, History keys and locations it already holds stay readable to whoever has the phone. History wraps are made per account, not per device, so until OPE-167 rotates the History key, a removed device that held it is stopped only by the server refusing its requests.
- Member removal creates a new epoch for remaining active devices. Tracking upload currently checks that an epoch belongs to the group, not that it is the latest epoch, so old-epoch uploads are accepted from an active member device. The wrapped-key read checks device ownership and skips revoked devices. Validate transactional behavior, concurrent changes, offline queues and deletion separately. Revocation cannot remove keys or data already retained by a former member.
- Local session-change cleanup removes native provisioned epoch keys and stops capture; it does not revoke the registered device or erase its private key. Reconciliation can restore a previously provisioned key if the same device still has a wrapped key and group membership.

### Recovery phrase and History key

The terms are defined in the [encryption glossary](../contexts/encryption/CONTEXT.md), and [ADR 0001](../adr/0001-random-history-key-separate-from-recovery-key.md) explains why the History key is separate from the phrase.

- **Recovery phrase.** Optional, offered in Account › Recovery phrase. Setting it up seals an escrow for every History key version the account already has, so it needs a phone that holds all of them; the server requires escrows for exactly those versions. Setting it up needs an Active device and a fresh sign-in (a session from the last 30 minutes, the `freshAge` set in `packages/auth/src/createAuth.ts`); the app only asks the user to sign in again when the session is older. The phone generates 12 BIP39 words (128 bits of entropy). The setup screen blocks screenshots and screen recording, has no copy option, and asks for three of the words back. The phrase is never stored or sent (`apps/mobile/components/NewRecoveryPhrase.tsx`).
- **Recovery key.** An X25519 key derived from the phrase's entropy with HKDF-SHA256 (salt `openbeacon.recovery.v1`, info `recovery-key`). Only its public key is sent. The private key exists in memory only during setup, restore, phrase change and reset (`packages/encryption/src/recovery.ts`). The info `identity-signing-key` is reserved for OPE-213.
- **History key.** A random X25519 key per account, numbered from v1; the highest version is current. The first phone creates v1 straight after it registers at sign-up, with no escrow (`accountHistory.create`, which fails if any version exists). For accounts created earlier, the next phone to run a tracking reconcile creates it, then backfills History wraps and re-seals Personal data to it. If two phones race, the server keeps the first and the other carries on without the key (`apps/mobile/lib/createHistoryKey.ts`). With a phrase, each version's private key is sealed as a Recovery escrow with HPKE auth mode, from the Recovery key to itself, bound to the user ID and version. See [ADR 0002](../adr/0002-every-account-has-a-history-key.md). Only someone with the phrase can create an escrow. Phones store History private keys in SecureStore with `WHEN_UNLOCKED_THIS_DEVICE_ONLY` and keep them on sign-out, like the device key (`apps/mobile/lib/historyKeys.ts`).
- **History wraps.** When an epoch is created, the creating device also wraps the epoch key to every recipient member's current History key. The server rejects the epoch unless the History wraps match that set exactly (`persistGroupEpoch` in `packages/api/src/lib/groupEpochs.ts`). Each Enrolled phone also backfills History wraps after setup and on every tracking reconcile, for epochs it can read through its own Device wraps (`apps/mobile/lib/recovery.ts`). A phone only backfills to the current History key if it holds that key and its public key matches the published one. Otherwise it uploads nothing, so setting up or resetting the phrase doesn't make the owner's other phones hand over history until they restore. The server only accepts a backfilled History wrap for an epoch from the start of the member's current membership that one of the member's own devices already has a Device wrap for. It deletes a member's History wraps for a group when they leave or are removed (`packages/api/src/router/group/groupEpochRouter.ts`, `groupMembershipRouter.ts`).
- **Restore.** A Pending device is set up by a Device link, by restoring the phrase, or by Start fresh. An active phone that doesn't hold the current History key can restore from Account › Recovery phrase. The server only returns versions that have an escrow. Restoring needs the signed-in account and the phrase. The phone checks the derived Recovery public key against the server's, opens every escrow, checks each History public key against the published one, and only then stores every version. History is then read on demand; nothing is re-encrypted. After restoring, a Pending device proves it holds the current History key and becomes active (see [Current key lifecycle](#current-key-lifecycle)).
- **Phrase change.** Needs an Enrolled device holding every History key version and a fresh sign-in (a session from the last 30 minutes). It re-seals every escrow to the new Recovery key. History key IDs, public keys and versions don't change, and no History wrap is touched.
- **Recovery reset.** For a lost phrase with no Enrolled device left, or "Start fresh" on a Pending device, including on an account that never had a phrase. It needs a session linked to a device, a fresh sign-in and typing `RESET` in the app, and activates that device. Inside its transaction the server checks again that the device is still this account's and not removed, and refuses otherwise. Removing a device deletes its sessions under the same lock. The server deletes every History key version, its escrow and its History wraps, then stores a new Recovery key and History key v(N+1) (`packages/api/src/router/accountRecoveryRouter.ts`). The phone that reset then backfills v(N+1) from its own Device wraps, so the account keeps whatever that phone can still read. The account's other phones only backfill after they restore the new phrase. Phones keep their keys for deleted versions; those keys no longer open any History wrap. When email is configured, the reset also needs a code emailed to the account's address, and the owner is emailed once it's done (OPE-218).
- **Personal data.** Nicknames and group colours are sealed as v3 to the current History key version when the phone holds that version and its public key matches the published one. A phone without it can't save them. v2 records sealed to a device key by older builds stay readable on that phone and are re-sealed to v3 when it gets the key. After setup, restore and reset, and whenever they're loaded, readable records that aren't on the current version are re-sealed to it. After a reset, records sealed to deleted versions stay readable only on phones that still hold those keys, until one of them re-seals the records (`apps/mobile/lib/personalData.ts`, `apps/mobile/lib/resealPersonalData.ts`).
- **Without a phrase.** The History key has no escrow, so it only lives on the phones that hold it. Losing every one of them means losing the account's encrypted history, nicknames and colours for good. Password reset doesn't recover them. A new phone on an account without a phrase is set up by a Device link from a phone that holds the History key, by creating a phrase on such a phone, or by Start fresh, which deletes the account's history. If no other phone of the account is active, Start fresh is the only way.
- **Not in Beta 1.** History key rotation on device revocation is OPE-167. Signing device keys and History public keys is OPE-213.

### Device links

[ADR 0002](../adr/0002-every-account-has-a-history-key.md#handing-the-history-key-to-a-new-device-ope-293) explains why this handover is acceptable when ADR 0001 rejected one.

- The new device calls `deviceLink.create`, which keeps one open link per Pending device and returns its ID. It shows the QR code `openbeacon-link:1:<linkId>:<devicePublicKey>:<psk>`, where `psk` is 32 random bytes made on the phone and never sent. The QR screen blocks screenshots and screen recording (`apps/mobile/app/setup/link.tsx`). The new phone keeps `{ linkId, psk }` in SecureStore (`WHEN_UNLOCKED_THIS_DEVICE_ONLY`) until the handover is stored, rejected or expired, or the phone is wiped, so a relaunch can finish the link (`apps/mobile/lib/savedDeviceLink.ts`).
- `deviceLink.create` refuses with `PRECONDITION_FAILED` when the account has no Active device that hasn't been removed, because no phone could scan the code. `device.status` tells the app whether another device of the account is active (`accountHasActiveDevice`). When it says no, the setup screen hides the QR option and "Create a phrase on your other phone", and offers only the Recovery phrase, if there is one, and Start fresh. While the answer is loading, failed or missing, the screen keeps every option, and it asks again each time it's shown.
- An Active device of the same account scans it and calls `deviceLink.get`, which returns the new device's ID, name, model and registered public key. The app refuses to go on unless that key is the one in the QR code, so the server can't swap in a key of its own. A link from another account, an expired or approved link, or a caller that isn't an Active device of the account is refused.
- After the user confirms, the approving phone seals `{ v: 1, historyKeys: [{ version, privateKey }] }` with HPKE AuthPSK (mode 0x03, the same suite as epoch wraps): sender = its Device key, PSK = `psk`, PSK id `openbeacon.device-link.v1`, info `["openbeacon.device-link.v1", userId, linkId, newDeviceId]` (`packages/encryption/src/deviceLink.ts`). It needs the current History key to do this. `deviceLink.approve` stores the ciphertext and activates the new device with `activatedBy = link`, which flags the account's groups for rotation.
- The new device polls `deviceLink.status`, which only answers the device the link was made for. It opens the handover with its private key, `psk` and the approving device's public key from the server, checks every private key against the published History public key for its version, and only then stores them. A handover made without `psk`, for another link, account or device, from another sender, or holding a key that doesn't match is rejected.
- "Not me" after scanning (`deviceLink.decline`) removes the Pending device as Account → Devices does, and sends the Device removed email. It doesn't need a recent sign-in, because the device can't see anything yet.

### Recovery threats

- The server never receives the phrase, the Recovery or History private keys, or an unwrapped epoch key. Tests capture every API input during setup, backfill, restore, change and reset and check for them.
- A server that substitutes a History public key receives future History wraps for that account. This is the same accepted risk as the device key directory until OPE-213. A phone that holds that version refuses to backfill or seal personal data to a mismatched key.
- A substituted or corrupted escrow is detected at restore. The server can't make an escrow of its own, because sealing one needs the Recovery private key, and the opened key must match the published History public key.
- A Device link hands over the History key only to the Device key in the QR code, so the server can't choose the receiving device. It supplies the approving device's public key, which the new device trusts until OPE-213; a server that swapped it still couldn't make a handover without `psk`, and any key handed over must match the published History public key. The server activates the new device when the handover is stored, so a new device that rejects it is active without the History key and needs Restore for its history. Someone with the password and a Pending device can't get the History key by Device link unless one of the owner's phones scans and approves its code.
- A server can leave epochs out of the list a phone receives, so the history coverage shown in the app may look more complete than it is.
- Someone with only a session can't read history without the phrase. Once the account has ever had an Active device, they can only register a Pending device, which receives no epochs. That holds after every device has been removed too: the next device is Pending, and the owner is emailed about it unless they turned new sign-in alerts off. With the password as well, they can pass the fresh sign-in and reset the phrase from a session linked to their device, which also activates it. When email is configured, that also needs a code sent to the account's address. With email off on a self-hosted server, the password alone is enough. That deletes the escrows and History wraps, but gives them no history. The owner's phones keep what their Device wraps can read, and never backfill to a History key they don't hold, so the attacker only receives History wraps and Device wraps for new epochs. Setting up or changing a phrase needs an Active device and a fresh sign-in. The server checks that there's an escrow for every History key version but can't check what's inside them. A phone that doesn't hold every version can't make escrows that open to the published History keys, so Restore rejects them. On an account created before every account had a History key, they could do it from a phone that creates v1 before the owner's phones do; that gives them only History wraps for new epochs, as above. A session alone can't set up a phrase, because setup needs a fresh sign-in on an Active device. When email is configured, the owner is emailed when the phrase is changed or reset and, unless they turned it off, when a new device signs in. Setting up a phrase on an account that has none sends no email.
- A stolen Enrolled device can read every epoch that has a History wrap for the versions it holds, including future ones, until OPE-167 rotates the History key. Removing it in Account → Devices makes the server refuse its requests, but can't take back the History key.

## When a session ends on the phone

A session ends when the user signs out, deletes their account, or the server revokes the session. Account deletion revokes every session.

The app notices a server revocation when it returns to the foreground, reconnects, or the API rejects a request as `UNAUTHORIZED`. A background upload rejected as `UNAUTHORIZED` stops capture and removes epoch keys without the app being opened.

When the session ends, or another account signs in, the app:

- Clears the query cache. Decrypted locations, nicknames, group colours, member lists and other account data are only held there, in memory.
- Removes group colours and last-upload times from MMKV.
- Removes provisioned epoch keys from native storage and stops capture. The removal is written synchronously.
- Clears the auth client's cached session.

If the app starts signed out, it runs the cleanup again, in case it was closed before cleanup finished. The cleanup is in `apps/mobile/providers/SessionDataCleanup.tsx` and `apps/mobile/lib/tracking.ts`.

Some data is kept on purpose:

- Queued tracking points stay in the offline queue as ciphertext only (OPE-63). They are scoped to the account and server, and only upload when that account signs in again. In-app sign-out tries to upload them for up to 10 seconds first. The phone no longer holds the epoch keys needed to read them. After account deletion they stay until the 10 MiB limit evicts them, oldest first.
- The device private key, device ID and public key stay, so the same account can sign in again (see `docs/development/account-deletion.md`). History private keys stay in SecureStore for the same reason.
- The server URL, theme and map preferences stay. They are not account data.
- Profile and group images may stay in the React Native image cache. These images are not encrypted on the server either.

### When the phone is removed

If the server answers with `DEVICE_REMOVED`, or the user signs out, chooses "Also remove this phone from your account" and the server removes it, the app also deletes what signing out keeps: the Device key and device ID, its History keys, and this account's queued tracking points. It then signs out. A removed phone shows "This phone was removed from your account", and the next sign-in makes a new device. The wipe is in `apps/mobile/lib/deviceRemoved.ts`. Queued points that were mid-upload when the error arrived may stay in the queue as ciphertext; the phone no longer has keys to read them.

"Also remove this phone" only signs out once the server has answered. If the app can't reach the server, or the server fails with a 5xx error, the phone stays signed in and the app offers Try again, Sign out without removing, or Cancel. If the server refuses the removal with a 4xx error, the app signs out without removing the phone and keeps its keys. If the session isn't linked to this phone yet, the app links it first and tries again.

A Pending phone has no plain "Sign out". Setup offers "Cancel and remove this phone", which removes the device with `account.removeThisDevice` the same way, sends the Device removed email and wipes the phone. If the app can't reach the server, or the server fails with a 5xx error, the user can try again or sign out anyway. A Pending device left behind that way is deleted within 7 days by the scheduled job runner.

A phone removed while the app was closed finds out on its next launch. If the app starts without a session but still has its device registration record, it sends one request naming the device. A `DEVICE_REMOVED` answer wipes the phone and shows "This phone was removed from your account". Any other answer forgets the record, as before. A phone that was removed while signed out and then signs in gets `DEVICE_REMOVED` when it registers, and goes straight to the same screen with no other alert.

## Proposed contract, pending decisions and independent review

1. Tracking plaintext and unwrapped group keys must never be sent to the API or object storage. Disclose server-visible metadata and plaintext fields accurately.
2. Group owners or admins invite existing accounts; acceptance creates a fresh epoch. New members do not receive prior epoch keys. No additional member or device approval is planned. The backend supplies device public keys in the Beta 1 trust model. Verify invitation authorization and concurrency under OPE-162.
3. Member removal must prevent the removed member from receiving future epoch keys and submitting uploads after the effective transition, including concurrent cases. Remaining active devices may upload queued ciphertext encrypted under older epochs. A removed person who retained an old key can decrypt such ciphertext if they obtain it. Removing a device (OPE-290) shipped in Beta 1 and rotates every group of the account to an epoch without it. History key rotation on device removal is deferred to OPE-167 for Public Release 1.
4. Recovery with a user-held phrase is optional. With a phrase, a new or reinstalled phone restores the History key and can read every epoch that has a History wrap, plus nicknames and colours sealed to it. Without one, losing every phone means the account's encrypted history can't be recovered. Password reset alone does not recover encrypted history. A lost phrase is changed from an Enrolled device; with no Enrolled device it can be reset, which keeps only what the account's phones can still read through their own Device wraps. A new phone gets no group keys until it's set up: by a Device link from one of the account's phones, by restoring the phrase, or by a reset ("Start fresh"). New members still don't receive epochs from before they joined. The phrase, Recovery and History private keys and unwrapped group keys must remain unavailable to the backend. When email is configured, a reset needs an emailed code, and the owner is emailed after a change or reset (OPE-218).
5. Inventory and minimize provider-visible data, logs, backups and retention; specify operational deletion and its limits. Verify hosted and self-hosted configurations independently.
6. Independently review the protocol and implementation before release. Record reviewer, scope, findings, resolutions and residual risks. Unit tests alone do not constitute security review.

## Open decisions and verification

- The owner accepts unencrypted image uploads and URL-based image access in Beta 1. Retain accurate disclosure and verify actual deployment behavior under OPE-157.
- Define retention and deletion periods for Beta 1. OPE-167 will define History key rotation on device removal for Public Release 1.
- OPE-64 locks append-only tracking history and allows uploads for any epoch belonging to the group. OPE-96 subsequently locks deletion of a departing user’s tracking data, which supersedes append-only retention for that departure case. Preserve that requirement while documenting backup and recipient-copy limits. The owner chose to retain old-epoch uploads from remaining active devices for offline continuity, accepting the confidentiality limitation after removal. OPE-63 specifies offline queue behavior.
- `groupTracking.uploadBatch` accepts points whose `senderDeviceId` is any Active device of the caller's account, not only the calling device, because the app re-sends queued points recorded under an earlier device ID. Only that account's own Active phones can do this.
- The owner accepts backend-visible group names, names, email and membership, and URL-based image access if disclosed. Verify the deployed CDN behavior and document who can access images; an unguessable URL is not authenticated access.
- Complete the code and provider inventory, exercise the lifecycle on real devices and obtain independent security review. The provider inventory, device verification and independent security review remain release gates, not blockers for the design handoff.

## Implementation and release handoff

- OPE-155: the recovery phrase, History key and History wraps ship in Beta 1, preserving the boundary that new members do not receive pre-join epoch keys. OPE-290 ships device removal in Beta 1. OPE-167 tracks History key rotation on device removal for Public Release 1. OPE-213 adds the phrase-derived identity signing key, which signs device keys and History public keys. OPE-218, also in Beta 1, requires an emailed code for a phrase reset when email is configured, and emails the owner after a phrase change or reset.
- OPE-96: implement member departure and deletion of the departing sender's group tracking data, including races and queued uploads. Deletion from the service cannot erase copies held by recipients or automatically prove backup deletion.
- OPE-157 and OPE-163: revise the image scope to reflect accepted unencrypted, URL-based access and disclose it; verify actual deployment behavior. OPE-164 should apply this contract to remaining fields rather than assume all names and membership must be encrypted.
- OPE-159 and OPE-161: verify actual provider exposure, logs, retention, deletion, device behavior and offline queue reconnection, and record evidence and limitations for hosted and self-hosted deployments. Independent security review of the contract and implementation remains required before release.

The issue's completion and the beta release are separate decisions. A written contract does not establish that its future implementation, deployment or security review is complete.
