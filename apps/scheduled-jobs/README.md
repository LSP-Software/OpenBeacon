# Scheduled jobs

The scheduled job runner is a separate Bun process and Docker image released alongside the backend. It runs seven jobs:

- `account-deletion` runs once per minute. It deletes accounts at the end of their grace period and retries image cleanup.
- `expired-records-cleanup` runs once per hour. It deletes:
  - `Verification` rows whose `expiresAt` is before the database time. These hold email codes, the tokens issued for a correct code and better-auth's own verification records, together with the email address or user ID they are for. It runs whether or not email is configured.
  - `Session` rows whose `expiresAt` has passed. better-auth only deletes an expired session when someone presents it, so abandoned sign-ins would otherwise keep their IP address, user agent and device link. Their device challenges and Google deletion challenges go with them.
  - `GoogleDeletionChallenge` rows whose `expiresAt` has passed.
  - `GroupSharedInvite` codes a day after they expire. Codes last 5 minutes, so this covers used codes too; the day lets an open invite dialog still read the code's status.
  - `GroupJoinAlert` rows (which hold the joining member's name) 30 days after they were created, or once the recipient is no longer in the group.
  - `GroupMemberInvite` email invites 30 days after they were sent, or once the person who sent them is no longer in the group. Leaving or being removed deletes them straight away; this catches any left behind. The app stops showing an invite once it is 30 days old, even before the job runs.
  - `Feedback` 30 days after it was received. Only the hosted API stores feedback; on a self-hosted backend the table stays empty.

  Unexpired rows, live sessions and usable invites are kept.

- `location-history-cleanup` runs once per hour. It deletes `trackingPoint` payloads in `GroupEncryptedPayload` whose server `createdAt` is more than 60 days before the database time; a point exactly 60 days old is kept until the next run.
- `epoch-cleanup` runs once a day. It deletes epochs that a newer epoch replaced more than 60 days ago and that no stored payload still uses, which also deletes their Device wraps and History wraps. The latest epoch of a group is never deleted, so new epochs keep their numbering. A phone that was offline for more than 60 days can still hold queued points for a deleted epoch. The server doesn't store them and lists them as `expired` in the upload response, so the app deletes them from its queue instead of retrying them.
- `pending-device-cleanup` runs once per hour. It deletes Pending devices (signed in but never set up) created more than 7 days before the database time, and signs out their sessions. It also deletes removed Pending devices 7 days after they were removed. Active devices, and removed devices that were ever active, are kept. It also deletes device links (QR codes), approved or not, a day after their code expires. It also deletes expired device challenges, the one-time values a phone answers to prove it holds a key.
- `pending-upload-cleanup` runs once per hour. It deletes profile and group image uploads that were requested more than an hour ago but never confirmed: first the file in storage (every version), then the `PendingUpload` row. Upload links last 5 minutes, so an hour is well past any upload still in progress. If the file is somehow already the user's or group's image, only the row is deleted.
- `image-storage-sweep` runs once a day. It lists every object version under `user/` in the S3 bucket and deletes avatar files (`user/<id>/uploads/avatar/…` and `user/<id>/uploads/group/<id>/avatar/…`) more than an hour old that no user, group or pending upload points to, including delete markers. For an image still in use it keeps the current version and deletes older ones. This catches files the other paths miss: an upload made with an old link after a newer one was requested, an upload for a group deleted before it was confirmed, or a replaced image whose deletion failed. Other keys in the bucket, including images under the old `group/<id>/uploads/avatar/` path, are left alone. Before listing anything it checks that every stored user and group image under `/user/` starts with `<S3_CDN_URL>/<S3_BUCKET_NAME>/`; if any doesn't, it skips the whole sweep and logs `Image storage sweep skipped: stored image URLs don't match S3_CDN_URL and S3_BUCKET_NAME`.

Run it locally with `bun run dev --filter=@openbeacon/scheduled-jobs`; it reads the root `.env`.

The runner requires `DATABASE_URL`, `S3_ACCESS_KEY_ID`, `S3_ACCESS_KEY`, `S3_BUCKET_NAME`, `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, and `R2_BUCKET`. `S3_ENDPOINT` and `S3_REGION` are optional and use the same defaults as the backend. When the backend has email configured, give the runner the same email settings (`RESEND_API_KEY` or the `SMTP_*` settings, `EMAIL_FROM` and `SERVER_NAME`) and `REDIS_URL`, so it can email owners when their account is deleted at the end of the grace period. Without them it deletes accounts as normal but sends no email. See the root `.env.example`. To refresh the map automatically, set `MAP_TILES_SERVICE_URL` and `MAP_TILES_API_KEY` to the map tiles service and its key; the runner then asks it once a day to refresh, and the service decides whether a refresh is due (see `apps/map-tiles/README.md`). Configure these values separately for the runner in Coolify; the backend and runner must use the same database and R2 bucket. Do not put credentials in Git.

> [!WARNING]
> `S3_CDN_URL` and `S3_BUCKET_NAME` must match the backend's values exactly. `S3_CDN_URL` has a default, so set it explicitly on both if the backend doesn't use the default. The image storage sweep decides whether a file is in use by rebuilding the image URL from these two values, so a mismatch would make every image look unused and delete it permanently. The sweep refuses to run if stored image URLs don't match, but don't rely on that. Never let two deployments (for example staging and production, or two self-hosted servers) share one bucket: each one's sweep would delete the other's images.

On startup the runner checks PostgreSQL with `SELECT 1`, lists S3 object versions, reads the map tiles manifest from R2 and checks that the current PMTiles archive exists (with no manifest yet it only checks it can read the bucket), checks it can reach the map tiles service with `MAP_TILES_API_KEY` when `MAP_TILES_SERVICE_URL` is set and, when email is configured, checks the email settings without sending anything. Its credentials also need permission to delete image objects, versions and delete markers. It exits if configuration or connectivity checks fail. Clients are closed on shutdown. The Docker image generates the Prisma client but does not apply migrations.

Once the checks pass, the runner serves `GET /health` on `127.0.0.1:3000`, inside the container only. It returns the same status, backend version and server name (`SERVER_NAME`) as the backend's health check. The image's Docker `HEALTHCHECK` calls it with Bun, so Coolify can tell when the runner is up. Leave the port unpublished.

## Adding a job

Register an object in `src/jobs/index.ts` with a unique stable `name`, a positive integer `delay` in milliseconds (at most 2,147,483,647), and an async `run` function. Put job-specific work in `src/jobs`. The shared Prisma, S3, and R2 clients are available from `src/services.ts`; pass them to jobs explicitly. Create and validate additional clients once at startup and close them after the scheduler stops. Grant only the permissions jobs need in addition to the startup checks.

Jobs start immediately on process startup. After each run completes or fails, the runner waits the configured delay before starting it again. Runs of the same job do not overlap within one process; different jobs can run concurrently. Failures are logged with the job name and the error code (or error name) only, never the error itself, and retried after the same delay. Shutdown stops future runs and waits for active work. Jobs should have bounded execution time so a container can shut down within its configured grace period. Account deletion processes at most 100 due accounts and 100 image cleanup records per run, and defers failed records for five minutes so other records can progress. Pending device cleanup skips a device that a request has locked at that moment; a later run deletes it. It deletes device links and challenges separately, so a skipped device doesn't hold them up. Expired records cleanup deletes verification rows with one `DELETE`; they expire within minutes, so an hourly run only finds an hour's worth. It deletes the other tables 1,000 rows at a time, at most 10 times per table per run. A table that fails is logged by name, with the database error code when there is one, and the remaining tables are still cleaned. None of their `expiresAt` columns are indexed. `Session` can be large, but an index was left out on purpose: it would stop session refreshes from being HOT updates and slow them down, and an hourly scan measured about 40 ms on 1 million sessions. Location history cleanup deletes the oldest due points first across all groups, 1,000 per statement, using the `(kind, createdAt)` index, so a run only reads rows that are due and costs one index probe when nothing is. A run stops after 500,000 points. When it stops at that limit it logs `Location history clean-up reached its limit of 500000 points; the rest will be deleted on later runs`, without any IDs; if that shows up every hour, uploads are outpacing the clean-up and points are staying past 60 days. Points that a concurrent delete has locked, such as a member leaving, are skipped (`FOR UPDATE SKIP LOCKED`). A failed statement stops the run and logs one line with the database error code; the next run carries on. Epoch cleanup walks the epochs created more than 60 days ago once a day, 5,000 at a time in `(createdAt, id)` order, and deletes the ones in each page that can go. An epoch that an upload in progress has locked is skipped (`FOR UPDATE SKIP LOCKED`) and looked at again the next day. An upload that read the epoch just before the job deleted it can fail once with a server error; when the app retries, the server lists those points as `expired`. A failed page stops that day's run and logs one line with the error code. Pending upload cleanup handles at most 500 uploads per run, each in its own transaction. It locks the row with `FOR UPDATE SKIP LOCKED`, so an upload being confirmed at that moment is skipped. A confirmation that arrives after the row is deleted fails, and the person picks the image again. If storage refuses the delete, the row is kept and retried next run; each run logs one line with the number of failures and their error codes. The image storage sweep checks each listed page of versions against users, groups and pending uploads in one `REPEATABLE READ` snapshot, so an image confirmed during the sweep is never treated as unused. It only deletes versions more than an hour old, and new uploads always use a new random file name. It scans the `User` and `Group` tables once per 1,000 object versions, because `image` isn't indexed; that's fine once a day at our size, but add an index on `image` if it ever shows up as slow. A failure stops that day's sweep and logs one line with the error code; the next day's run starts again from the beginning. Until a backlog clears, rows can stay past 60 days, and deleted rows stay in database backups until those backups are replaced. `GroupEncryptedPayload` has `autovacuum_vacuum_scale_factor` set to 0.02 and `autovacuum_vacuum_cost_limit` set to 1000, so dead rows from these deletions are vacuumed sooner and faster. This matters because the clean-up reads the `(kind, createdAt)` index from its oldest end: until a vacuum removes the deleted entries, each batch steps over them. A benchmark with 1 million groups and 10 million points measured an empty hourly run at about 2 ms, 50,000 due points in under half a second, and a 3.4 million point backlog cleared at 100,000 to 175,000 points a second while the index was clean, slowing to about 15,000 a second when vacuum fell behind. The daily epoch clean-up took about 7 seconds per million old epochs. The new index made no measurable difference to upload speed.

Schedules and run history are not persisted. Restarts run every job again; missed intervals are not backfilled. Run exactly one runner per backend installation, and make jobs idempotent and safe to retry after interruption. Deployments may briefly overlap old and new containers: before adding a job with side effects, implement and test distributed coordination and durable scheduling appropriate to that job. Do not assume this runner provides exactly-once execution, cross-process locking, or persistent last-run tracking. Add database migrations and integration tests when introducing durable state. The x-bot runner persists last-run times, but also records failed runs as completed; do not copy that failure behavior.

Keep tracking plaintext, encryption keys, credentials, and user data out of logs. Test scheduling and failure behavior as well as the job's business logic. Avoid coupling jobs to the API process: both containers should use shared packages and the same backing services where necessary.

## Deployment

The `Build images` workflow builds both images from the same commit. The `Deploy backend` workflow releases them together and deploys the backend first and then the `OpenBeacon Scheduled Jobs` Coolify application. A backend deployment failure prevents the runner deployment; a runner deployment failure leaves the backend deployed and requires operator intervention. Check both applications after a release and roll back both by releasing an earlier version. Future schema changes must remain compatible across the rollout. The runner image does not apply migrations; the backend owns them.
